# Orchestrarr

> Act. A self-hosted orchestrator agent that coordinates worker agents to fix, update and verify, in the spirit of the *arr suite.

**Status: first verticals, read-only.** Orchestrarr reads Portarr's findings and the dependency pull requests from GitHub, and shows them as **a table of problems** (one row per problem, how far each goes by itself, and one authenticator code validates the whole selection; the table has three tabs (to decide, to configure, to know), a row can be set aside, and a history keeps what was decided ([ADR 0027](docs/adr/0027-the-table-shows-what-can-be-decided-by-application-and-keeps-what-was-decided.md)); [ADR 0019](docs/adr/0019-a-decision-is-a-problem-the-table-selects-and-one-code-validates.md)). It holds **no write power yet**: nothing merges, deploys or writes to a repository. **People sign in with local accounts** (a name and a password, a cookie session kept by the server, roles made of permissions: `Admin`, `Operator`, `Reader`; [ADR 0018](docs/adr/0018-people-sign-in-with-local-accounts-and-permission-based-roles.md)), the same way as in Portarr and Mnemarr; every route of the API needs a session, and only an operator (or an administrator) approves. **Validating a selection records a decision per pull request** (pull request, commit, steps, approver) in a queue and an audit trail, with a global stop, kept in memory or, with `Storage:Provider=Sqlite` (the image's default), in a file that survives a restart; the Runner (below) validates a pull request for real in a throwaway container and lets an agent try to repair it on paper; merging is a dry run and nothing is written to a repository. The roadmap is in [docs/SPEC.md](docs/SPEC.md) §8; the founding vision in [docs/VISION.md](docs/VISION.md); how an order is secured, from the person to the machine, in [docs/security-model.md](docs/security-model.md).

**Runner.** The Runner that takes the approved tasks is a .NET process per environment (`src/Orchestrarr.Runner`): every task is typed, approved with a second factor (an authenticator-app code) that the Runner checks itself, and leaves a full trace that the interface shows ([ADR 0017](docs/adr/0017-orders-are-typed-tasks-approved-with-a-second-factor-that-the-executor-checks.md)). It checks everything, then validates a pull request for real in a throwaway container and lets an agent try to repair it, the patch being shown and **nothing pushed** ([ADR 0024](docs/adr/0024-a-pull-request-is-validated-for-real-and-an-agent-may-try-to-repair-it-on-paper.md)); merging is a dry run. **Decided, not built:** applications are described in a private configuration repository, today read from a JSON file ([ADR 0020](docs/adr/0020-applications-are-described-in-a-private-configuration-repository.md)); a separate qualification host precedes production ([ADR 0021](docs/adr/0021-qualification-on-a-separate-host-then-promotion-through-the-git-flow.md), proposed). Open before the first write power: who starts a workshop run (Q-28), how a required review is met (Q-14) and a merge on a repository that deploys itself (Q-29); see [docs/SPEC.md](docs/SPEC.md) §9.

Orchestrarr reads the findings of [Portarr](https://github.com/MafLabs38/portarr) (vulnerable dependencies, outdated images, broken applications), plans the work, delegates it to worker agents, verifies that nothing regressed, and proposes the result as a pull request for a human to approve. Safety and approval gates are core concerns: no direct push, sandboxed workers, least privilege, bounded budgets, full audit trail. It works with Mnemarr, the companion long-term memory.

## Releases

A release is a pull request `develop → main`, merged with a **merge commit** (`main` refuses squash: semantic-release reads the commits of the pull request, [ADR 0009](docs/adr/0009-releases-are-decided-by-semantic-release-from-main.md)). The pipeline then picks the version from the Conventional Commits (`feat` minor, `fix` patch, below 1.0 a breaking change is a minor), tags it, publishes the GitHub release and the image `ghcr.io/maflabs38/orchestrarr:<version>`. The title of every pull request into `develop` is a Conventional Commit and decides the version. The cluster's GitOps repository follows the newest version tag.

## Repository settings

The GitHub repository, its branches, rulesets and labels are declared as code in `repos/orchestrarr.yaml` of `MafLabs38/github-template`: change a setting with a pull request there, never in the GitHub settings. `ci.yml`, `codeql.yml`, `mutation.yml` and `ai-review.yml` (the five advisory review agents) are the pipeline (see [docs/TESTING.md](docs/TESTING.md)). CodeQL runs but does not gate merges: the ruleset waits for CodeQL results, so a skipped CodeQL would block every merge.

Before a push, check that no real infrastructure value slipped in (`gitleaks dir .`).

## Run in the sandbox

Needs the .NET 10 SDK and Node 22.

```bash
# API, with the sample data of samples/ (http://127.0.0.1:7878). The first start needs a first administrator (see below)
dotnet run --project src/Orchestrarr.Host

# Interface with hot reload (http://127.0.0.1:5178, on the loopback only), proxying /api to the API
cd frontend && yarn install && yarn dev

# Tests and lint (see docs/TESTING.md)
dotnet test --solution Orchestrarr.slnx && dotnet format Orchestrarr.slnx --verify-no-changes
cd frontend && yarn test && yarn lint && yarn stylelint && yarn format:check && yarn typecheck
```

**The first administrator.** An empty Orchestrarr has no account and nobody can sign in. The first start creates one, from a name and a **password file** (never a value in the environment): `printf '%s' 'a long password' > ~/admin-password && chmod 600 ~/admin-password`, then `Auth__AdminUser=root Auth__AdminPasswordFile=$HOME/admin-password dotnet run --project src/Orchestrarr.Host`. The administrator then creates the other accounts in the interface (System, Accounts): an `Operator` approves and engages the global stop, a `Reader` only reads. A password is at least 12 characters. In Development the cookie is not `Secure` (`Auth:CookieSecurity=SameAsRequest`), so a sandbox on a private network can be opened over plain HTTP: `dotnet run` listens on the loopback, and to open it from another machine, forward the port (`ssh -L 5178:127.0.0.1:5178 <host>`) rather than listening on every interface. If nobody can sign in any more, the break-glass settings `Auth__ResetPasswordUser` and `Auth__ResetPasswordFile` reset that account at the next start (remove them once used).


**The screens are live.** The host opens a WebSocket (SignalR) at `/api/v1/live` that tells the page what changed (runs, approvals, the trail, the status, the table, the accounts, the options); the page then reads it through the API. A badge in the header says whether it is live; without it the page reads again every thirty seconds. A reverse proxy should pass WebSocket upgrades (in development the Vite proxy does); without them the page falls back to server-sent events or long polling, and to its 30-second reading when nothing works. The Runner sends the trace of a run as it goes on (`Runner:LiveSendMilliseconds`, 1000), and the work of an agent (what it says, reads, edits and runs) is in the trace.

**Run the Orchestrarr Runner (a dry run unless a validation profile is configured, see below: it checks everything, and merging always stays a dry run).** `dotnet run --project src/Orchestrarr.Runner -- run`, configured with an `runner.json` or with environment variables, each starting with `ORCHESTRARR_`: `ORCHESTRARR_Runner__Name`, `ORCHESTRARR_Runner__ControlPlane__Url` (https, or a private network), `ORCHESTRARR_Runner__ControlPlane__Token` (or `...TokenFile`), `ORCHESTRARR_Runner__Rights__Kinds__0=ValidatePullRequest`, `ORCHESTRARR_Runner__Rights__Repositories__0=example/*` (an empty list refuses everything), `ORCHESTRARR_Runner__JournalPath` (the host's journal), `ORCHESTRARR_Runner__DataPath` (`runner.db`), `ORCHESTRARR_Runner__RequireSecondFactor` (true; `false` stops the Runner from checking the code, **and the Runner then refuses to start unless `DOTNET_ENVIRONMENT` (or, when it is unset, `ASPNETCORE_ENVIRONMENT`) is `Development` or `Testing`**, accepted only while every handler changes nothing outside its sandbox (a dry run, a validation or a repair), and the control plane's option cannot set it: both sides have to be relaxed to approve without a code), `ORCHESTRARR_Runner__LocalStopFile` (a file there stops the Runner: it asks for nothing while the file exists and a run ends before its next task; default `STOP` in the folder of `runner.db`, so the local stop is never off; the global stop of the control plane is read when a batch is claimed and again while a run goes on, every `ORCHESTRARR_Runner__StopPollMilliseconds` (3000): the task that is running is cancelled and its container killed, and a control plane that cannot be read three times in a row counts as a stop) and `ORCHESTRARR_Runner__PollSeconds` (3). **Validating a pull request for real** is configured in the Runner's own file, never by a task, and only on a host that is declared a workshop (`Runner:Validation:Workshop=true`: the code of pull requests runs in containers there, from a user that can start any container, so never on the host of a production environment): `Runner:Validation:WorkRoot` (a folder where each run gets a fresh clone, removed after), `GitTokenFile` (a file with a read-only token, given to the `git` process only, never to the container or the trace), `RepositoryUrl` (`https://github.com/{0}.git`), and `Profiles`, each with `Repositories` (patterns), an `Image` and `Steps` (`Name`, `Command`, `Network`: off by default, an install step turns it on). For each approved task the Runner fetches `refs/pull/<n>/head`, refuses it if the head is not the approved commit, then runs each step with `docker run` as a non-root `ContainerUser` (default `1000:1000`), `--cap-drop ALL`, `no-new-privileges`, a read-only image (the work folder and `/tmp` are what is written), bounded CPU (`Cpus`), memory (`MemoryMegabytes`, `PidsLimit` (512), `TmpfsMegabytes` (512, the temporary folder of a container)), processes and time (`StepTimeoutMinutes`), and writes the end of every step's output (`MaxOutputCharacters`, colours removed) in the trace. A step that fails ends the task as `failed` and the merge of the same approval is skipped; a fetch, a commit or a container that cannot be started (docker itself failing, exit 125) is a refusal, while a step whose tool is missing from the image (exit 126 or 127) is a failed step. Nothing is written to the repository. Running docker is a power of its own: the user of the Runner can start any container, so run it as a user meant for that. The validation changes nothing outside its container, so a Runner that only validates may run without the code of the second factor in development (`Runner:RequireSecondFactor=false`, and the host's option relaxed too); the first handler that merges or pushes will not be allowed to. **Repairing a pull request** (a third kind of task, `RepairPullRequest`: a pull request whose checks fail on the forge, or that failed when the workshop ran it, goes up to "Repair" in the table, where the `repair` step is granted and a Runner accepts the kind; selecting the row approves the repair, and a repair that worked leaves a patch and no action): the Runner validates it first, and when it fails an agent (Claude Code, headless, on the subscription) tries to make it pass in a container that holds the token of the subscription and the folder of the run, nothing else; the Runner then runs the steps again itself (the agent's word is not a fact), refuses a change to a protected file (the tests, the dependencies, the pipeline: `Runner:Repair:ProtectedPaths`) and puts the patch in the trace. **Nothing is pushed**: applying a patch is a write power that is not built. Configure it beside the validation: `Runner:Repair:Image` (build `docker/agent/Dockerfile`), `MaxTraceLines` (150: the most lines of the agent's work kept in the trace), `TokenFile` (a file with `CLAUDE_CODE_OAUTH_TOKEN`; it goes to the agent's container as an environment variable, never in an argument or the trace), `Model` (`sonnet`), `MaxTurns` (20), `TimeoutMinutes` (15), `Cpus`, `MemoryMegabytes`, `MaxOutputCharacters` (20000: the most of what a failing step printed that is given to the agent), `ProtectedPaths` (the globs of the files an agent may not change: enforced by the Runner after the agent) and `ProtectedSummary` (the same in words, which is what the prompt says), `Prompt` (the template: what the failing step printed is placed between markers as data), and add `RepairPullRequest` to `Runner:Rights:Kinds`. The agent's container can reach the network (the API of the model, the package registry): that is acceptable for a test application and a reason to restrict its egress before it touches anything private. The token must be one of the host's `Tasks:Runners`. Enrol each operator in **your own terminal** (the secret is shown once, as a QR code, and never reaches the control plane): `dotnet run --project src/Orchestrarr.Runner -- enroll-operator --subject <account id>`, where the id is the `subject` of `GET /api/v1/auth/me` (shown on the Account screen). Other commands: `operators`, `delegations list|add|revoke` and `acts` (what the operators did on this Runner: enrolments, replaced secrets, delegations given and revoked, in an append-only table; never a secret or a code). There is no image of the Runner yet (the only image besides the control plane's is the agent's, `docker/agent`, built where the Runner runs). It refuses to start while settings under the old name remain (`Executor` settings, `ORCHESTRARR_Executor__…` variables or an `executor.json`, ADR 0026), and it moves an old `executor.db` next to the default `runner.db` to the new name so that the enrolments are kept.

To read a real Portarr instead of the sample, set `Portarr:BaseUrl` and give the key as `Portarr:ApiKey` through the environment (`Portarr__ApiKey`) or `dotnet user-secrets`: the key never goes in a file that is committed. Redirects are not followed, so the key only goes to that address; use https or a private network.

To read the dependency pull requests, give a GitHub token that can **only read** as `GitHub:Token` (`GitHub__Token`, or `dotnet user-secrets`): a fine-grained token with *Pull requests: read*, *Checks: read* and *Commit statuses: read* on the repositories (without the last one, the checks of a repository that reports commit statuses stay unknown). Without a token the screens say the pull requests were not read. The token only goes to the configured API address, which must be https (redirects are not followed). The pull requests of the bots of `GitHub:BotLogins` are read (default: Dependabot and Renovate); a list in the configuration replaces the default. For a demo without GitHub, `Forge:SamplePullRequestsFile` reads a file of the shape of `samples/github-pull-requests.sample.json`.

### API

Under `/api/v1`. **Every route needs a session** (a `401` with no body without one, unknown routes included), except `POST /api/v1/auth/login` and `GET /health` (`{ "status": "ok" }`, for a probe); the files of the interface are public, since they say nothing about the fleet. Each route needs a permission of the person's role (a `403` without it): reading needs `fleet.read` (every role), the trail `audit.read`, approving `approvals.create` and the global stop `stop.control` (`Operator`, `Admin`), accounts `accounts.manage` and the options `options.manage` (`Admin`). **A write from a person carries the header `X-Orchestrarr-Request`** (any value: a page of another site cannot add it; the interface does), or it is a `403`. The routes of the Runners are under `/api/v1/runner` and carry their own token, not a session. Every answer forbids being framed by another page and being sniffed, carries a policy that keeps the interface's scripts, styles and requests to itself (`Content-Security-Policy`); with `Auth:CookieSecurity=Always` (the default) it also carries `Strict-Transport-Security`. Nothing here runs anything:

| Route | Gives |
|---|---|
| `GET /api/v1/work-items[?refresh=true]` | The work items, with their findings, plan and pull requests |
| `GET /api/v1/work-items/{id}` | One work item (404 if unknown) |
| `GET /api/v1/problems[?refresh=true]` | The table: one row per problem (`id`, `application` (the name a person knows, with its `icon` and `applicationId` when Portarr names the application; the repository or the image is in `source`), `kind`, `description`, `severity`, `checks` (`unknown`, `pending`, `passing`, `failing`, or `notRun` for a bot's pull request whose only failing checks need secrets), `pullRequest`, `headSha`, `url`), with the `tab` of the row (`act`, `configure` or `know`), `inProgress` while an approval works on it, `goesUpTo` (`noAction`, `repair`, `qualification`, `mergeIntoDevelop`, `production`), `workshop` (what the Runner's validation or repair last said about this commit: `unknown`, `passes`, `fails` or `repaired`), `why` it stops there (among others `qualificationFailed`, `repairFailed`, `patchReady`, `passesHereChecksFailing`) and `canStopBeforeProduction`, the `descriptionsVersion` it was computed from, and `skipped`, the number of rows set aside (they are not in `rows`). How far a row goes is the lowest of what the description of the application allows (`Applications:File`), what the connected Runners accept and the powers granted, and the state of the pull request (checks, mergeable) |
| `POST /api/v1/problems/approve` | Validates a selection with **one** code: `{ "rows": [{ "id", "headSha", "stopBeforeProduction" }], "secondFactorCode" }`. The plan is computed again on the server from the current table (a row with no action, a moved commit or an unknown row is a `409 planChanged`); the pull requests of every application become **one batch** that the Runner checks once. The trail keeps the effective plan (`goesUpTo`, `stopBeforeProduction`, the version of the descriptions). A reader gets a `403` |
| `POST /api/v1/problems/skip` | Sets rows aside: `{ "rows": [{ "id", "description" }], "reason" }` (the description the operator saw: a row that changed since is refused with `409` `planChanged`). The row leaves the table until its target changes or the problem is gone (the skip then ends, `problem.skip-lapsed` in the trail); the history keeps it. Needs the right to approve, no second factor; traced in the trail. `400` for an empty request, more than 200 rows or a reason of more than 300 characters; answers `{ "skipped": <n> }`, `409` `inProgress` for a row an approval is working on, `409` `danger` for a row of severity danger, `503` when the trail or the store cannot be written (a skip that cannot be traced is not made) |
| `POST /api/v1/problems/unskip` | `{ "id" }` of a line of the history: takes the skip back (`204`; `404` when there is none; `400` `invalidRequest` without an `id`; `503` when the trail or the store cannot be written). Needs the right to approve, no second factor |
| `GET /api/v1/problems/history[?state=approved\|skipped&limit=&before=]` | What was decided, newest first, a page at a time (100 by default, 200 at most; `next` is the `before` of the following page): the photograph of the row, who and when, and the outcome (`skipped`, `inProgress`, `passed`, `failed`, `repaired`, `refused`, `expired`, `ended`) |
| `GET /api/v1/icons/{name}` | The picture of the icon of an application, relayed from the source of the fleet (`404` when there is none); served so that it cannot run anything |
| `GET /api/v1/system/status` | Name, version, the state of the sources (`source`, `forge`) and of approving (`approvals`: the identifier `operator` (the id of the account) and the name to show `operatorName`, `isOperator` (whether this person may approve and stop), `killSwitchEngaged`, `killSwitchSaved`, `requiresSecondFactor`: whether the interface asks for the code), where things are kept (`storage.kind`, `sqlite` or `memory`) and `runners` (each Runner that asked for work: its name, version, kinds, repositories and delegations, as it reported them) |
| `GET /api/v1/options`, `PUT /api/v1/options/{id}` | The options (today `approvals.require-second-factor`): `value`, `canTurnOff`, and `lockedReason` (`host` or `configuration`). `PUT` needs `options.manage` and `{ "value", "password" }`; turning one off also needs the host started with `Options:AllowRelaxingSecurity` (`403 lockedByHost` otherwise), the password of the administrator (`400 passwordRequired`, `401 invalidCredentials`) and is traced as `option.changed`; turning on asks for nothing |
| `POST /api/v1/approvals` | Approves a card: `{ "workItemId", "steps", "pullRequests": [{ "number", "headSha" }], "secondFactorCode" }`, the pull requests and commits the card displayed. `secondFactorCode` is the six-digit code of the authenticator app: the control plane only checks its shape (`422` `secondFactorRequired`), the Runner checks that it is right. The server decides the repository, the powers and the approver, and refuses unless what was displayed is what is there now |
| `GET /api/v1/approvals?limit=` | The approvals, newest first, each with its state (`waiting`, `taken`, `ended`, `refused`, `expired`; `ended` is a run that is over, whatever its result, which the run says), the batch it belongs to and when it ended: 200 by default, 1,000 at most; a `limit` outside 1 to 1,000 is brought back into that range, and if the file cannot be read the route answers `503` `storageUnavailable`, never an empty list |
| `GET /api/v1/audit?limit=` | The audit trail (the screen is called Activity; the route is not, because some content blockers refuse a request to a path called `activity`), newest first: 200 by default, 1,000 at most, with the same bound and the same `503`. The `id` of an entry is its number in the trail, counted from 1 in the order it was recorded: it never changes |
| `GET /api/v1/runs[?limit=]` | The runs of the Runners, newest first: 100 by default, 500 at most; `503` `storageUnavailable` if the file cannot be read |
| `GET /api/v1/runs/{id}` | One run with its tasks and the hash-chained timeline of its trace (404 if unknown) |
| `GET /api/v1/auth/me` | Who is signed in: `{ subject, name, role, permissions }`; `subject` is the id of the account, which the approvals and the Runner's second factor use. `401` when nobody is |
| `POST /api/v1/auth/login` | `{ "name", "password" }`: starts a session and sets the cookie (`HttpOnly`, `SameSite=Strict`, `Secure` with the `__Host-` prefix by default). `401` `invalidCredentials` for a wrong password and an unknown name alike; `429` `locked` (five failures in fifteen minutes lock the name, with `Retry-After`) or `busy`. No session needed (it still needs the `X-Orchestrarr-Request` header, like every write from a person) |
| `POST /api/v1/auth/logout` | Ends the session on the server, so a copied cookie is dead |
| `POST /api/v1/auth/password` | `{ "currentPassword", "newPassword" }`: changes one's own password and ends the other sessions of the account |
| `GET/POST /api/v1/accounts`, `PUT/DELETE /api/v1/accounts/{id}`, `POST /api/v1/accounts/{id}/password`, `GET /api/v1/roles` | The accounts and the roles, for an administrator. A change of a role or of the state applies at once; a disabled account loses its sessions; the last enabled administrator can be neither deleted, disabled nor demoted (`409` `conflict`) |
| `GET /api/v1/safety` | The global stop: `{ "killSwitchEngaged", "saved" }`; `saved` is false when it is engaged but the file could not take it (a restart would release it) |
| `PUT /api/v1/safety/kill-switch` | The global stop: `{ "engaged": true }`. Engaged, nothing is approved. Engaging always takes effect; a release is answered `503` `killSwitchUnavailable` when it cannot be saved, or `503` `auditUnavailable` when it cannot be written to the trail, and the stop stays engaged |

Approval answers: `201` recorded; `401` with no body when nobody is signed in; `403` for a role that cannot approve (no body), or `notAPerson`, `notAnOperator`; `404` `unknownWorkItem`; `409` `pullRequestsNotRead`, `planChanged`, `alreadyApproved`; `422` `tooManyPullRequests` (more than 100 pull requests on a card with both steps), `tooManyRepairs` (more than five repairs in one approval), `nothingTicked`, `stepNotOffered`, `stepNotGranted`, `stepNotSupported`, `mergeNeedsValidation`, `noPullRequests`, `secondFactorRequired`; `423` `killSwitchEngaged`; `429` `tooManyRequests` (see `Approvals:ApprovalsLimit`); `503` `storeFull`, `auditUnavailable`. A draft pull request is never approved. The global stop answers `401` without a session and `403` without the permission.

**Runner routes** (`POST /api/v1/runner/claim`, `/runs/{id}/events`, `/runs/{id}/complete`): `Authorization: Bearer <token>` of one of the `Tasks:Runners`, no session and no `X-Orchestrarr-Request` header. The token is checked before the body is read, which is capped at 256 KiB. The routes exist only when a Runner is configured. Answers: `401` `notSignedIn` with `WWW-Authenticate: Bearer`, `400` `invalid` for a claim that does not say who the Runner is, `409` `notYours`, `422` `invalid`, `503` `storageUnavailable`.

| `Powers:Grants` | none | What the operator grants: a list of `{ "Repository": "owner/name" or "*", "Steps": ["validate", "mergePullRequests", "repair"] }`; `repair` lets a failing pull request go up to *Repair* (an agent tries on paper, nothing is pushed, ADR 0024). | `Auth:ResetPasswordUser`, `Auth:ResetPasswordFile` | none | Break-glass: while both are set, that account gets the password of the file, is enabled, and loses its lockout and its sessions, at **every start**. Remove them once used |

`dotnet run` runs as Development: it reads the sample data and grants validate, merge and repair on every repository, so the Approve button works for an operator. The image runs as Production, where there is no grant and no sample data, the cookie is `Secure` (so serve it over https) and `appsettings.Development.json` is not carried; give it the first administrator (`-e Auth__AdminUser=root -e Auth__AdminPasswordFile=/run/secrets/admin-password`, a secret mounted as a file) and keep the cookie's keys in `/config` with the database. The file is the state of the product: keep `/config` on a local disk (not a network share), owned by the image's user (`$APP_UID`: with a bind mount or a volume claim, set the owner or `fsGroup`, otherwise the host stops at its start), run a **single replica** (the host takes a lock on `orchestrarr.db.lock` and a second host on the same file refuses to start) (a rollout that starts the new pod before stopping the old one is a second writer: use a `Recreate` strategy), and back it up with SQLite's online backup from a container that has the `sqlite3` tool and mounts the volume (`sqlite3 /config/orchestrarr.db ".backup /config/copy.db"`; the image does not ship it, and a copy of the file alone while the host runs can be torn). It holds the identifiers of people and their decisions, no credential. **When the queue (10,000 approvals) or the trail (200,000 entries) is full**, every approval is refused (`storeFull`, `auditUnavailable`) until you archive and start again: stop the host, take the online backup, move the file away and start the host, which creates a new database that **starts with the stop engaged**; release it once, deliberately. The retention policy itself is Q-24. It listens on port 8080 as a non-root user: `docker run -p 8080:8080 -v orchestrarr-config:/config -e Portarr__BaseUrl=... -e Portarr__ApiKey=... -e GitHub__Token=...`.

> **Security.** Every route of the API needs a sign-in, and there is no mode that trusts the network. The database holds the **password hashes** of the accounts (PBKDF2): it is a secret, and so is a backup of it. Serve the interface over https and keep `Auth:CookieSecurity=Always`; do not publish the port of a Runner-facing route to the Internet (ADR 0017). Never start the image with `ASPNETCORE_ENVIRONMENT=Development`.
