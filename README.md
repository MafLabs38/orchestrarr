# Orchestrarr

> Act. A self-hosted orchestrator agent that coordinates worker agents to fix, update and verify, in the spirit of the *arr suite.

**Status: first verticals, read-only.** Orchestrarr reads Portarr's findings and the dependency pull requests from GitHub, and shows them as decision cards. It holds **no write power yet**: nothing merges, deploys or writes to a repository. **People sign in with local accounts** (a name and a password, a cookie session kept by the server, roles made of permissions: `Admin`, `Operator`, `Reader`; [ADR 0018](docs/adr/0018-people-sign-in-with-local-accounts-and-permission-based-roles.md)), the same way as in Portarr and Mnemarr; every route of the API needs a session, and only an operator (or an administrator) approves. **Approving a card records a decision** (pull request, commit, steps, approver) in a queue and an audit trail, with a global stop, kept in memory or, with `Storage:Provider=Sqlite` (the image's default), in a file that survives a restart; the executor (below) takes the approvals in a dry run, so nothing real runs. The roadmap is in [docs/SPEC.md](docs/SPEC.md) §8; the founding vision in [docs/VISION.md](docs/VISION.md); how an order is secured, from the person to the machine, in [docs/security-model.md](docs/security-model.md).

**Executor.** The executor that takes the approved tasks is a .NET process per environment (`src/Orchestrarr.Executor`): every task is typed, approved with a second factor (an authenticator-app code) that the executor checks itself, and leaves a full trace that the interface shows ([ADR 0017](docs/adr/0017-orders-are-typed-tasks-approved-with-a-second-factor-that-the-executor-checks.md)). It runs in a **dry run** for now: it checks everything and starts nothing. **Decided, not built:** a decision is about one problem, in a table, validated with one code ([ADR 0019](docs/adr/0019-a-decision-is-a-problem-the-table-selects-and-one-code-validates.md)); applications are described in a private configuration repository ([ADR 0020](docs/adr/0020-applications-are-described-in-a-private-configuration-repository.md)); a separate qualification host precedes production ([ADR 0021](docs/adr/0021-qualification-on-a-separate-host-then-promotion-through-the-git-flow.md), proposed). Open before the first write power: who starts a workshop run (Q-28), how a required review is met (Q-14) and a merge on a repository that deploys itself (Q-29); see [docs/SPEC.md](docs/SPEC.md) §9.

Orchestrarr reads the findings of [Portarr](https://github.com/MafLabs38/portarr) (vulnerable dependencies, outdated images, broken applications), plans the work, delegates it to worker agents, verifies that nothing regressed, and proposes the result as a pull request for a human to approve. Safety and approval gates are core concerns: no direct push, sandboxed workers, least privilege, bounded budgets, full audit trail. It works with Mnemarr, the companion long-term memory.

## Releases

A release is a pull request `develop → main`, merged with a **merge commit** (`main` refuses squash: semantic-release reads the commits of the pull request, [ADR 0009](docs/adr/0009-releases-are-decided-by-semantic-release-from-main.md)). The pipeline then picks the version from the Conventional Commits (`feat` minor, `fix` patch, below 1.0 a breaking change is a minor), tags it, publishes the GitHub release and the image `ghcr.io/maflabs38/orchestrarr:<version>`. The title of every pull request into `develop` is a Conventional Commit and decides the version. The cluster's GitOps repository follows the newest version tag.

## Repository settings

The GitHub repository, its branches, rulesets and labels are declared as code in `repos/orchestrarr.yaml` of `MafLabs38/github-template`: change a setting with a pull request there, never in the GitHub settings. `ci.yml`, `codeql.yml`, `mutation.yml` and `ai-review.yml` (the five advisory review agents) are the pipeline (see [docs/TESTING.md](docs/TESTING.md)). CodeQL runs but does not gate merges: the ruleset waits for CodeQL results, so a skipped CodeQL would block every merge.

Before a push, check that no real infrastructure value slipped in (`gitleaks dir .`).

## Run in the sandbox

Needs the .NET 10 SDK and Node 22.

```bash
# API, with the sample data of samples/ (http://127.0.0.1:7878). The first start needs a first administrator (see below)
dotnet run --project src/Orchestrarr.Host

# Interface with hot reload (http://127.0.0.1:5178, on the loopback only), proxying /api to the API
cd frontend && yarn install && yarn dev

# Tests and lint (see docs/TESTING.md)
dotnet test --solution Orchestrarr.slnx && dotnet format Orchestrarr.slnx --verify-no-changes
cd frontend && yarn test && yarn lint && yarn stylelint && yarn format:check && yarn typecheck
```

**The first administrator.** An empty Orchestrarr has no account and nobody can sign in. The first start creates one, from a name and a **password file** (never a value in the environment): `printf '%s' 'a long password' > ~/admin-password && chmod 600 ~/admin-password`, then `Auth__AdminUser=root Auth__AdminPasswordFile=$HOME/admin-password dotnet run --project src/Orchestrarr.Host`. The administrator then creates the other accounts in the interface (System, Accounts): an `Operator` approves and engages the global stop, a `Reader` only reads. A password is at least 12 characters. In Development the cookie is not `Secure` (`Auth:CookieSecurity=SameAsRequest`), so a sandbox on a private network can be opened over plain HTTP: `dotnet run` listens on the loopback, and to open it from another machine, forward the port (`ssh -L 5178:127.0.0.1:5178 <host>`) rather than listening on every interface. If nobody can sign in any more, the break-glass settings `Auth__ResetPasswordUser` and `Auth__ResetPasswordFile` reset that account at the next start (remove them once used).


**Run the executor (a dry run: it checks everything and starts nothing).** `dotnet run --project src/Orchestrarr.Executor -- run`, configured with an `executor.json` or with environment variables, each starting with `ORCHESTRARR_`: `ORCHESTRARR_Executor__Name`, `ORCHESTRARR_Executor__ControlPlane__Url` (https, or a private network), `ORCHESTRARR_Executor__ControlPlane__Token` (or `...TokenFile`), `ORCHESTRARR_Executor__Rights__Kinds__0=ValidatePullRequest`, `ORCHESTRARR_Executor__Rights__Repositories__0=example/*` (an empty list refuses everything), `ORCHESTRARR_Executor__JournalPath` (the host's journal), `ORCHESTRARR_Executor__DataPath` (`executor.db`), `ORCHESTRARR_Executor__RequireSecondFactor` (true; `false` stops the executor from checking the code, accepted only while every runner is a dry run, as today, and the control plane's option cannot set it: both sides have to be relaxed to approve without a code), `ORCHESTRARR_Executor__LocalStopFile` (a file there stops the executor: it asks for nothing while the file exists and a run ends before its next task; default `STOP` in the folder of `executor.db`, so the local stop is never off; the global stop of the control plane is read when a batch is claimed, and reading it again between tasks comes with the first real runner) and `ORCHESTRARR_Executor__PollSeconds` (3). The token must be one of the host's `Tasks:Executors`. Enrol each operator in **your own terminal** (the secret is shown once, as a QR code, and never reaches the control plane): `dotnet run --project src/Orchestrarr.Executor -- enroll-operator --subject <account id>`, where the id is the `subject` of `GET /api/v1/auth/me` (shown on the Account screen). Other commands: `operators`, `delegations list|add|revoke` and `acts` (what the operators did on this executor: enrolments, replaced secrets, delegations given and revoked, in an append-only table; never a secret or a code). There is no executor image yet.

To read a real Portarr instead of the sample, set `Portarr:BaseUrl` and give the key as `Portarr:ApiKey` through the environment (`Portarr__ApiKey`) or `dotnet user-secrets`: the key never goes in a file that is committed. Redirects are not followed, so the key only goes to that address; use https or a private network.

To read the dependency pull requests, give a GitHub token that can **only read** as `GitHub:Token` (`GitHub__Token`, or `dotnet user-secrets`): a fine-grained token with *Pull requests: read*, *Checks: read* and *Commit statuses: read* on the repositories (without the last one, the checks of a repository that reports commit statuses stay unknown). Without a token the screens say the pull requests were not read. The token only goes to the configured API address, which must be https (redirects are not followed). The pull requests of the bots of `GitHub:BotLogins` are read (default: Dependabot and Renovate); a list in the configuration replaces the default. For a demo without GitHub, `Forge:SamplePullRequestsFile` reads a file of the shape of `samples/github-pull-requests.sample.json`.

### API

Under `/api/v1`. **Every route needs a session** (a `401` with no body without one, unknown routes included), except `POST /api/v1/auth/login` and `GET /health` (`{ "status": "ok" }`, for a probe); the files of the interface are public, since they say nothing about the fleet. Each route needs a permission of the person's role (a `403` without it): reading needs `fleet.read` (every role), the trail `audit.read`, approving `approvals.create` and the global stop `stop.control` (`Operator`, `Admin`), accounts `accounts.manage` and the options `options.manage` (`Admin`). **A write from a person carries the header `X-Orchestrarr-Request`** (any value: a page of another site cannot add it; the interface does), or it is a `403`. The routes of the executors are under `/api/v1/executor` and carry their own token, not a session. Every answer forbids being framed by another page and being sniffed, carries a policy that keeps the interface's scripts, styles and requests to itself (`Content-Security-Policy`); with `Auth:CookieSecurity=Always` (the default) it also carries `Strict-Transport-Security`. Nothing here runs anything:

| Route | Gives |
|---|---|
| `GET /api/v1/work-items[?refresh=true]` | The work items, with their findings, plan and pull requests |
| `GET /api/v1/work-items/{id}` | One work item (404 if unknown) |
| `GET /api/v1/system/status` | Name, version, the state of the sources (`source`, `forge`) and of approving (`approvals`: the identifier `operator` (the id of the account) and the name to show `operatorName`, `isOperator` (whether this person may approve and stop), `killSwitchEngaged`, `killSwitchSaved`, `requiresSecondFactor`: whether the interface asks for the code), where things are kept (`storage.kind`, `sqlite` or `memory`) and `executors` (each executor that asked for work: its name, version, kinds, repositories and delegations, as it reported them) |
| `GET /api/v1/options`, `PUT /api/v1/options/{id}` | The options (today `approvals.require-second-factor`): `value`, `canTurnOff`, and `lockedReason` (`host` or `configuration`). `PUT` needs `options.manage` and `{ "value", "password" }`; turning one off also needs the host started with `Options:AllowRelaxingSecurity` (`403 lockedByHost` otherwise), the password of the administrator (`400 passwordRequired`, `401 invalidCredentials`) and is traced as `option.changed`; turning on asks for nothing |
| `POST /api/v1/approvals` | Approves a card: `{ "workItemId", "steps", "pullRequests": [{ "number", "headSha" }], "secondFactorCode" }`, the pull requests and commits the card displayed. `secondFactorCode` is the six-digit code of the authenticator app: the control plane only checks its shape (`422` `secondFactorRequired`), the executor checks that it is right. The server decides the repository, the powers and the approver, and refuses unless what was displayed is what is there now |
| `GET /api/v1/approvals?limit=` | The approvals, newest first, each with its state (`waiting`, `taken`, `dryRunDone`, `refused`, `expired`), the batch it belongs to and when it ended: 200 by default, 1,000 at most; a `limit` outside 1 to 1,000 is brought back into that range, and if the file cannot be read the route answers `503` `storageUnavailable`, never an empty list |
| `GET /api/v1/audit?limit=` | The audit trail (the screen is called Activity; the route is not, because some content blockers refuse a request to a path called `activity`), newest first: 200 by default, 1,000 at most, with the same bound and the same `503`. The `id` of an entry is its number in the trail, counted from 1 in the order it was recorded: it never changes |
| `GET /api/v1/runs[?limit=]` | The runs of the executors, newest first: 100 by default, 500 at most; `503` `storageUnavailable` if the file cannot be read |
| `GET /api/v1/runs/{id}` | One run with its tasks and the hash-chained timeline of its trace (404 if unknown) |
| `GET /api/v1/auth/me` | Who is signed in: `{ subject, name, role, permissions }`; `subject` is the id of the account, which the approvals and the executor's second factor use. `401` when nobody is |
| `POST /api/v1/auth/login` | `{ "name", "password" }`: starts a session and sets the cookie (`HttpOnly`, `SameSite=Strict`, `Secure` with the `__Host-` prefix by default). `401` `invalidCredentials` for a wrong password and an unknown name alike; `429` `locked` (five failures in fifteen minutes lock the name, with `Retry-After`) or `busy`. No session needed (it still needs the `X-Orchestrarr-Request` header, like every write from a person) |
| `POST /api/v1/auth/logout` | Ends the session on the server, so a copied cookie is dead |
| `POST /api/v1/auth/password` | `{ "currentPassword", "newPassword" }`: changes one's own password and ends the other sessions of the account |
| `GET/POST /api/v1/accounts`, `PUT/DELETE /api/v1/accounts/{id}`, `POST /api/v1/accounts/{id}/password`, `GET /api/v1/roles` | The accounts and the roles, for an administrator. A change of a role or of the state applies at once; a disabled account loses its sessions; the last enabled administrator can be neither deleted, disabled nor demoted (`409` `conflict`) |
| `GET /api/v1/safety` | The global stop: `{ "killSwitchEngaged", "saved" }`; `saved` is false when it is engaged but the file could not take it (a restart would release it) |
| `PUT /api/v1/safety/kill-switch` | The global stop: `{ "engaged": true }`. Engaged, nothing is approved. Engaging always takes effect; a release is answered `503` `killSwitchUnavailable` when it cannot be saved, or `503` `auditUnavailable` when it cannot be written to the trail, and the stop stays engaged |

Approval answers: `201` recorded; `401` with no body when nobody is signed in; `403` for a role that cannot approve (no body), or `notAPerson`, `notAnOperator`; `404` `unknownWorkItem`; `409` `pullRequestsNotRead`, `planChanged`, `alreadyApproved`; `422` `tooManyPullRequests` (more than 100 pull requests on a card with both steps), `nothingTicked`, `stepNotOffered`, `stepNotGranted`, `stepNotSupported`, `mergeNeedsValidation`, `noPullRequests`, `secondFactorRequired`; `423` `killSwitchEngaged`; `429` `tooManyRequests` (see `Approvals:ApprovalsLimit`); `503` `storeFull`, `auditUnavailable`. A draft pull request is never approved. The global stop answers `401` without a session and `403` without the permission.

**Executor routes** (`POST /api/v1/executor/claim`, `/runs/{id}/events`, `/runs/{id}/complete`): `Authorization: Bearer <token>` of one of the `Tasks:Executors`, no session and no `X-Orchestrarr-Request` header. The token is checked before the body is read, which is capped at 256 KiB. The routes exist only when an executor is configured. Answers: `401` `notSignedIn` with `WWW-Authenticate: Bearer`, `400` `invalid` for a claim that does not say who the executor is, `409` `notYours`, `422` `invalid`, `503` `storageUnavailable`.

| `Portarr:BaseUrl`, `Portarr:ApiKey` | none | The Portarr to read. Without them nothing is read (the sample file is set only in Development) |
| `Portarr:TimeoutSeconds`, `Portarr:MaxResponseBytes` | 20, 10 MiB | Bounds on a Portarr call |
| `GitHub:Token` | none | Read-only token. Without it the pull requests are "not connected". This token stays read-only. When a write power exists, the executor will hold a GitHub App token of its own, limited to the task kind (ADR 0017); the control plane never holds it |
| `GitHub:BotLogins` | Dependabot and Renovate | Authors whose pull requests count as dependency updates |
| `GitHub:ApiUrl`, `GitHub:WebUrl` | github.com | For GitHub Enterprise |
| `GitHub:MaxPullRequests`, `GitHub:MaxPages` | 30, 5 | Bounds on a repository's list |
| `GitHub:CacheSeconds`, `GitHub:TimeoutSeconds`, `GitHub:MaxResponseBytes` | 300, 20, 5 MiB | Cache and bounds |
| `WorkItems:CacheDuration`, `MinRefreshInterval` | 30 s, 5 s | How long the list is kept, and the shortest gap between refreshes |
| `WorkItems:ForgeFirstWait`, `ForgeTimeBudget`, `ForgeParallelism` | 3 s, 60 s, 4 | How the forge is read in the background |
| `Powers:Grants` | none | What the operator grants: a list of `{ "Repository": "owner/name" or "*", "Steps": ["validate", "mergePullRequests"] }`. Off until listed. Checked at startup; outside Development a `*` grant may only cover `validate` |
| `Auth:AdminUser`, `Auth:AdminPasswordFile` | none | The first administrator, created at start **only when there is no account**; the password is read from the file (a secret mounted as a file, never an environment variable). Set together or not at all. Without an account and without them, nobody can sign in, and the log says so |
| `Auth:ResetPasswordUser`, `Auth:ResetPasswordFile` | none | Break-glass: while both are set, that account gets the password of the file, is enabled, and loses its lockout and its sessions, at **every start**. Remove them once used |
| `Auth:CookieSecurity` | `Always` | `Always`: the session cookie is `Secure` and named `__Host-orchestrarr.session` (https only). `SameAsRequest`: for a plain-HTTP sandbox on a private network (Development sets it) |
| `Auth:SessionHours`, `Auth:SessionMaxDays` | 12, 30 | How long a session lasts without use (1 to 720 hours), and at most (1 to 365 days). The server keeps the sessions: signing out, a new password, a disabled account and the end of the absolute lifetime end one for real |
| `Auth:KeysDirectory` | next to the database | A folder for the keys that protect the cookie, so that a new container still reads it (**a secret**: the keys sit there unencrypted). Unset with a SQLite file: a `keys` folder next to it; with the store in memory the keys stay in the container |
| `Storage:Provider`, `Storage:Path` | unset (see below), `data/orchestrarr.db` | Where the approvals, the audit trail and the global stop are kept. `Memory` forgets them at a restart (the sandbox); `Sqlite` keeps them in a file, created with its folder, and **an engaged global stop stays engaged** after a restart. A stop whose state cannot be read counts as engaged, and one that cannot be released for certain stays engaged. **Unset, it is `Memory` in Development, and the host refuses to start otherwise**, so that a restart never releases the stop by omission; the image sets `Sqlite`. **A database created outside Development starts with the stop engaged** (and a trace says so): release it once, deliberately. A file that cannot be used stops the host at its start. A relative path is read from the content root; the image sets `Sqlite` and `/config/orchestrarr.db`. The accounts and their sessions are in the same file; with the store in memory outside Development, the host logs a warning at its start (accounts, approvals, the trail and the stop are lost at every restart) |
| `Storage:MemoryStartsEngaged` | unset | With `Storage:Provider=Memory`: whether the stop starts engaged. Unset, it does outside Development (a store that forgets everything is a new store, and a new store starts engaged); `false` says otherwise |
| `Approvals:ApprovalsLimit`, `Approvals:ApprovalsWindowMinutes` | 30, 1 | How many times a person may try to approve in a window: more is a `429`, before anything is recorded or traced, so that a loop of refusals cannot fill the trail. The global stop is never limited. The same person refused for the same reason is traced once every ten minutes |
| `Approvals:QueueCapacity`, `Approvals:AuditCapacity` | In memory 500 and 2000; in a file 10,000 and 200,000 | How many approvals and trail entries are kept before refusing (the trail needs at least 2). A full trail refuses new approvals first, and keeps a twentieth of itself (at least one entry) to trace the global stop and its release |
| `Tasks:Executors` | none | The executor, as one `{ "Name", "Token" }` (one is supported for now; batches are not routed between several) (`Tasks__Executors__0__Name`, `Tasks__Executors__0__Token`): a secret of at least 32 characters (`openssl rand -hex 32`), a name of letters, digits and `. _ -`, unique. None: the executor routes do not exist |
| `Tasks:BatchLifetimeMinutes`, `Tasks:DeliveryTimeoutMinutes` | 2, 10 | How long an approval waits for an executor (1 to 1,440 minutes; the executor checks the code of the authenticator when it takes the batch, and a code is good for about a minute and a half, so a batch that waits longer expires and the operator approves again; the host ends the batches past their time every 15 seconds, whether or not an executor is connected and even while the global stop is engaged), and how long a batch may stay with an executor that does not answer (1 to 120) |
| `Tasks:RequireSecondFactor` | `true` | Approving needs the code. For tests only: the host refuses `false` in Production, and when it is `false` the screen of options cannot change the option |
| `Options:AllowRelaxingSecurity` | `false` | Lets an administrator turn off the authenticator code from the screen of options (with their password). Development and tests only: the host refuses to start with it in Production; without it the option is locked and the stored value is ignored (ADR 0023) |
| `Tasks:JournalPath` | `journal/approvals-journal.jsonl` next to the database | The append-only, hash-chained journal of the approvals that the executor compares with its batch (double control). With the store in memory and no path there is no journal, and the executor refuses every batch. The journal has a folder of its own so that the executor can be given that folder alone, read-only: never mount the database or the configuration folder into the executor, they hold the password hashes and the pending codes |
| `Fleet:SampleFile`, `Forge:SamplePullRequestsFile` | Development only | Sample data of `samples/`; a configured Portarr or token wins over them |

`dotnet run` runs as Development: it reads the sample data and grants validate and merge on every repository, so the Approve button works for an operator. The image runs as Production, where there is no grant and no sample data, the cookie is `Secure` (so serve it over https) and `appsettings.Development.json` is not carried; give it the first administrator (`-e Auth__AdminUser=root -e Auth__AdminPasswordFile=/run/secrets/admin-password`, a secret mounted as a file) and keep the cookie's keys in `/config` with the database. The file is the state of the product: keep `/config` on a local disk (not a network share), owned by the image's user (`$APP_UID`: with a bind mount or a volume claim, set the owner or `fsGroup`, otherwise the host stops at its start), run a **single replica** (the host takes a lock on `orchestrarr.db.lock` and a second host on the same file refuses to start) (a rollout that starts the new pod before stopping the old one is a second writer: use a `Recreate` strategy), and back it up with SQLite's online backup from a container that has the `sqlite3` tool and mounts the volume (`sqlite3 /config/orchestrarr.db ".backup /config/copy.db"`; the image does not ship it, and a copy of the file alone while the host runs can be torn). It holds the identifiers of people and their decisions, no credential. **When the queue (10,000 approvals) or the trail (200,000 entries) is full**, every approval is refused (`storeFull`, `auditUnavailable`) until you archive and start again: stop the host, take the online backup, move the file away and start the host, which creates a new database that **starts with the stop engaged**; release it once, deliberately. The retention policy itself is Q-24. It listens on port 8080 as a non-root user: `docker run -p 8080:8080 -v orchestrarr-config:/config -e Portarr__BaseUrl=... -e Portarr__ApiKey=... -e GitHub__Token=...`.

> **Security.** Every route of the API needs a sign-in, and there is no mode that trusts the network. The database holds the **password hashes** of the accounts (PBKDF2): it is a secret, and so is a backup of it. Serve the interface over https and keep `Auth:CookieSecurity=Always`; do not publish the port of an executor-facing route to the Internet (ADR 0017). Never start the image with `ASPNETCORE_ENVIRONMENT=Development`.
