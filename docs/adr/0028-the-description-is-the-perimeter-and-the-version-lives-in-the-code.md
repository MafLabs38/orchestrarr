# 0028 — The description is the perimeter, and the version lives in the code

- **Status**: proposed (asked for by the maintainer on 2026-11-12; accepted when the pull request that carries it is merged)
- **Date**: 2026-11-12
- **Spec**: D-78, D-79, D-80, D-81 (extends ADR 0020 and ADR 0027)

## Context

The audit of the table ([ADR 0027](0027-the-table-shows-what-can-be-decided-by-application-and-keeps-what-was-decided.md)) showed that a new version of an image is only half of the work: the version of an image is written somewhere in code (a manifest, a kustomization, a Terraform file, a compose file, a variable of an inventory), and a redeployment from that code brings the old version back. A row that says "bump this tag" is useless if nobody knows which file holds the tag. The code that holds the versions is spread over several repositories, some owned by the maintainer, some of which describe third-party software, and some of which are not on the forge at all.

The maintainer asked for the same state of mind as Portarr: **one YAML description says what is maintained, and the product works inside it, with no magic.** Extending the perimeter, or reducing it, is editing that file (by hand, through the MCP or through an editor, later). A repository the maintainer does not care about is not in the file, so it is never read.

## Decision

1. **The description is the only entry** (extends [ADR 0020](0020-applications-are-described-in-a-private-configuration-repository.md)). It is a YAML file (JSON is YAML, so the existing file still reads) named by `Description:File` (`Applications:File` is still read). It has three sections: `environments` (identifiers of Portarr, only the ones the perimeter refers to), `repositories`, and `applications` (as before, with a source that may be an object: `{ repository: … }` or `{ image: … }`, and `third-party` written either way). A mistake in it stops the start and says where.
2. **`repositories` is the perimeter of the code.** Each entry names a repository, the **kind** of files it holds (`kubernetes`, `kustomize`, `compose`, and `terraform-docker`), the **paths** (globs) that are read, and, when the repository deploys to one environment, that `environment`: a change is per environment, never one that bumps every environment at once. Orchestrarr reads no other code. The findings and the pull requests it lists still come from its sources and are not filtered by the description yet. A file whose **name** says that it holds a secret (`*.enc.*`, `*.tfstate*`, `*.tfvars*`, `.env*`, keys) is never read, whatever a path says; the content of a file is not searched for secrets, so the change that is shown is the one line, with nothing around it.
3. **Where a version is written is found by a deterministic reader, line by line, inside that perimeter**: an `image:` line, a `newTag`, a string given to a `docker_image`, a value of a variable file. No heuristic, no crawling, no model. A line that carries Flux's marker is Flux's, and Orchestrarr does not change it.
4. **A row about an image says where its version is written**: the file and the line, and what the guards found (an automation that rewrites the line, a pin by digest, several environments, a version that differs from what runs). It proposes no version: *the computed change of a version was removed on 2026-11-13 at the maintainer's request; how a version is changed is decided in ADR 0038 (proposed).*
5. **Nothing is written to a repository by this reading**, and a platform upgrade is not a tag change (§6). *(The endpoint that computed a diff, `GET /problems/change`, was removed on 2026-11-13.)*
6. **The platform and the operating systems are Portarr's to say, not read here.** Whether K3s or the operating system of a machine is behind, or out of support, is a fact about the fleet: Portarr reports it (the node information of the cluster, the release of each host, the public release lists), and Orchestrarr will read it as a finding, like every other. Orchestrarr does not compare a version of the platform with a public list itself (the rows that did so were removed, and with them the `platforms` section, the `variables` kind and the K3s channels reader): a platform upgrade is planned and done by a person, with the order, the snapshot and the way back, and is never offered by a tag change. Reading Portarr's platform findings is a later vertical, once Portarr reports them.
7. **The perimeter does not hide failures.** A repository of the description that cannot be read (not found, no access, a tree too large, files that could not be read, an answer that is not what the API documents) is shown on the table.
8. **The code is read in the background**, never inside a request for longer than a few seconds: a request that comes during a reading gets what was read last and the screens are told (the `problems` topic) when a new index is there; a refresh does not read again before a minute; a reading has a time budget. This adds nothing to the inventory of ADR 0002: Portarr still says what runs where, the description says what is maintained and in which code, and nothing of Portarr's data is copied (the identifiers of environments only point to Portarr's).

Amends nothing of [ADR 0002](0002-environment-description-is-a-provider.md): where each application runs stays Portarr's; the code that deploys it is policy (the maintainer's perimeter), not inventory.

## Consequences

- The maintainer decides, once and in one file, which repositories are maintained; a repository of a training course on a personal account is simply absent.
- The code is read with a token of its own (`GitHub:ContentsToken`, *Contents: read* on the repositories of the description only), so that the token of the pull requests does not widen to the code of the whole fleet; unset, `GitHub:Token` is used and must carry *Contents* too. A token reads repositories of an organisation and of a person. Without a token, each repository of the description is told as not readable ("no token to read it"), never as "written nowhere".
- A repository must be on the forge to be in the perimeter; two infrastructure repositories of the maintainer are still on the work machine only.
- Reading costs one tree request per repository and one request per changed file (a file already read is not read again while its identifier is the same), kept five minutes.
- The pull request that applies a change is the next vertical: it needs a Runner task, the second factor, and the write power of ADR 0001.
- Not done here, on purpose: the last version of the current line before a major (the registry's tags are not in the fleet model yet), operating system support, Helm values, Terraform provider versions.
- The default branch of a repository is what is read, not the branch that is deployed; the two are the same for a repository that deploys from its default branch, and a different branch is for a later setting.
