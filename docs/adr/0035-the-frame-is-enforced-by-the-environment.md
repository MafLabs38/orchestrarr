# 0035 — The frame is enforced by the environment, never by the agent's good will

- **Status**: proposed (the architecture was described to the maintainer on 2026-11-13 and the maintainer agreed with it in broad lines; accepted when the pull request that carries it is merged)
- **Date**: 2026-11-13
- **Spec**: D-88 ([FUNCTIONAL.md](../FUNCTIONAL.md), [ARCHITECTURE.md](../ARCHITECTURE.md))
- **Amended by**: [ADR 0055](0055-the-flow-is-a-fab-lots-routes-machines-and-rules-that-keep-it-moving.md): changing a pipeline is maintenance that an operation about the pipeline may do (a red pipeline, a pipeline tool, a base image), never in a way that weakens it (`PipelineChanges`); every other operation has the pipelines in its frame; [ADR 0057](0057-the-control-plane-justifies-the-powers-on-a-pipeline.md): the push credential of the free agent is made by the control plane for each mission and carries `workflows` only when the operation and its approved frame justify it.

## Context

An agent reads pull requests, changelogs and repositories, which can contain instructions. The maintainer wants the agent to be as free as a developer **inside a frame**, and the frame to hold even if the agent misbehaves.

## Decision

1. The agent **never touches**: the pipelines and the files that decide quality and release; any secret; data outside the mission; anything outside the perimeter. If a pipeline is itself broken it hands the maintainer a **patch or an issue** and **never pushes or merges it**.
2. The frame is enforced in layers, from the outside in: **the forge** (protection rules, code owners on pipeline and quality files, an agent identity that cannot merge a protected file, required checks), **credentials** (one repository, one world, short-lived, never a production secret in the agent's reach), **the mandate**, **the runner** (isolation, forbidden paths, network, a stop that kills the sandbox), **the act gateway**, **checks by code**, **the controller**, **the kill switch**, **the audit trail** (also written outside the host).
3. What the agent reads is **data and never an instruction**; nothing it reads can widen its frame, because the frame is not in its instructions.
4. The agent's identity on the forge is a **GitHub App limited per repository, without the `workflows` permission** (the forge refuses a push that touches a pipeline file) *(amended by ADR 0055, then by ADR 0057: on the test bed the free agent's push credential is made by the control plane for each mission and holds the `workflows` permission only when the operation is about its pipeline and its approved frame leaves the pipeline files open, so that the forge refuses every other push that touches a workflow; the control plane refuses a pipeline change that the operation is not about, or that weakens the pipeline, `PipelineChanges`)*, and it can only read and push to non-protected `orchestrarr/*` branches, **which a ruleset on every other branch enforces** (it refuses the creation, update, deletion and force-push of any other branch to the agent's identity: a fact the control plane checks, unknown counts as unconfined). **Opening a pull request and merging use a separate identity** held only by the **act gateway of the Git world**: a runner on a host apart from every agent sandbox, which verifies the mandate and the authority's certificate itself before every act and asks the control plane for the authorisation of the moment (the control plane's own forge credential stays read-only, D-63). Jobs on branches written by the agent run **without secrets** (secrets behind environments with a required reviewer). Its rulesets and code owners are written as code in the repositories' infrastructure code.
5. Requests to production from the release world go through an **egress proxy that allows safe methods only** and holds no production session; a verification that must write is a declared act.
6. A migration of a database requires a backup first and a way back; deleting data and handling a secret are never done by the agent alone; an exposed secret is removed from the code and told at once, the rotation is the maintainer's.
7. **The release is not a fixed rule (the maintainer, 2026-11-15).** Repositories differ: some have no CI (the update and the deployment are done by hand), some publish on merge, some are in GitOps (a merge is the deployment). The **worker agent judges the delivery mode of each repository** from its pipeline, reports it, and acts accordingly; the **controller reviews the probity** of what it did. What stays fixed is the frame, with **mechanical checks on facts the control plane fetches from the forge** (never from the agent), made at the crossing and again at the act, on the exact head commit: (a) a merge that **may deploy or use a write secret** (deploy, publish, push an image, sign), or is not known not to, is a release-world act, refused under an approval that stops before the release world; (b) where it may, a change that touches files the pipeline executes is **escalated to the maintainer**; (c) the agent must not be able to create tags and releases (a read-only default workflow token, no workflow on an agent branch raising permissions, rulesets that restrict creation to the release identity for every actor); (d) no job that runs on the agent's branch may obtain any write credential: no workflow of the base branch's context that runs what the agent pushed, no secret outside a reviewer-gated environment, no `id-token: write` on a workflow that the branch triggers (or a federation trust not pinned to protected refs or environments), no write scope of the default workflow token, and Actions may not approve pull requests. A merge is **known not to deploy only on a positive declaration** (the description in the perimeter, or Portarr); what is read on the forge can only raise the answer. Unknown counts as failing. FUNCTIONAL FR-WLD-11a carries the detail. Still open: the required checks that need tokens (analysis tokens limited to reading are acceptable on agent branches, deployment secrets are not), and the repositories that define the frame (outside the agent's perimeter).

## Consequences

- Negative cases in the laboratory (CASE-15, with its variants: the model token, a workflow that exfiltrates a CI secret, instructions for the controller in the dossier, a container reaching the host) test that the environment refuses, on every change to the runner or the rulesets.
