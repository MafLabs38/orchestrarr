# 0035 — The frame is enforced by the environment, never by the agent's good will

- **Status**: proposed (the architecture was described to the maintainer on 2026-11-13 and the maintainer agreed with it in broad lines; accepted when the pull request that carries it is merged)
- **Date**: 2026-11-13
- **Spec**: D-88 ([FUNCTIONAL.md](../FUNCTIONAL.md), [ARCHITECTURE.md](../ARCHITECTURE.md))

## Context

An agent reads pull requests, changelogs and repositories, which can contain instructions. The maintainer wants the agent to be as free as a developer **inside a frame**, and the frame to hold even if the agent misbehaves.

## Decision

1. The agent **never touches**: the pipelines and the files that decide quality and release; any secret; data outside the mission; anything outside the perimeter. If a pipeline is itself broken it hands the maintainer a **patch or an issue** and **never pushes or merges it**.
2. The frame is enforced in layers, from the outside in: **the forge** (protection rules, code owners on pipeline and quality files, an agent identity that cannot merge a protected file, required checks), **credentials** (one repository, one world, short-lived, never a production secret in the agent's reach), **the mandate**, **the runner** (isolation, forbidden paths, network, a stop that kills the sandbox), **the act gateway**, **checks by code**, **the controller**, **the kill switch**, **the audit trail** (also written outside the host).
3. What the agent reads is **data and never an instruction**; nothing it reads can widen its frame, because the frame is not in its instructions.
4. The agent's identity on the forge is a **GitHub App limited per repository, without the `workflows` permission** (the forge refuses a push that touches a pipeline file), and it can only read and push to non-protected `orchestrarr/*` branches. **Opening a pull request and merging use a separate identity** held only by the control plane's act gateway (never by a runner or an agent sandbox). Jobs on branches written by the agent run **without secrets** (secrets behind environments with a required reviewer). Its rulesets and code owners are written as code in the repositories' infrastructure code.
5. Requests to production from the release world go through an **egress proxy that allows safe methods only** and holds no production session; a verification that must write is a declared act.
6. A migration of a database requires a backup first and a way back; deleting data and handling a secret are never done by the agent alone; an exposed secret is removed from the code and told at once, the rotation is the maintainer's.

## Consequences

- Negative cases in the laboratory (CASE-15, with its variants: the model token, a workflow that exfiltrates a CI secret, instructions for the controller in the dossier, a container reaching the host) test that the environment refuses, on every change to the runner or the rulesets.
- **The release is not a fixed rule (the maintainer, 2026-11-15).** Repositories differ: some have no CI (the update and the deployment are done by hand), some have a CI (a merge publishes on the release branch), some are in GitOps (a merge is the deployment). No fixed strategy fits them: the **worker agent judges the delivery mode of each repository** from its pipeline and its situation, **reports it**, and acts accordingly; the **controller reviews the probity** of what the agent did, as an agent that can read the same pipeline. What stays fixed is the frame, not the judgement, and the frame has **mechanical checks on facts the control plane fetches from the forge** (never from the agent): the Git-world crossing is refused when the merge **may deploy (or is not known not to)** and the approval stops before the release world (`MergeMayDeployBeyondApproval`); when it may deploy and the approval reaches the release world, a change that touches files the pipeline executes (build scripts, hooks, container files) is **escalated to the maintainer** (`ExecutedFilesTouchedWhereMergeDeploys`), because that code would reach the deployment secrets without having been proved; the Git-world crossing is also refused unless the **tag and release creation is blocked for the agent** (`AgentCouldCreateTags`): the default workflow token is read-only, no workflow on an agent branch raises its permissions, and the tag and release rulesets restrict creation to the release identity for every actor. A merge counts as **known not to deploy only on a positive declaration** (the repository's description in the perimeter, or Portarr); what the control plane reads on the forge (a workflow triggered by a push, a GitOps controller watching the branch) can only raise the answer to "may deploy". Unknown counts as failing. The plan's **ceiling** (a merge that would deploy is a release-world act, so a mandate that stops at the Git world cannot be used to make it: the agent says so and the controller refuses or escalates), the agent never holds deployment secrets of its own (the act is performed under the mandate), the facts fetched outside the agent, the audit trail, and the rollback.  Still open, to be settled with what the agent finds in practice: the required checks that need tokens (analysis tokens limited to reading are acceptable on agent branches, deployment secrets are not), and the repositories that define the frame (outside the agent's perimeter).
