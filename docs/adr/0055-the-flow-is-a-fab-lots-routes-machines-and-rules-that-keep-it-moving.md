# 0055 — The flow is a fab: lots, routes and machines, and the rules that keep it moving

- **Status**: proposed (accepted when the pull request that carries it is merged)
- **Date**: 2026-11-25
- **Spec**: D-109 ([SPEC.md](../SPEC.md)). Builds on [ADR 0049](0049-problems-on-one-repository-are-done-one-at-a-time-and-a-conflict-is-not-mended-here.md) (a line per repository), [ADR 0050](0050-the-flow-has-a-priority-from-0-to-100-and-a-failed-release-goes-ahead.md) (priority) and [ADR 0053](0053-each-world-has-lanes-and-a-machine-is-never-idle-while-a-mission-waits.md) (lanes). It amends ADR 0049 on one point: a pull request that conflicts is no longer ended at once.

## Context

The maintainer's model (chat of 2026-11-25) is a clean-room fab. **Worlds are workshops**, each with a kind of machine (two staging machines, one deployment machine, the Git world with no machine); **a lot is a repository**, and each thing to do on it is an operation of the lot's route; the question is how to run every operation of every lot over the machines. He asked that a batch ticked **all at once** always runs to the end, whatever the order of the ticks, and that a **grain of sand** (an operation that cannot succeed) be put aside without stopping anything else.

The first full run of the demo showed that the flow did not hold that:

- the line of a repository took its problems **in the order they were validated**, so the five dependency alerts of a repository ran before the base image that their fixes need (a newer runtime), and were rightly escalated;
- a pull request made before another one was merged became **stale** (the lock file was rewritten): the product ended it, and the maintainer would have to tick it again. ADR 0049 left the rebase to "the bot", but nobody asked the bot to do it.

The way that problems are chosen, started and put aside is therefore the core of the product, and it is designed here from what the field has learned, not from our first intuition.

## What the field says (and what we take from it)

| Practice | Source | What we take |
|---|---|---|
| **Dispatching rules for a re-entrant flow**: priority first, then a secondary rule (FIFO, critical ratio, least work ahead); hot lots go first but disturb the normal ones; WIP-balancing and due-date rules can conflict | fab scheduling literature ([WSC 2005](https://www.informs-sim.org/wsc05papers/273.pdf), [dispatching and WIP rules](https://athene-forschung.unibw.de/doc/97064/97064.pdf), [FabTime on hot lots](https://inficon.com/media/11349/download/FabTimeNewsletter6.04.pdf)) | the order of a line is a **composed rule**: the rank in the route, then arrival; the priority (ADR 0050) orders the next mission a runner is given. A hot lot never interrupts a running operation |
| **Drum-buffer-rope**: the constraint paces the whole plant; keep a buffer in front of it so it never starves; a rope stops the release of more work than it can take | [Goldratt's Theory of Constraints, DBR](https://www.bdc.ca/en/articles-tools/operations/operational-efficiency/production-planning-drum-buffer-rope) | the **drum is the staging machines** (a proof is minutes, a restore follows). Their buffer is the problems that are planned and ready, so a machine never waits for work; the rope is that nothing is started upstream (a clone, an agent, a pull request) for a lot that has no machine to go to |
| **CONWIP / Kanban**: cap the work in progress; by Little's law, cycle time = WIP / throughput, so more WIP only makes everything slower | [CONWIP principles](https://is.muni.cz/el/econ/podzim2019/MPH_AOPR/CONWIP_principles_20141121.pdf?lang=en) | the caps we have stay: **one operation per lot**, one job per machine, `GitLanes` for the Git world |
| **Merge queues**: changes to one branch go one at a time; each is proved on top of the ones ahead of it; **a failing change is removed and the others go on without it**; queues are **per project**, because one shared queue blocks everything | [Zuul gating](https://zuul-ci.org/docs/zuul/9.4.0/gating.html), [GitHub merge queue](https://docs.github.com/en/enterprise-server@3.17/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue), [the Wikimedia lesson](https://phabricator.wikimedia.org/T94322) | one **line per lot** and never a global queue; an operation is proved on the base as it will be merged; a failure leaves the line and the next one goes. We do **not** do speculative merging (testing on top of the ones ahead that have not merged yet): one operation at a time on a lot makes it useless, and the cost is in the machines |
| **Dead-letter queue**: bounded retries, then the item is put aside **with its payload and error**, so that one poison item cannot hold up the rest; replay is a controlled act | [DLQ and poison messages](https://alivedise.github.io/backend-engineering-essentials/messaging/dead-letter-queues-and-poison-messages), [Temporal](https://temporal.io/blog/reliable-data-processing-queues-workflows) | an operation that cannot be solved is **put aside with its evidence** after bounded attempts (the three send-backs we have), the lot and the machines go on, and running it again is the maintainer's act |
| **Dependency bots rebase their own pull requests**, on a conflict or when behind; they stop when someone else pushes to the branch; they take a command or a label | [Dependabot comment commands](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-pull-request-comment-commands), [Renovate rebasing](https://docs.renovatebot.com/updating-rebasing/) | we **never rewrite a bot's branch**; we **ask the bot** to rebase (`@dependabot rebase`) |

## Decision

1. **The vocabulary is the fab's.** A **lot** is a repository (a work site). An **operation** is one problem on a lot. The **route** of a lot is the ordered list of its operations in the batch that was validated; each operation crosses the worlds (staging, Git, release) that its plan allows. A **machine** is a staging or a deployment machine; a **lane** is a place where one operation at a time is worked (ADR 0053). The screens and the documents say lot, operation and route where they say repository, problem and line today, once this is merged.
2. **The order of a route is a rule, not the order of the ticks.** The line of a lot, and the order in which a validated batch is planned and started, is: the **rank** of the operation, then arrival (the priority of ADR 0050 orders the next mission a runner is given, not the line). The rank is read from the kind and the nature of the row (ADR 0054), never from an agent's word, and puts first what **changes what the others run on**: (0) a **pipeline that is red** on the default branch (nothing of the lot merges while it is red); (1) the **runtime**: the base image of a container, which fixes the version of the language (a bot's pull request on the container ecosystem, `dependabot/docker/…` or the label `docker`, or an image row whose version is written in the `FROM` of a Dockerfile); (2) **security alerts** (their fixes need that runtime); (3) **updates of libraries and of pipeline tools** (a pull request of a bot); (4) the rest (a moving tag, an image that is behind and not a base). The maintainer ticks in any order; the route is the same.
3. **A lot is never held by what only an outside party can do.** A bot's pull request that is **behind its base or conflicting** when its turn comes (the bot's branch was made before an earlier operation was merged) is **parked**: Orchestrarr asks the bot to rebase it (a comment with the command written for that bot's account, `Missions:BotRebaseCommands`, an act of the control plane's gateway, `IForgeActs.RequestBotRebaseAsync`, that merges nothing and writes no branch; it is made **before a mission exists** (the problem is planned and not started, ADR 0049), so it is not an act of a mandate: it is gated by the validated plan entry, limited to the repositories the gateway may write on, and written in the audit trail as `problem.bot-rebase-requested`), and **the lot goes on with its next operation**. The parked operation **re-enters the route** when its bot made a new head on the base as it is now, and is proved again from the start (the head changed): the staging proof, the pipeline and the controller judge the new head. At most **two requests in one wait and four in all** (`Missions:BotRebaseRequests`, `Missions:BotRebaseRequestsInAll`) and a bounded wait (`Missions:BotRebaseWaitMinutes`, 30 by default): after that it is put aside with the reason *"the bot did not rebase"*. A bot that has no command is not waited for: its pull request is put aside at once. A pull request that its bot closed (another change already brought what it carried) is done by another operation, and its operation is closed. A pull request whose author is not a bot, or that someone other than its bot pushed to, is not followed: it is put aside with the reason, and the maintainer ticks it again on the commit it is at, as ADR 0049 said.
4. **An operation that cannot be solved is put aside, and the flow goes on.** After its bounded attempts (send-backs, the repair budget) or when the plan says it is complex, it ends *failed* or *escalated* **with its evidence and the reason in words**, frees its machine, and never blocks its lot or another one. Nothing retries it by itself; ticking the row again is the replay. This is the dead-letter rule, and it is **tested on purpose** (point 6).
5. **The caps stay what they are** (one operation per lot, one job per machine, the lanes of the Git world); nothing is started upstream for a lot that cannot be served. No global queue, no speculative merging.
6. **The definition of "it holds" is a test that anyone can run.** The demo ticked **all at once** must end with **every operation in a final state** (done, or put aside with its reason), none stuck, the staging machines both used at the same time, and **a grain of sand**: a problem of the real world that cannot be solved **by its nature, not by a rule of ours** (the maintainer, 2026-11-26: for example a security flaw in an image that has no newer version), placed **on an application that has several other operations**. On the test bed it is a **fabricated advisory** that the lab plants (`lab/`, `Missions:SandboxFindingsFile`): a critical flaw, embargoed, in an image for which no fixed version exists, so that no agent can refute it or mend it. The test passes when the grain of sand is put aside within its bounds and **all the other operations of that lot, and of the other lots, are done**.
7. **Every maintenance action is doable** (the maintainer, 2026-11-26). Changing a container file is maintenance, done by an agent as a developer would, and a repair may raise a companion dependency that a bump needs. A **pipeline** (a workflow, the version of a GitHub action, the runtime of the CI) is maintenance too, but it is also what judges a change (as built after the reviews of 2026-11-27), so:
   - only an operation **about the pipeline** may change it: a red pipeline (kind `FailingCi`), or a pull request that raises a tool of the pipeline or the base image (nature `PipelineToolUpdate` or `BaseImageUpdate`, ADR 0054); every other operation has the pipeline files in the frame of its missions (`PipelineChanges.ForbiddenFor`). The pipeline files are the list of `PipelineChanges.Paths`;
   - a change that may touch a pipeline never **weakens** it. It is refused when a line it adds (for a repair, which carries whole files: any line of the file) makes a step unable to fail (`continue-on-error: true`, `|| true`, `allow_failure: true`), switches a job off (`if: false`), widens a token (`write-all`, `<scope>: write`), runs with the base's credentials (`pull_request_target`, `workflow_run`) or reads a secret (`${{ secrets.`). A repair of a workflow that already does one of these is therefore refused, and the operation ends with the reason.

   **Dependencies come from a registry** (`DependencySources`): in a manifest (`package.json`, `requirements*.txt`, `pyproject.toml`, `Pipfile`, `setup.cfg`, `setup.py`, `go.mod`, `Cargo.toml`, `Gemfile`, `composer.json`, `*.csproj`, `Directory.Build.props`, `Directory.Packages.props`) or a container file, a change (the lines it adds) or a repair (the whole file) that fetches a dependency from an address, a git repository or a local path, uses another package index, or pipes a downloaded script into a shell (`curl … | sh`, `ADD https://…`) is refused. What stays out of a change is what is not maintenance: a secret, a file that instructs an agent, the review owners, the dependency bot's configuration, the settings of the package managers' registries and the repository's metadata; and a repair of a pull request still does not change the tests (and their configuration) that the pull request is judged on. A **red pipeline with no pull request** is a row that a free agent works on, ranked **first** in its lot (nothing of the lot merges while the pipeline is red), and repaired as a good developer does (`PipelineChanges.RepairRules`): a test that fails only some of the time is made deterministic, never retried until it passes; a check or a smoke test is never weakened to pass; a step that needs a secret that is not set runs only when the secret is there. **Maintenance stays in proportion** (learned from the grain of sand, 2026-11-26): a note, a mitigation that leaves the flaw or a risk said to be accepted is never the fix of a finding, and a rewrite of the application in another language, a change of its runtime or of its architecture, or the removal of what it does is never maintenance; both are the maintainer's decisions, and the controller escalates them however well they pass.

8. **A merge that turns the integration branch red is fixed forward** (the maintainer, 2026-11-26). The change is in: going back cannot un-merge it, and ending the operation would leave a red branch that holds every other operation of the lot. Whatever the controller judged, when the facts read on the forge say that the change is merged and that the pipeline of the merge commit **failed** (not pending, not unknown), the operation goes back to the staging world as an operation with no pull request: a free agent (ADR 0048) works on the integration branch as it is now and brings its pipeline back to green, the gateway carries that change into a pull request, and the Git world merges it with every pipeline green. Same approval, same bounds of the loop, no other validation; the operation goes ahead of the normal ones (a hot lot, ADR 0050), and its lot waits, because the operation is still in progress on it. This is the Git world's version of what ADR 0040 decided for a release. An application with no staging world stops the work with the reason. A fix forward is made **once** per operation: when the integration branch is red again after it, the operation is escalated to a person (*"the integration branch is red again after a fix forward"*), never sent to another agent.
9. **The pipeline is the project's, not the forge's services.** The forge runs jobs of its own on the commits of the default branch (GitHub runs Dependabot's updates and its dependency graph as workflows under `dynamic/dependabot/`); their failure says nothing about the commit (in the first full run, one failed because the forge could not pull an image of its own service), and they are left out of the verdict on a pipeline. The merge commit of point 8 is judged on the repository's own workflows only (the runs of `.github/workflows/` of the repository itself); a check that another app or the forge's own service reports on it is not the project's pipeline.

## As built

- **Who is a bot** is configuration: `Missions:BotAuthors` (the accounts that made the pull request: `dependabot[bot]`, `renovate[bot]`; the test bed adds the account of the lab, which plays one). Only those are asked to rebase (each with its own command, `Missions:BotRebaseCommands`: `@dependabot rebase` for `dependabot[bot]`; at most 100 characters, one line) and only those are followed to a new head; the author, and the account of every commit of the pull request, are the guard (a pull request of more than 99 commits is not followed), and the staging proof, the pipeline and the controller still judge the new head.
- **The facts are read on the forge when the turn comes**, not at the tick (`PullRequestFreshness`, pure): the head, the author, the account of each commit and whether every commit is signed with a signature the forge verified (the account is read from an e-mail that whoever writes the commit chooses; a signature is not, so a new head is followed only when it is signed, or when its bot is named in `Missions:BotUnsignedAuthors`, as a test bed names its lab bot; the setting is read on a test bed only). The forge's signing key is then the root of trust for following a head: a commit is the bot's when the forge verified it and it was committed by the bot or by the forge (`web-flow`); a bot that does not commit through the forge (a self-hosted Renovate) is never followed, its pull request is ticked again. The facts also say how far behind its base the pull request is, and its merge state. A forge that does not answer holds nothing: the staging proof refuses what moved, as before.
- **A parked problem does not hold its lot**: it is not "ahead" of a problem that arrives, and the next operation of the route takes the turn; it is read again every `Missions:BotRebaseRecheckSeconds` (30), the Missions screen says it waits for its bot. It is read only while its lot is free: when another operation of the lot held it, the clock of the bot did not run and the base moved, so the wait and the requests start again from that moment.
- **Planning is a pipeline**: the rows are taken in the order of the route, each plan is asked of the lead (`Agents:LeadMaxConcurrent` at a time) and each problem **starts as soon as its own plan is ready**; the plans of a lot are placed in the order of its route and the lots go side by side, so a plan that is slow to come holds its own lot only; the validation answers when the last one is placed. The selection limit `Agents:LeadMaxRows` is a guard of the subscription, not of the flow: the test bed sets it to 40.
- **Fixing forward** is a route of the conductor (`Route.FixForward`, on the failure `IntegrationBranchRedAfterMerge` that the conductor adds when the source reads the change as merged and the pipeline of the merge commit as failed): the Git mission ends, the plan entry of the problem loses its pull request and gets a staging instruction that names the merge commit, the host forgets the repair and the pull request it held for the problem (`IProblemRestarts`), and a staging mandate is issued under the same certificate.
- **A red pipeline names its pipelines**: before the lead plans a red pipeline, the control plane reads on the forge the last run of each workflow of the repository on its default branch, started by a push, by hand or on a schedule of the repository itself (a fork's run is someone else's text and is left out), and gives the lead the ones that did not pass (`IPipelineFailures`), as data; the first full run showed that "the build fails" alone made the agent repair a check that was not red and leave the red ones.
- **An alert names its packages**: the lead of a dependency alert is given the open alerts of the forge, one finding per package with the version that fixes all of them (Dependabot's alerts, `IDependencyFindings` of the GitHub provider; on the test bed what the lab planted for a repository comes first). Without them the lead told the worker to avoid a major version, and a flaw whose only fix is a major version stayed. They are read **from the forge, not from Portarr** (ADR 0002): Portarr gives counts per repository, and the lead needs the package and the version that fixes it; they are data for the plan, read when it is asked, never an inventory that Orchestrarr keeps (a field of Portarr's if a second product needs it).
- **The forge's own jobs** are told apart by their workflow run (`event=dynamic`, a path under `dynamic/dependabot/`), read only when a check that is not green could change the verdict; a list of runs that cannot be read leaves nothing out.
- **The lab's bot** is `lab/demo-bot.sh`: every half minute it makes again, on the base as it is now, the open pull requests of a scenario that are behind it (as Dependabot does after a merge); a hunk that the base already holds is dropped, as git does; and, as Dependabot does, it closes a pull request whose version the base already holds; the control plane then closes that operation as done by another one.
- **Fixing forward is made once**: the conductor looks for an earlier mission of the problem that ended to fix it forward; if there is one, the problem is escalated with the reason *"the integration branch is red again after a fix forward"*. Only the repository's own workflows of the merge commit judge it (`GitHubPullRequestFacts`, the check suites of `.github/workflows/` on the repository itself); the forge's own service runs (Dependabot's) are left out.
- **The pipelines and the dependencies are guarded by code**, read by the control plane that opens the pull request: `PipelineChanges` (which operations may touch a pipeline, and what weakens one) and `DependencySources` (a dependency from outside a registry), in `ChangePolicy` for a free agent's change (the lines it adds, the steps it removes and a restriction of the token it takes out: a `permissions` block, a `read` or `none` scope) and in `RepairPolicy` for a repair (the lines it adds to the file at the repaired head, read on the forge, and the steps it removes; a file that is new is judged whole; an existing pipeline that the forge could not read refuses the repair, since what it removes cannot be judged). The line-based rules are a net, not a proof: the controller reads the lines too. The restriction of an operation that is not about the pipelines is **signed in its certificate** (the approval request carries `PipelineChanges.ForbiddenFor`), so the verifier holds it, not only the conductor; the agents' instructions of the forge (`.github/copilot-instructions.md`, `.github/instructions/**`, `.github/prompts/**`, `.github/agents/**`, `.github/chatmodes/**`) and `.github/settings.yml` are in the floor. The pipelines left the floor of the frame (`ForbiddenPathsDefaults.Floor`): it keeps the review owners (`CODEOWNERS`, `docs/CODEOWNERS`, `.github/CODEOWNERS`), the dependency bot's configuration (`.github/dependabot.yml`, `.yaml`), `.gitmodules`, the encrypted files (`**/*.enc.*`) and the environment files (`**/.env*`).
- **A machine that went Down is qualified again by itself** (`MachineKeeper`): after `Missions:MachineRequalifyMinutes` (5), at most `Missions:MachineRequalifyPerHour` (3) times an hour, never while the global stop is engaged, and never when the check that failed is one of `Missions:MachineRequalifyNever` (`isolation` by default: an isolation that does not hold may mean that something ran on the machine that a person must look at first). It is the whole qualification (restore and every check), so it only puts back a machine that passes; each is in the audit trail (`machine.requalified`).

## What this does not do

- No speculative merging, no merge of several lots at once, no change that spans repositories (a problem is on one repository, ADR 0041).
- The rank is a **default for the test bed's kinds of operation**, not a dependency graph: two operations that need a different order (an upgrade of a runtime that breaks its libraries, which would need the libraries first) are tuned with the priority, until a real need asks for more.
- The bot is asked **by a comment on a pull request**: it is not known to work for every forge or every bot. A forge or a bot that has no such command puts the operation aside (point 3). Asking is a write on a pull request: it is gated by the validated plan entry and the repositories the gateway may write on, and the audit trail records it (`problem.bot-rebase-requested`); it opens no pull request and writes no branch.
- The measures that a fab watches (machine utilisation, the age of the oldest operation, cycle time per lot) are a screen of their own and are not part of this decision.

## Defaults taken, for the maintainer to veto

- The rank order above, and that the line uses it, not the priority.
- Two requests to the bot in one wait, four in all, and thirty minutes, as settings.
- A pull request that is behind its base **but not conflicting** is asked to be rebased too (a strict base wants an up-to-date head): a rebase costs a minute of pipeline, and the alternative is a merge that the forge refuses.

## Consequences

- A batch ticked in any order runs in the route's order, and the lock-file conflicts of a bot's pull requests no longer end an operation: they park it, the machines work on something else, and the operation comes back.
- The gateway gains one act (ask a bot to rebase), in the code of the forge acts and of the starter of problems, which are **launch contract files, merged by the maintainer** (rule 15).
- The lab gains a **bot that answers the command** for the pull requests that it plants, so that the demo behaves as a real repository does; real Dependabot pull requests answer by themselves.
- The grain of sand becomes part of the demo and of the scenario of the lab: a flow that has never met a failure on purpose has not been tried.
