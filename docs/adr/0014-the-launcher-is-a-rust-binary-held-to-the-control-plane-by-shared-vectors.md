# 0014 — The launcher is a Rust binary, held to the control plane by shared conformance vectors

- **Status**: accepted for the language and the vectors (the maintainer chose on 2026-11-04); proposed for how the launcher gets its orders (the safest default, to be changed if wanted)
- **Date**: 2026-11-04

## Context

[ADR 0006](0006-a-launch-is-a-signed-order-and-credentials-are-short-lived.md) and [ADR 0007](0007-a-dedicated-vault-and-a-small-control-plane.md) make the launcher a boundary of its own: first a module with an interface, then a separate process, then a separate host. They say it is "small and boring on purpose" and that it has no inbound port, but **they do not say in which language it is written**. Today it is C# library code in `Orchestrarr.Core` (`Launcher`, the order's canonical form, the refusal codes), tested and not run by any process.

Two facts weigh on the choice:

- **The launcher is the most sensitive component.** It holds the workload identity that Vault answers to (one per environment, [ADR 0012](0012-one-launcher-and-one-vault-role-per-environment.md)) and it is the only thing able to start an agent. What it carries is worth keeping small: no runtime, no shell, few dependencies.
- **The control plane is allowed to be heavy.** It is one central .NET container; the maintainer does not mind its weight. The launcher, one per environment, is the one that should be light. Portarr already made this trade for its machine-side probe (its ADR 0011: the reader, a Rust binary under 1 MB, in an image that holds nothing else), and Mnemarr's collector is also Rust.

Writing the launcher in a second language means **two implementations of the same security rule**: the canonical bytes that are signed, the checks and their order, the refusal codes. If they ever differ (a field written another way, a check moved, a clock tolerance applied to the other side), an order could pass in one and not in the other, or worse, mean something else. That is the real cost, and it is a security flaw if left to chance.

## Decision

1. **The launcher is a Rust binary**, in its own Cargo project (`launcher/`), built into its own image (a static binary built against musl, no shell, no dynamic library, no runtime). It opens no port. It is not a dependency of the host and the host is not a dependency of it. The footprint is a goal, not a number to defend: the reader's order of magnitude (about 1 MB, a few MB of memory) is the reference.
2. **The contract between the two implementations is the signed order, written down once, in a language-neutral form**, and held by **shared conformance vectors**: data files, in `contract/launch/`, that both implementations must satisfy. The contract is:
   - the canonical form (`orchestrarr-order-v2`);
   - the checks the launcher makes, **in order**, and the refusal code of each (`LaunchRefusal`);
   - the defaults of the options (lifetime ceiling, clock tolerance, age of the second factor);
   - **the grants and how they match**: the format of a grant and the rule that decides whether an order's steps, repository and environment are inside the grants (step × repository × environment, the wildcard, nothing granted means denied), because the launcher holds its own copy of the grants (point 7) and that matching is a safety rule like the others; the vectors carry grants and an order in, allowed or not out;
   - **what production is**: the launcher's own list of production environments, an environment it does not know being production, so that the check of the second factor is held by the vectors too. This is **an exception to D-17/ADR 0002 for the launcher only** (the control plane keeps classifying from the environment description): an independent authorization must not depend on what the control plane or Portarr says. When the two disagree (the card says "not production", the launcher says "production"), the launcher's answer wins and the step-up is refused late, with its code in the trail;
   - **which environments a launcher serves, and the audience**: both are **configuration of each launcher** (one per environment, ADR 0012). The audience has **no default**: the Rust launcher refuses to start without one, and **refuses to start with the literal `launcher`** or any value another environment's launcher uses. An order's environment **must be one the launcher serves**, otherwise it is refused as `WrongAudience`, and the environment wildcard of a grant ranges over the served environments only. An order with **no environment** (a merge only, which acts on a repository, not on an environment) is served only by a launcher configured to serve such orders; who runs them is SPEC Q-26. The vectors take the audience and the served environments as inputs and have a case for another launcher's audience, an environment not served and an order with none;
   - the signature scheme and the key's form;
   - the audit entries (event name, subject, detail) that a decision writes, and what an unverified order is never allowed to write;
   - what a decision spends: an order refused before the last check does not burn its id; an order that passed every check but the final read of the stop stays spent.
3. **The vectors are produced by the control plane's side, in C#, and committed.** Each vector is one case: the fields of the order and its options, **a script of the answers of the ports in the order they are called** (the stop read first, the verifier's answer or its failure, the ledger's answer, the stop read a second time, the audit sink's answer or refusal, and the time), next to the launcher's own configuration (its audience, its grants, its production environments), because the order of the checks and what each one spends cannot be expressed by a single snapshot of the world; the canonical bytes in hexadecimal, the signature, and the expected outcome (the refusal code, or accepted with the canonical bytes of the **normalized** order that is to be run, and the audit entries written, and whether the id was spent). There is a vector per refusal, one for the accepted order, a set for the grants, and the awkward ones: absence against the empty string, steps unsorted or repeated, times with fractions, a field that moves a boundary, a signature of another version, an order of another form, and the signatures that two libraries may judge differently: a malleated one (`S + L`), a small-order `R`, a small-order public key, a truncated or over-long signature, a malformed `vault:vN:` prefix.
4. **Both suites run all the vectors.** The **intended outcome of each case (its refusal code, whether its id is spent) is written by hand in the C# test that defines the case**; the generator produces only what follows from it (the bytes, the signature, the trail) and **fails, before it writes any file, if the C# launcher disagrees with the declared outcome**. Otherwise a check moved in C# would regenerate the files silently and the comparison would prove nothing. The .NET tests also regenerate the vectors and fail when the committed files differ (so a change to the form cannot go in without the files). The Rust tests read the same files and check that the Rust launcher gives the same outcome, byte for byte on the canonical form. **A change to the form, to the signature scheme, to a check or its order, to a refusal code, to the grants' matching or to a default is one pull request that changes the C# code, the Rust code and the vectors together**; a change of the wire form also changes the tag. The C# `Launcher` stays in Core as the executable reference and as the oracle of the vectors; it runs in no process.
5. **The signature scheme is asymmetric, and the vectors sign with Ed25519**, with a key pair made for the tests and published in the vectors, in the form Vault's transit engine gives (`vault:vN:` and the signature), under a key version that production never uses (`vault:v0:`). Ed25519 is deterministic (the same bytes and key give the same signature, so the files do not change on every run) and Vault's transit engine offers it. **Verification is strict in both implementations**: a non-canonical `S` (`S ≥ L`) is rejected, a small-order or non-canonical public key or `R` is rejected, and the cofactorless equation is used, so that the two libraries cannot disagree on a signature; the vectors above hold it. The production verifier (a public key, the key version bound) comes with the Vault adapter ([SPEC](../SPEC.md) Q-23). **The test key is test data**: the **private** key is in no build and no image; a release embeds the published **public** key, or its fingerprint, only as a deny-list. The launcher **refuses to start** when its configured public key is the published one, comparing the **decoded 32 raw bytes** (a re-encoded copy, in another text form, must not get past), and a release refuses any order whose key version is `vault:v0:`. The gitleaks allowance for the private key is added with the vectors and allows **the one value** (a fingerprint in `.gitleaksignore`), not the directory; the C# generator refuses to write a vector signed with any other key.
6. **What the vectors do not cover is deliberately left out of the contract**: the launcher's adapters (how it gets an order, how it talks to Vault, how it starts the workshop) are tested on their own, in Rust, with fakes. The vectors hold the pure decision: an order, a signature, the launcher's configuration and the answers of its ports, in; a decision and its trace, out.
7. **Where the launcher gets what its checks read** (proposed default). The launcher must stay an authorization **independent** of the one that had the order signed (ADR 0007 rule 2: whoever gives an order is authorized twice): if it took the granted powers and "is this production" from the same API that had Vault sign the order, a compromised control plane could sign any order *and* tell the launcher it is allowed. So, of the ports of the C# `Launcher`:
   - **the order**: pulled through the control plane's API, which is the only reader of the store (the file of [ADR 0013](0013-approvals-the-trail-and-the-stop-are-kept-in-a-sqlite-file.md) is a single-replica local store: the launcher never opens it). The launcher polls, it opens no port (SPEC D-46);
   - **the granted powers and the environment classifier**: the **launcher's own configuration**, per environment and delivered through the infrastructure repositories, never asked of the API. This **reverses on purpose** what Core does today (`PolicyGrantedPowers` reads the same grants as the decision card, "one source"): an independent authorization is worth more than one source. The cost is that the operator grants a power that acts in **two places**, the control plane (what a card offers) and the launcher (what runs), and the effective power is the intersection: a card can offer a step that the launcher refuses with `OutsideGrantedPowers`, and the trail says so (SPEC D-10, D-60). The matching of grants is held by the vectors (point 2), so the two implementations do not hold two opinions on it;
   - **the nonce ledger**: **local to the launcher**, on a small volume it alone writes (an exclusive lock on the volume, like the control plane's file), so that replay protection does not depend on the API; the volume carries over from the dry run to the real run, and recreating it is safe because of the creation-time rule below. **It fails closed**: an unreadable ledger refuses every order; a ledger that is **new** (a recreated volume, a restore) writes its creation time in itself, traces it, and refuses every order issued before that time plus the clock tolerance, since such an order may have been spent in the ledger that was lost; two launchers on one volume cannot both start. The dry run spends ids exactly as a real run would, so the vectors are the same;
   - **the global stop**: read from the control plane (it is its state), **unknown means engaged**, plus a local stop an operator can set on the launcher's own machine (proposed, an addition to D-43 and F-SAF-01). The consequence is deliberate: **every launch depends on the control plane being reachable**, so an outage of the central container stops every environment, which is what D-43 asks of a product that fails closed;
   - **the audit sink**: written through the API, which is where the trail lives; if the launcher cannot record, it accepts nothing (D-43). The route it writes to accepts a machine identity, never the approval, release or stop routes, and takes **two kinds of entry only**: a decision tied to an order that exists (waiting, or already decided by this launcher), and an **untrusted refusal** with no order id and the fixed subject `unverified`, which the launcher writes when the stop, the verifier, the signature or the shape of the order refuses it before anything can be trusted (the reference implementation writes exactly these), and which never changes the state of an approval. Untrusted refusals are **deduplicated** per launcher identity and refusal code, one entry per window with a counter (as ADR 0013 does for a person's repeated refusals), so that a launcher stuck on garbage cannot fill the trail that approvals depend on. The route accepts only the event names of the contract, fixes the size of the detail and checks it against the audit entry of the vectors, and limits the rate per order and per launcher identity, so that a compromised launcher identity cannot flood the bounded trail (ADR 0013) or inject text into what the screens and the logs show.

   How the launcher authenticates to the API is open (SPEC Q-25).
8. **The first slice that runs the Rust launcher is a dry run**: it pulls, verifies, writes to the audit trail what it would have started, and starts nothing; it holds no credential to Vault, no access to a forge and no container runtime. It proves the chain (the order, the signature, the checks, the pull, the trace) before any power exists. **It needs Q-25 settled first**: the audit route is the first route used by a machine, and it must not share the authorization of the routes for people.

## Alternatives considered

| Alternative | Why not |
|---|---|
| The launcher in C#, in its own project that references only Core | Simplest, the verifier is written once, but a .NET runtime in the most sensitive component, in an image far larger than needed. The maintainer prefers the small surface. Remains the fallback if the vectors prove too heavy to keep |
| Rust, with a verifier written independently and no shared files | Two opinions on the same bytes: a divergence is a security flaw nobody sees until it matters. Rejected |
| One Rust verifier called from the control plane through a native interface (FFI) | Only one implementation, but it puts a native build and an unsafe boundary in the central container and in every test of the control plane, for a function that signs on the other side and builds the bytes in C# anyway |
| A schema compiled to both languages (Protobuf and the like) | It shares the shape of the data, not the checks or their order; the order of the checks and what a decision spends are the risky part |

## Consequences

- The repository gains a second language: a Cargo project, a CI lane (`rustfmt`, `clippy` as errors, the tests, an audit of the dependencies), Dependabot entries, an image and its scan. Portarr's reader is the model to copy; [TESTING.md](../TESTING.md) says what runs where.
- The vectors are the reviewable form of the safety rule: a person (or an agent) can read the cases, with no need to read either implementation. A new refusal is a new vector.
- The C# `Launcher` and the Rust launcher are checked against each other through the files, not by one calling the other; either can be rewritten without the other as long as the files agree.
- The supply chain of the binary that holds the workload identity is pinned: `Cargo.lock` committed, `cargo build --locked`, `cargo deny` (advisories, licences, sources limited to crates.io), the builder and base images pinned by digest, the CI actions pinned by SHA.
- Arrives with the vectors: the gitleaks allowance for the published test key (one value), the test that both suites read the same set of vector files (a file nobody loads fails), and the test that Core's `Launcher` is registered by no host.
- The Cargo lane is a **required check** of the repository once the launcher exists (`required_checks` of the repository's file in `github-template`), so that a change to the rules cannot merge with the Rust side red.
- Core's `Launcher` ships in the production assembly and is registered by no host today.
- The shared `"launcher"` audience default of the C# options goes away with row 3a, when the issuer learns to address an order to the launcher of its environment (a map from environment to audience).
- The format of the vector files (one file per case, JSON, a version field) is fixed when they are written, in `contract/launch/README.md`.
- The first slice depends on the lifecycle of an approval (ADR 0013), so that "an order that exists and is waiting" is something the audit route can check; the repository's settings (`github-template`) gain the Rust lane as a required check when it lands.
- The launcher stops being a few hundred lines once it carries an HTTP client, JSON and Ed25519; the bound is the handful of crates, listed in the pull request that writes it.
- Mutation testing of the Rust launcher is not decided here (the .NET lane uses Stryker); it follows when the launcher exists.
- The vertical that validates and merges is split: the launcher and the vectors first (SPEC roadmap row 3a), the merge after (row 3b).

## Not decided here

- When the order is signed relative to the approval, and what happens when a production step-up has gone stale or the order has expired before the launcher pulls it (the issuer's trigger and the re-issue): settled with row 3a, with the open question of [the security model](../security-model.md) on the refresh of the operator's session.
- Who runs an order with no environment, a merge only (SPEC Q-26).

- How the launcher authenticates to the control plane's API, and the control plane to the launcher (SPEC Q-25): a token of the launcher's workload identity, mutual TLS, or the identity provider's service accounts.
- The Rust crates beyond the standard library (the signature check, the HTTP client, the JSON of the vectors): chosen when the launcher is written, kept to a handful and listed in the pull request.
- Whether the launcher runs in the production cluster or on the workshop host (ADR 0012 only says one per environment).

See also [How an order is secured, from the person to the machine](../security-model.md).
