# 0014 — The launcher is a Rust binary, held to the control plane by shared conformance vectors

- **Status**: accepted for the language and the vectors (the maintainer chose on 2026-11-04); proposed for how the launcher gets its orders (the safest default, to be changed if wanted)
- **Date**: 2026-11-04

## Context

[ADR 0006](0006-a-launch-is-a-signed-order-and-credentials-are-short-lived.md) and [ADR 0007](0007-a-dedicated-vault-and-a-small-control-plane.md) make the launcher a boundary of its own: first a module with an interface, then a separate process, then a separate host. They say it is "small and boring on purpose" and that it has no inbound port, but **they do not say in which language it is written**. Today it is C# library code in `Orchestrarr.Core` (`Launcher`, the order's canonical form, the refusal codes), tested and not run by any process.

Two facts weigh on the choice:

- **The launcher is the most sensitive component.** It holds the workload identity that Vault answers to (one per environment, [ADR 0012](0012-one-launcher-and-one-vault-role-per-environment.md)) and it is the only thing able to start an agent. What it carries is worth keeping small: no runtime, no shell, few dependencies.
- **The control plane is allowed to be heavy.** It is one central .NET container; the maintainer does not mind its weight. The launcher, one per environment, is the one that should be light. Portarr already made this trade for its machine-side probe (its ADR 0011: the reader, a Rust binary under 1 MB, in an image that holds nothing else), and Mnemarr's collector is also Rust.

Writing the launcher in a second language means **two implementations of the same security rule**: the canonical bytes that are signed, the checks and their order, the refusal codes. If they ever differ (a field written another way, a check moved, a clock tolerance applied to the other side), an order could pass in one and not in the other, or worse, mean something else. That is the real cost, and it is a security flaw if left to chance.

## Decision

1. **The launcher is a Rust binary**, in its own Cargo project (`launcher/`), built into its own image (a static binary built against musl, no shell, no dynamic library, no runtime). It opens no port, and it keeps **no state on disk**. It is not a dependency of the host and the host is not a dependency of it. The footprint is a goal, not a number to defend: the reader's order of magnitude (about 1 MB, a few MB of memory) is the reference.
2. **The contract between the two implementations is the signed order, written down once, in a language-neutral form**, and held by **shared conformance vectors**: data files, in `contract/launch/`, that both implementations must satisfy. The contract is:
   - the canonical form (`orchestrarr-order-v2`) and the signature scheme (point 5);
   - the checks the launcher makes, **in order**, with the refusal code of each (`LaunchRefusal`), including the four that Core does not have yet (point 7: the quiet period at start, the clock not known to be synchronized, an order issued before the start; point 6: the environments a launcher serves);
   - the defaults of the options: lifetime ceiling, clock tolerance, age of the second factor;
   - **the grants and how they match**: the format of a grant and the rule that decides whether an order's steps, repository and environment are inside the grants (step × repository × environment, the wildcard, nothing granted means denied);
   - **what production is**: the launcher's own list of production environments, an environment it does not know being production;
   - **the audience and the served environments**: configuration of each launcher, with the rules of point 6;
   - the audit entries (event name, subject, detail) that a decision writes, and what an unverified order is never allowed to write;
   - what a decision spends: an order refused before the last check does not burn its id; an order that passed every check but the final read of the stop stays spent.
3. **Two kinds of vectors, produced by the control plane's side, in C#, and committed.**
   - **Decision vectors.** One case: the fields of the order, the launcher's configuration (audience, served environments, grants, production environments, options), **a script of the answers of the ports in the order they are called** (the time since the start, the stop read first, the verifier's answer or its failure, the ledger's answer, the stop read a second time, the audit sink's answer or refusal, and the time), because the order of the checks and what each one spends cannot be expressed by a single snapshot of the world; and the expected outcome: the refusal code, or accepted with the canonical bytes of the **normalized** order that is to be run, the audit entries written, and whether the id was spent. There is one vector per refusal (a test fails when a refusal code has none), one for the accepted order, a set for the grants, and the awkward ones: absence against the empty string, steps unsorted or repeated, times with fractions, a field that moves a boundary, an order of another form, an environment not served, an order with none.
   - **Signature vectors.** The verifier is a port in the decision vectors, so they cannot test a signature. These run against the **real** verifier of each side: a public key, bytes and a signature in; valid or not out. They hold the cases that two libraries may judge differently: a malleated signature (`S + L`), a small-order `R`, a small-order public key, a non-canonical encoding, a truncated or over-long signature, a malformed `vault:vN:` prefix, a signature of another version.
4. **Both suites run all the vectors.** The **intended outcome of each case (its refusal code, whether its id is spent) is written by hand in the C# test that defines the case**; the generator produces only what follows from it (the bytes, the signature, the trail) and **fails, before it writes any file, if the C# launcher disagrees with the declared outcome**. Otherwise a check moved in C# would regenerate the files silently and the comparison would prove nothing. The files are written deterministically (sorted keys, LF line endings, invariant culture: the same bytes on Linux and on Windows), and the .NET tests regenerate them and fail when the committed ones differ. The Rust tests read the same files and check that the Rust launcher gives the same outcome, byte for byte on the canonical form, and each suite fails on a file it did not read. **A change to the form, to the signature scheme, to a check or its order, to a refusal code, to the grants' matching or to a default is one pull request that changes the C# code, the Rust code and the vectors together**; a change of the wire form also changes the tag. The C# `Launcher` stays in Core as the executable reference and as the oracle of the vectors; it runs in no process.
5. **The signature scheme is asymmetric; the vectors sign with Ed25519**, with a key pair made for the tests and published in the vectors, in the form Vault's transit engine gives (`vault:vN:` and the signature), under a key version that production never uses (`vault:v0:`). Ed25519 is deterministic (the files do not change on every run) and Vault's transit engine offers it; another asymmetric scheme would be a change of the scheme, hence one pull request (point 4). **Verification is strict in both implementations**: a non-canonical `S` (`S ≥ L`) is rejected, a small-order or non-canonical public key or `R` is rejected, and the cofactorless equation is used; the signature vectors hold it. The Rust crate and its strict mode, and the C# Ed25519 library (the generator signs with it, the oracle verifies with it), are chosen with row 3a. The production verifier (a public key, the key version bound) comes with the Vault adapter ([SPEC](../SPEC.md) Q-23).
   - **The test key is test data.** The **private** key lives only in the test data of `contract/launch/`, and no build or image includes that directory; a release embeds the published **public** key, or its fingerprint, only as a deny-list. The launcher **refuses to start** when its configured public key is the published one, comparing the **decoded 32 raw bytes**, and a release refuses any order whose key version is `vault:v0:`.
   - The gitleaks allowance for the private key is added with the vectors and allows **the one value** (a fingerprint in `.gitleaksignore`), not the directory; the C# generator refuses to write a vector signed with any other key.
6. **The audience and the served environments are configuration of each launcher** (one per environment, ADR 0012).
   - The audience has **no default**: the Rust launcher refuses to start without one, with the literal `launcher` (the shared default of the C# options, which goes away with row 3a) or with a deny-listed test value.
   - That two launchers do not share an audience cannot be checked by a launcher, which knows only its own configuration: it is checked where every audience is visible, in the issuer's map from environment to audience (the host refuses to start with a duplicate) and in the infrastructure repository that delivers the launchers' configuration.
   - An order's environment **must be one the launcher serves**, otherwise it is refused as `WrongAudience`, by a check that runs right after the audience check; the environment wildcard of a grant ranges over the served environments only.
   - An order with **no environment** (a merge only, which acts on a repository, not on an environment) is served only by a launcher configured to serve such orders; who runs them is SPEC Q-26.
7. **Where the launcher gets what its checks read** (proposed default: every bullet below is part of the proposal, none is decided yet). The launcher must stay an authorization **independent** of the one that had the order signed (ADR 0007 rule 2: whoever gives an order is authorized twice): if it took the granted powers and "is this production" from the same API that had Vault sign the order, a compromised control plane could sign any order *and* tell the launcher it is allowed. So, of the ports of the C# `Launcher`:
   - **the order**: pulled through the control plane's API, which is the only reader of the store (the file of [ADR 0013](0013-approvals-the-trail-and-the-stop-are-kept-in-a-sqlite-file.md) is a single-replica local store: the launcher never opens it). The launcher polls, it opens no port (SPEC D-46). The API hands an order to **one** launcher identity, **once**, as a **lease**: the delivery is recorded with the approval lifecycle (ADR 0013), a delivered order that the launcher has not decided by the order's own expiry goes back to a state where it is issued again, and a second instance of the same launcher gets nothing. The launcher **does not pull** while it is in its quiet period, while its clock is not known to be synchronized, or while the stop (central or local) is engaged, so that it does not use up deliveries it cannot accept. It is deployed as a singleton (replaced, never rolled). This is a guard of the API, in addition to the launcher's own, not independent of it;
   - **the granted powers and the environment classifier**: the **launcher's own configuration**, delivered through the infrastructure repositories, never asked of the API. This **reverses on purpose** what Core does today (`PolicyGrantedPowers` reads the same grants as the decision card, "one source"): an independent authorization is worth more than one source. The cost is that the operator grants a power that acts in **two places**, the control plane (what a card offers) and the launcher (what runs), and the effective power is the intersection: a card can offer a step that the launcher refuses with `OutsideGrantedPowers`, and the trail says so (SPEC D-10, D-60). Likewise for production: the control plane keeps classifying from the environment description (D-17), the launcher from its own list (an exception to D-17 for the launcher only), and when they disagree the launcher's answer wins and the step-up is refused late, with its code in the trail. The matching of grants is held by the vectors (point 2). **The launcher's configuration (and the issuer's map from environment to audience) lives in a repository that Orchestrarr holds no grant on** (the check of D-53 refuses a grant on it) **and changes only by a person's review**: otherwise an order to merge a change of those grants, signed by a compromised control plane, would widen the launcher's powers and the independence would be only apparent (SPEC Q-10);
   - **the nonce ledger and time**: the ledger is **in the launcher's memory**, so that replay protection does not depend on the API and nothing is kept on disk. Three things make that sound, all from the launcher's **own** configuration, never from an order or the API:
     - **a quiet period at every start**: the launcher accepts nothing for its own `MaxLifetime + ClockSkew`, measured on its monotonic time (an untrusted refusal, checked right after the stop). An order spent before a restart expires before the quiet period ends, so a restart, a recreated volume, a restored snapshot or a copied deployment that starts later cannot make it run again. A restart delays the acceptance of orders by about ten minutes with the default options;
     - **an issue-time floor**: the launcher keeps the wall-clock time of its start and refuses, as `IssuedBeforeStart` (a new check, after the signature), any order issued before it minus the clock tolerance, so that a wall clock stepped backwards after the start cannot make an expired order look valid again;
     - **a clock that is known to be right**: the launcher accepts nothing until its host reports the clock as synchronized (unknown means refused). A clock wrong **at** the start is outside the guarantee otherwise, and it is a requirement of the deployment, not something the launcher can prove.
     The dry run spends ids exactly as a real run would. The vectors script the time since the start and the wall clock, and have the boundary cases (an order at the end of the quiet period, an order issued just before the start);
   - **the global stop**: read from the control plane (it is its state), **unknown means engaged**, plus a local stop an operator can set on the launcher's own machine (proposed, an addition to D-43 and F-SAF-01). The consequence is deliberate: **every launch depends on the control plane being reachable**, so an outage of the central container stops every environment, which is what D-43 asks of a product that fails closed;
   - **the audit sink**: written through the API, which is where the trail lives; if the launcher cannot record, it accepts nothing (D-43). The route it writes to accepts a machine identity, never the approval, release or stop routes, and takes **two kinds of entry only**: a decision tied to an order that exists (waiting, or already decided by this launcher), and an **untrusted refusal** with no order id and the fixed subject `unverified`, written when the stop, the quiet period, the verifier, the signature or the shape of the order refuses it before anything can be trusted (the reference implementation writes exactly these), which never changes the state of an approval. The route accepts only the event names of the contract, fixes the size of the detail and checks it against the audit entry of the vectors, limits the rate per order and per launcher identity (which needs an identity that is stable per launcher and distinct per environment: a requirement on the answer to Q-25), and **deduplicates** untrusted refusals per launcher identity and refusal code, one entry per window with a counter (as ADR 0013 does for a person's repeated refusals), so that a compromised identity or a launcher stuck on garbage cannot fill the trail that approvals depend on.

   How the launcher authenticates to the API is open (SPEC Q-25).
8. **The first slice that runs the Rust launcher is a dry run**: it pulls, verifies, writes to the audit trail what it would have started, and starts nothing; it holds no credential to Vault, no access to a forge and no container runtime. It proves the chain (the order, the signature, the checks, the pull, the trace) before any power exists. **A dry run takes the approval exactly as a real run would**: the trail names it with an event of its own (`launch.dry-run`), the approval ends in a terminal state flagged as a dry run that a real launcher never takes, and the operator approves again for a real run. **It needs Q-25 settled first**: the audit route is the first route used by a machine, and it must not share the authorization of the routes for people.

## Alternatives considered

| Alternative | Why not |
|---|---|
| The launcher in C#, in its own project that references only Core | Simplest, the verifier is written once, but a .NET runtime in the most sensitive component, in an image far larger than needed. The maintainer prefers the small surface. Remains the fallback if the vectors prove too heavy to keep |
| Rust, with a verifier written independently and no shared files | Two opinions on the same bytes: a divergence is a security flaw nobody sees until it matters. Rejected |
| One Rust verifier called from the control plane through a native interface (FFI) | Only one implementation, but it puts a native build and an unsafe boundary in the central container and in every test of the control plane, for a function that signs on the other side and builds the bytes in C# anyway |
| A schema compiled to both languages (Protobuf and the like) | It shares the shape of the data, not the checks or their order; the order of the checks and what a decision spends are the risky part |

## Consequences

- The repository gains a second language: a Cargo project, a CI lane (`rustfmt`, `clippy` as errors, the tests, an audit of the dependencies), Dependabot entries, an image and its scan. Portarr's reader is the model to copy; [TESTING.md](../TESTING.md) says what runs where. The Cargo lane is a **required check** of the repository once the launcher exists (`required_checks` of the repository's file in `github-template`), so that a change to the rules cannot merge with the Rust side red.
- The supply chain of the binary that holds the workload identity is pinned: `Cargo.lock` committed, `cargo build --locked`, `cargo deny` (advisories, licences, sources limited to crates.io), the builder and base images pinned by digest, the CI actions pinned by SHA.
- The vectors are the reviewable form of the safety rule: a person (or an agent) can read the cases, with no need to read either implementation. A new refusal is a new vector.
- The C# `Launcher` and the Rust launcher are checked against each other through the files, not by one calling the other; either can be rewritten without the other as long as the files agree.
- Row 3a changes Core before any vector is generated: the quiet period, the clock check, the issue-time floor and the served environments are added to `Launcher` and `LauncherOptions` (no default audience), the issuer addresses an order to the launcher of its environment (a map from environment to audience, which retires the shared `"launcher"` default), and the lifecycle of an approval (ADR 0013) gives "an order that exists and is waiting" a meaning.
- Arrives with the vectors, and is tested then: the gitleaks allowance for the published test key (one value); that both suites read the same set of files; that every refusal code has a vector; that Core's `Launcher` is registered by no host and referenced by no host project; that the dry-run launcher's composition has no adapter to Vault, a forge or a container runtime, and writes its "would have started" entry exactly once per order.
- The format of the vector files (one file per case, JSON, a version field, decision and signature vectors apart) is fixed when they are written, in `contract/launch/README.md`.
- The launcher stops being a few hundred lines once it carries an HTTP client, JSON and Ed25519; the bound is the handful of crates, listed in the pull request that writes it.
- Mutation testing of the Rust launcher is not decided here (the .NET lane uses Stryker); it follows when the launcher exists.
- The vertical that validates and merges is split: the launcher and the vectors first (SPEC roadmap row 3a), the merge after (row 3b).
- An operator-facing cost, to be shown one day: a power granted in the control plane and not on the launcher (a card that offers a step that will be refused).

## Not decided here

- When the order is signed relative to the approval, and what happens when a production step-up has gone stale or the order has expired before the launcher pulls it (the issuer's trigger and the re-issue): settled with row 3a, with the open question of [the security model](../security-model.md) on the refresh of the operator's session.
- Who runs an order with no environment, a merge only (SPEC Q-26).
- How the launcher authenticates to the control plane's API, and the control plane to the launcher (SPEC Q-25): a token of the launcher's workload identity, mutual TLS, or the identity provider's service accounts.
- The Rust crates beyond the standard library (the signature check, the HTTP client, the JSON of the vectors) and the C# Ed25519 library: chosen with row 3a, kept to a handful and listed in the pull request.
- Whether the launcher runs in the production cluster or on the workshop host (ADR 0012 only says one per environment).
