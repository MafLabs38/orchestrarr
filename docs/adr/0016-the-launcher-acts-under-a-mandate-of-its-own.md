# 0016 — The launcher acts under a mandate of its own: a signed token per launcher, and the launcher of the home environment serves orders with no environment

- **Status**: accepted by the maintainer on 2026-11-04 (it amends the "approve" half of D-19, a consequence of [ADR 0001](0001-merge-and-deploy-on-operator-approval.md), which stays accepted otherwise), points 1 to 3 except the clauses marked proposed, listed in SPEC D-64 (on condition that the launcher pulls through the control plane's API, D-60, proposed: if the maintainer changes that, points 1 and 3 are revisited; nothing is built: the launcher is row 3a of the [SPEC](../SPEC.md) roadmap; the signed stop statement and the machine routes stay proposals, [ADR 0015](0015-where-the-launcher-gets-what-its-checks-read.md) and SPEC Q-27)
- **Date**: 2026-11-04

## Context

[ADR 0015](0015-where-the-launcher-gets-what-its-checks-read.md) has the launcher pull its orders through the control plane's API and leaves two points open: how the launcher authenticates to that API and knows it is the real one (SPEC Q-25), and who runs an order that has no environment, which is every step that can be approved today, since a merge acts on a repository through the forge, not on an environment (SPEC Q-26). Both are needed before the first slice of the launcher, the dry run.

The principle the maintainer set: **the action is always delegated to a launcher, and a launcher can act only under a real mandate.** A launcher acts on the environment where it runs, and it reaches outward (the forge, another site) only through connections it opens itself.

## Decision

1. **The launcher authenticates to the control plane's API with a signed token of the identity provider, one client per launcher.**
   - **The flow** is the OAuth 2.0 client credentials grant with a signed assertion (`private_key_jwt`). The assertion is short-lived (a short `exp`), single-use (a `jti` the identity provider refuses to see twice) and addressed to the token endpoint (`aud`), so that a captured assertion is worth nothing. There is one client per launcher, so one per environment (D-55), which is what ADR 0015 requires: an identity stable per launcher and distinct per environment.
   - **The key pair** is generated by the provisioning of the launcher's environment (a one-shot job or its infrastructure-as-code), not by the launcher, which holds no right to create or update secrets. The private key is kept in a secret that only the launcher's own workload can read, never the control plane nor the credential of a run, and it is copied nowhere else. It is a secret the launcher reads, not state it writes (the clause of ADR 0014 on state on disk is about what the launcher writes).
   - **The public key is registered** with the identity provider for the launcher's client, **by a person or by the identity provider's own infrastructure-as-code, never at run time by the launcher or the control plane**: neither holds a credential that manages the identity provider's clients, so that one compromise cannot become the identity of every launcher.
   - **The token** lives for minutes. Its audience is the control plane's API. It carries a `launcher` role that **can never be an operator** (D-47) and reaches only the routes for machines (delivery, decision, stop statement, published grants, audit; their detail is SPEC Q-27). A person's session cannot use the routes for machines, and a launcher's token cannot use the routes for people.
   - **Revoking a launcher is disabling its client**: its token expires within minutes and no new one is issued.
   - The launcher knows the API is the real one through **TLS verified against the certificate authority it is configured with**; plain HTTP is refused. Mutual TLS is not used: the signed token replaces it, and the signed stop statement of ADR 0015 §5 (proposed, SPEC D-60) is what keeps a false API from saying the stop is released; it does not depend on this decision. "Authenticated in both directions" in ADR 0015 reads as this.
   - The token is a mandate to **ask for the orders addressed to its own environment**, not a power. The launcher still verifies each order's signature and its own grants and production flags; the token alone starts nothing.
2. **The token gives no access to Vault.** If Vault is later made to accept the same client, its role pins an audience other than the API's, so that a token captured on the API path is useless at Vault. To act, the launcher asks Vault for credentials, for one run and one environment, under its workload identity ([ADR 0012](0012-one-launcher-and-one-vault-role-per-environment.md)). Whether that identity is the same client of the identity provider (Vault accepting its signed token) is settled with Vault's configuration (D-44), not here. The dry run holds no credential to Vault.
3. **The launcher of the environment where the control plane is installed (the home environment) also serves the orders that have no environment**, that is the work done through the forge: merging a pull request. What validating needs, a workshop run, is SPEC Q-28.
   - It lists "no environment" among what it serves (ADR 0014 point 6), as an entry of its configuration with **its own forge credential**, a GitHub App token for one repository from a Vault role of its own, kept apart from the roles that act on the environment, and, as [ADR 0015](0015-where-the-launcher-gets-what-its-checks-read.md) §2 proposes, **its own grants and its own production list per repository** (proposed, with the exception to D-17 that it needs). No other launcher serves such orders, and a launcher serves them only if its configuration says so.
   - This **amends D-55** (one launcher per environment): the home environment's launcher serves two things, the environment and the forge. It replaces the launcher of its own for the forge work that SPEC Q-26 proposed, so there is one kind of launcher.
   - **Whether such an order is production is decided per repository, not once for all** (proposed default, to be confirmed by the maintainer): a merge deploys when its repository is deployed by continuous deployment or by GitOps, so the launcher's configuration says, for each repository it may act on, whether it is production, and a repository that is not listed is production (D-17: unknown is production). The control plane keeps no list of its own (D-17, D-18): it classifies from the environment description, where a repository that is the code or the deployment definition of an application deployed in production, or one the description does not know, is production, so that the step-up of D-51 applies to such a merge; the launcher's list is part of the proposed exception to D-17 for the launcher (ADR 0015 §2). The vectors cover an order with no environment on a repository marked production, on an unlisted one and on one marked not production.
   - **The home launcher runs in a namespace of its own, with a service account of its own** (a requirement of the decision, which follows from D-45, no component being able both to sign and to execute; the namespace and the service account are those of a cluster, and elsewhere an isolation boundary and a workload identity of its own): the control plane's identity has no right there (its service account, its key, its claim), and a run's credential on the home environment can neither read nor write the namespaces of any launcher (its key, its claim, its service account, its pods and token requests), of the control plane, of the identity provider or of the Vault (their workloads, service accounts, secrets and role bindings; the same exclusion D-48 gives the Vault), so that a run cannot change the component that signs, and the forge's Vault role is bound to the launcher's workload identity only, never to the control plane's, so that a compromised control plane cannot both sign and execute (D-45). A run reaches the launcher by no path: not a namespace, not a cluster-scoped object, not a privileged pod, not the node. **The mechanics are proposed defaults (SPEC D-64)**: no cluster-scoped write for a run's credential (RBAC, admission webhooks, CRDs, nodes, volumes), Pod Security `restricted` in the run's namespaces, and the launcher, the control plane, the identity provider and the Vault on nodes that workloads cannot be scheduled on; the tests are that the run's credential is denied `create clusterrolebindings` and a privileged pod.
   - The issuer's map from environment to audience has an **explicit entry for "no environment"**, which is where the home environment is named, with no default: the host that delivers orders refuses to start when a step that has no environment (the merge, and a validation once Q-28 is settled; until then no approval can be delivered) is granted and no entry is configured (a host that only records approvals keeps working), and an order with no environment goes to that audience only.
   - **There are two forge identities.** The control plane's own forge credential (the reader of row 2) has read rights only; the right to merge exists only in the home launcher's forge role. D-19 (frozen), "Orchestrarr's identity may approve and merge", keeps only its "merge" half, held by that role and never by a credential of the control plane; the role never approves, and Q-14 (how a required review is met) is reopened for row 3b.
   - **The forge role is limited at the forge**, so that a compromise of the launcher cannot approve, push, tag or merge code that no person approved, and **it is never installed on the repositories that hold the launch chain**: the launcher's own configuration, the manifests that deploy it and the signer (kept in a repository or a path protected at the forge, apart from the fleet's own GitOps content: until they are, the GitOps repository that holds them is outside the allow-list, and the fleet's updates in it wait for SPEC Q-10), the infrastructure-as-code of the identity provider and of the Vault (they register the launchers' keys and bind their roles), the repositories' settings (`github-template`) and this product's own repository. A merge there would let a compromise raise its own power and reach another environment. The limit is set at the forge, since a check inside a compromised launcher protects nothing; they are also the launcher's protected repositories (ADR 0015 §3), refused whatever the grants say. This is decided.
   - **The rulesets that do this are proposed defaults, settled with row 3b and SPEC Q-14 (D-64)**: the forge adapter calls only the merge endpoint (no ref, tag, content or workflow call) and never holds the `workflows` permission; the merge names the order's head commit as the expected head (the `sha` of the merge endpoint), and the launcher traces a refusal for a moved branch (a refusal code of the contract, with its vector); the repositories carry tag and branch-creation rulesets with the App in no bypass list (D-50 deploys the newest version tag); the default branch requires the approval of the most recent push by someone other than the pusher; an approval by the App never satisfies a required review or a code-owner rule; a *restrict updates* and a *restrict deletions* ruleset on all branches with the App in no bypass list (a per-opener rule cannot be expressed), and the workflows that a push on a non-default branch triggers hold no deploy or publish secret; the allow-list of repositories is SPEC Q-10. A test or a vector covers a head that no person approved, and the App's attempt to push to an existing branch is refused by the forge.
   - The forge's own record (every write event of the home launcher's App, not only its merges; proposed, SPEC D-64) is one of the independent records that an audit compares with the control plane's trail (ADR 0015 §5), so that a merge made without a delivered order shows.
   - A task on a remote environment is run by the launcher of that environment, which opens its connections outward only; the home launcher does not reach into it.

## Alternatives considered

- **The workload token of the cluster (a Kubernetes service account)**: elegant, but it works only for a launcher inside that cluster, so a launcher on another host or site would need a second mechanism.
- **Mutual TLS**: it adds the life of certificates (issue, renewal, revocation) to a product that means to stay light; the signed token covers the identity, and TLS covers the API's.
- **A shared secret** (a client secret): it exists on both sides and travels; a key pair that never leaves the launcher is stronger for the same effort.
- **A launcher of its own for the forge work** (the first proposal for SPEC Q-26): a second kind of launcher to run; rejected by the maintainer in favour of the home environment's launcher.

## Consequences

- The identity provider gains a client per launcher, with a `launcher` role and a short token lifetime. If it is unreachable, no launcher can renew its token, so nothing starts: a failure that stops, which D-43 accepts.
- The home environment's launcher holds more than another: a compromise of it yields the home environment and the forge for the repositories its forge role covers, within the limits of the forge rulesets (proposed, D-64), and so also what a continuous-deployment or GitOps repository of the allow-list deploys to, and no other environment. The two entries of its configuration, and the two Vault roles, are the separation.
- SPEC Q-12 (keys for machines) is settled for the launcher, and Q-25 and Q-26 are resolved. The machine routes stay open (Q-27), and so does the rotation of a launcher's key.
- Tested with row 3a: that a token without the `launcher` role, or one of a person, is refused on the routes for machines and the reverse; that an expired token or one for another audience is refused; that a launcher's token reaches only the order delivered to its own identity; that an order with no environment is delivered to the home environment's launcher only and is classified per repository, and that the host that delivers orders refuses to start when a step with no environment is granted and no entry is configured; and, in the launcher, that it refuses to start without its key, with a plain HTTP address, or without the certificate authority it is configured with; that the forge adapter calls only the merge endpoint, naming the expected head; that the host which delivers orders reads the permissions of its own forge credential at start and, outside Development, refuses to deliver while it holds any write permission (the reader must be a GitHub App installation token, the only kind whose permissions can be read, with read permissions only, named in the README; a credential whose permissions cannot be read counts as holding write, so that unknown means refused as in D-51), with a test that a token of unknown kind refuses delivery; and that a run's credential on the home environment can neither read nor write the namespaces of any launcher, of the control plane, of the identity provider or of the Vault.

## Not decided here

- A merge on a repository that deploys itself, and the base branch that the approval binds (SPEC Q-29), before row 3b. Until it is answered, as a safe default (SPEC D-64), no repository deployed by continuous deployment or GitOps is on the home launcher's forge allow-list, so that its blast radius stays the home environment and the forge.
- Who starts a workshop run, and what validating means for a launcher (SPEC Q-28), which every approval needs, so before the dry run. If the validation and the merge go to different launchers, they are two orders, one per launcher (an order has one environment and one audience).
- Whether the token is bound to the launcher's key (a sender-constrained token) so that a captured token is useless; a bearer token that lives minutes is the default.
- The rotation of a launcher's key (a maximum lifetime of 90 days by default and an API that refuses the token of a disabled client are proposed, SPEC D-64) (how often, and how the identity provider learns the new public key), and where the key is kept where the launcher runs: settled with row 3a (SPEC Q-27).
- The machine routes themselves, the stop statement, and where the launcher runs ([ADR 0015](0015-where-the-launcher-gets-what-its-checks-read.md), SPEC Q-27).
- Whether Vault authenticates the launcher with the same client as the API (point 2), the confirmation of the proposed defaults of SPEC D-64 (the production classification of an order with no environment, the grants and lists of the home launcher), and which identity opens the pull request that a merge acts on (the workshop agent or the home launcher's App) and how a required review is met, settled before row 3b (D-19, Q-14).
