# 0048 — A problem with no pull request is solved by a free agent in staging, and the gateway carries what it made

- **Status**: proposed (accepted when the pull request that carries it is merged)
- **Date**: 2026-11-22
- **Spec**: D-102 ([SPEC.md](../SPEC.md)). Builds on [ADR 0044](0044-a-worker-agent-repairs-the-source-in-staging-and-the-gateway-carries-it.md) (the repair agent and the gateway), [ADR 0046](0046-a-lead-agent-thinks-and-workers-act-on-one-world-with-one-instruction.md) (the lead, workers with one instruction) and [ADR 0047](0047-a-machine-has-a-state-and-leaves-a-reset-isolated-and-qualified.md) (a machine that is isolated by design). Cases 03 and 16 of [CASE-GRID.md](../CASE-GRID.md).

## Context

Until now every row that could be started was a pull request: something to prove, and, when it did not pass, to repair on paper. The other rows (an alert on a dependency, an abandoned library) were shown and could not be ticked ([CASE-GRID.md](../CASE-GRID.md): *only the pull request is actionable*). Yet the cases of the dependencies are about a problem that **has no change yet**: a vulnerable version, with or without a fixed one; a library that nobody maintains. The change has to be **made**, by someone who can read the code, install, build and test.

The maintainer decided on 2026-11-22 that the worker of the staging world is **free inside its machine** (ADR 0047: the machine is the boundary, and it is isolated by design after every reset), and that the control plane holds the whole problem and gives the worker only its instruction (ADR 0046). The repair agent of ADR 0044 is the opposite: it edits a few source files in a container with no network, forbidden to touch the dependencies, the tests or the build. It cannot solve a dependency problem, which is a change to a dependency.

## Decision

1. **A row that has no pull request can be ticked** when the application is described and a runner takes the work (the same gates as a pull request row, `DecisionTable`): the maintainer's tick binds to the row **as it is** (no commit to bind to, the table does not offer a pull request's head). The problem is planned by the lead like any other, which receives the **findings** of the source (an advisory with the installed version and the fixed one, or none; an abandoned library with a replacement that is suggested) as untrusted data fenced with the description, and writes the instruction of the staging worker from them: the facts the worker needs, never the commands. It names only what the data names.
2. **The staging worker of such a problem is a free agent** (Claude Code, on the subscription, in a container that runs as root, with the docker socket of the machine, on a **clone of the default branch** made on the staging machine). It decides how: it installs, upgrades, replaces a library, edits the calls, runs the audit, builds and tests, with the network. Nothing it does can leave the machine (ADR 0047). There is no short limit on its time; the limits are generous settings of the runner (`FreeMaxTurns`, `FreeTimeoutMinutes`).
3. **What it made is read back by the runner, not told.** The runner reads the changed files itself (`git status` in the clone, then each file in slices of what one call may bring back, and the tree they make on the commit), **refuses** what a change may never carry (`ChangePolicy`: a pipeline, a file of secrets or keys, a file that instructs an agent, a deletion or a rename, a file over a size, more than a few dozen files; what the build leaves, `node_modules` and the like, is not a change), runs the steps of the repository **again itself** on what it read (the agent's word is not a fact), and hands over the files, the commit they were made from, the tree, and **the lines that changed, read in the repository by the runner**, so that the controller judges the change and not the agent's account of it.
4. **The gateway carries the change into a pull request.** The act gateway opens it from the files **on the current head of the default branch**, only if that head is the commit the change was made from (a head that moved is refused: the loop makes the change again), and checks the policy again with its own copy (the control plane never trusts the runner's check). The Git and release worlds then merge and deploy that pull request as any other. A problem that has no pull request replaces none.
5. **The controller judges the staging world on what the objective asks.** A count of alerts is what the source reports, and the findings are what the control plane knows: the worker is judged on the findings that are named being fixed (at or above the fixed version), the steps passing, and the lines that the runner read; a finding that has **no fixed version** is not dealt with by leaving the dependency: the exposure must be removed another way (and the problem is complex), or the controller escalates. The later worlds judge only their own objective.
6. **The source of findings is a seam.** `IDependencyFindings` reads what is known about the dependencies of a repository; on the test bed it is a JSON file that the scenarios of the lab write (`Missions:SandboxFindingsFile`), the fake source of the maintainer's reports. A deployment reads Portarr and the scanners through a provider, as the table does. It says nothing when it cannot answer, never a guess.

## Consequences

- The cases 03 (with and without a fixed version) and 16 are played end to end by their scenarios, and the grid is ticked from the replays.
- The root agent in the staging machine is the largest power the product gives an agent, and it is acceptable **only because** of ADR 0047 (isolation by design, qualification before every use, reset after it) and because nothing it produces is believed: the runner reads, checks and re-runs, the control plane re-checks, a pull request carries the change, and the merge, as always, is the act gateway's.
- The image of the free agent (`docker/agent-free`) is built on the staging machine when it is missing (a reset removes it); it is pinned by digest and bumped by Dependabot.
- A binary file cannot be carried yet (the gateway writes text), and a change is limited to the sizes of `ChangePolicy`. A deletion is not carried: the removal of a dependency is a change to its manifest and the code that used it.

## Not decided here

- Where the findings come from in a deployment (Portarr's reports, a scanner), and how a finding is tied to a row when a repository has several alerts: the test bed has one row per repository.
- The mail that tells the maintainer at once (the case 03 frame) and the complex flag beyond the lead's mark: the report of the cases 14 and 03 is its own lot.
