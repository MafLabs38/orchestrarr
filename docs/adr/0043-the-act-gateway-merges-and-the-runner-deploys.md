# 0043 — The act gateway merges, and the runner deploys what the controller accepted

- **Status**: proposed (accepted when the pull request that carries it is merged)
- **Date**: 2026-11-21
- **Spec**: D-97 ([SPEC.md](../SPEC.md), [FUNCTIONAL.md](../FUNCTIONAL.md) FR-WLD-6 to FR-WLD-14, FR-MIS-6). Builds on [ADR 0042](0042-a-runner-serves-one-world-and-the-test-bed-validates-through-the-plan.md), [ADR 0031](0031-a-mandate-is-the-signed-permission-for-a-mission.md), [ADR 0040](0040-the-way-back-is-a-change-the-loop-makes.md) and [ADR 0041](0041-a-problem-is-on-one-repository-and-the-staging-is-held-only-while-it-is-needed.md).

## Context

The first real pass stopped at the Git mandate: nothing merged and nothing deployed. The maintainer asked for the whole path on the test bed: a problem ticked in the table is proved in staging, merged, deployed, verified and closed, each crossing decided by the controller on facts that the control plane read itself.

## Decision

1. **The control plane's act gateway merges; a runner never does and never holds a credential for it.** A runner of the Git world asks `POST /api/v1/runner/missions/{id}/acts/merge`. The control plane reads the pull request from the forge, has the conductor authorise the merge **on this exact head with the power read now** (the checks of the code: the pipeline of the head is green, the diff touches no forbidden path, the claim matches the facts, the stop is not engaged, the mandate lists the act), and only then merges with its own token, a **squash**, telling the forge the head that was authorised (the forge refuses if the branch moved). A refusal says which checks failed; when only the pipeline is not over, the runner may ask again, and a red pipeline is final.
2. **After the merge, what runs is the commit that the merge made on the base branch.** The Git world's dossier names that commit, and the controller reads, next to it, the facts of the control plane: the pipeline of that commit, read from the forge (the update jobs of Dependabot are not the repository's pipeline and are not judged, `GitHub:IgnoredChecks`).
3. **The release is the tree that was proved in staging** (FR-WLD-14). The staging proof builds and tests the **result of the merge** (the test merge that the forge keeps), and puts the tree it built in its evidence. At the crossing into the release world the facts source compares that tree with the tree of the commit that the merge made: a base that moved between the proof and the merge is another artifact, the release is refused and the problem goes back.
4. **The release world deploys the commit that the controller accepted, nothing else.** The runner asks `POST …/acts/deploy`; the gateway authorises the deployment of the accepted commit (the one the Git world's dossier named and the controller granted). The runner then deploys **the way the environment is deployed**: on the deployment machine (never the staging machine), from the repository at that commit, a container built from its Dockerfile, or a compose stack; it says the previous version, verifies the application as a tester would, and hands over. **Nothing is rolled back by the runner**: a release that does not verify is a failed push and the loop goes on with the same problem (ADR 0040).
5. **The control plane looks at the deployed application itself.** The health of a release is read by the control plane from its own settings (`Missions:SandboxDeployHost`, and the port that the repository always lands on, one function in Core), and shown to the controller; the worker's word that it verified is not a fact.
6. **One problem at a time on a repository** (FR-MIS-6): a mission is offered only when its problem is the oldest in progress on its repository, and the later worlds are offered first, so that what was proved is what is merged and deployed. **A mission that the controller sent back is offered again once, with its remarks**; the same mandate goes on.
7. **One runner process serves the three worlds on the test bed** (`MissionRunner:Worlds`), under the one name of `Tasks:Runners` (one is supported, ADR 0017), and the three runners of `Missions:*Runner` name it. This weakens the separation of the worlds, which a deployment must keep (one runner profile per world, each with only its own credentials): the Git world's runner here holds no credential at all, the release world's holds the SSH access to the deployment machine, the staging world's holds the one to the staging machine and the tool that restores it.
8. **Departures kept from ADR 0042** (accepted by the maintainer for the staging proof, and still to be closed): the runner still does not check the signed mandate on its side, and it is the Git and release runner that will get it, with the batches routed between several runners.

## Consequences

- The test bed merges pull requests of the public test-bed organisation for real, with the token of `GitHub:Token`, which must be able to write there; the repository's own protections (required check, rulesets) still apply and are what stops a merge the gateway allowed.
- A pull request whose merge result differs from what was proved is not released: with several pull requests on one repository, one is finished before the next one is proved.
- The deployment recipes (a Dockerfile, a compose file) are written in the runner, an interim like the staging recipes (ADR 0042 6(c)).
