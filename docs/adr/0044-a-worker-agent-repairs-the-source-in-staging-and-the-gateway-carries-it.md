# 0044 — A worker agent repairs the source in staging, and the gateway carries the repair into a pull request

- **Status**: proposed (accepted when the pull request that carries it is merged)
- **Date**: 2026-11-22
- **Spec**: D-98 ([SPEC.md](../SPEC.md), [FUNCTIONAL.md](../FUNCTIONAL.md) FR-WLD-1 to FR-WLD-10, FR-MIS-1). Builds on [ADR 0042](0042-a-runner-serves-one-world-and-the-test-bed-validates-through-the-plan.md), [ADR 0043](0043-the-act-gateway-merges-and-the-runner-deploys.md) and the repair on paper of [ADR 0024](0024-a-pull-request-is-validated-for-real-and-an-agent-may-try-to-repair-it-on-paper.md).

## Context

A change that does not pass in staging (a dependency bump that breaks the application's own code) used to end there: the dossier said that it failed and the controller ended the problem. The maintainer asked for the product to do what a developer does: repair it, prove the repair, and carry it through the same worlds.

**The maintainer decided this in the chat of 2026-11-21**, when the plan of the first real pass was agreed (the third step: "a worker agent, Claude Code, repairs the problems that do not pass, the staging proves it, the pull request is opened and merged") and he said to go on; the choices of this ADR (who writes the commit, what an agent may change, what he sees) are explained to him in the pull request and are his to confirm there.

## Decision

1. **The staging runner starts a worker agent when the steps fail.** Claude Code, in a container of the staging machine, under the subscription of the maintainer. It has the tools `Read`, `Edit`, `Glob` and `Grep` and **no shell, no network tool and no reading of the machine**; every capability of the container is dropped and its resources are bounded. The runner, not the agent, **runs the steps again** on the repaired source, so that "it passes" is never the agent's word. The agent works on a copy without the repository's metadata or the files that instruct an agent; the only secret of its container is the token of the subscription, which reaches it by the standard input of the connection (never in an argument, a script or a trace). What the failing step printed is data between two markers that it cannot guess. The agent tries up to `MissionRunner:Repair:Attempts` times, told after each try what still fails.
2. **What an agent may change is one policy, read by the runner and by the control plane** (`RepairPolicy`, rule 14): the source of the application, **never** what decides whether it passes (the tests and their configuration), what it depends on (manifests and lock files), how it is built and released (pipelines, images, compose files) or what instructs an agent. The protected list is a floor, not an inventory: it also holds the forbidden-paths floor of the conductor (`.github`, `CODEOWNERS`, `.env*`, `*.enc.*`…) and the usual tests, pipelines and settings of the common ecosystems. A repair is 1 to 20 text files, whole, of a bounded size, with plain paths. The runner refuses a try that touches a protected path; **the control plane refuses it again** when the dossier is handed over, whatever the runner did.
3. **The gateway carries the repair; the runner never holds a credential that writes to a repository.** The dossier hands over the files whole; the control plane keeps them (in memory) and, in the Git world, the runner asks `acts/open-pull-request`. The gateway has the conductor authorise the `OpenPullRequest` act, then makes a branch from the tip of the base branch, **merges the change under repair into it** (so that the branch carries the base's own pipeline, which is what the staging proved), puts the repair on top in one commit and opens the pull request, with the token of the gateway and only on the repositories that `Missions:SandboxMergeRepositories` names. The act is written in the audit trail. The branch has a new name at each attempt. Once the replacement is merged, the original pull request is closed, saying where it went (a write of the gateway, on the same repositories, written in the audit trail with the merge). **A repair that was made is never merged around**: the staging dossier says that one was made (`repair:files=N` in its evidence), and while no pull request carries it (it was not opened yet, or the control plane restarted and lost what it held) the merge and the deployment are refused and the problem goes back to staging.
4. **From then on the problem is about the pull request that carries the repair.** The merge, the pipeline and the release read it (`RepairRegistry`); the original is only where the problem started, and the dossiers say so ("replaces #N") so that the controller does not read a discrepancy.
5. **The release is the repaired tree.** The staging proof records the tree of the merge result **with the repair** (made from the merge and those files only, not from what the build left in the folder); at the release the facts source compares it with the tree of the commit that the merge made.
6. **Declared by the test bed's facts, said at start and here**: the pipeline of a repair that is not in a pull request yet is read as green **at the crossing into the Git world only** (no act is judged on it; there is no commit for a pipeline to have run on; the pipeline of the pull request that will carry it is what the merge checks), and the dossier of the staging world names the commit that the repair started from, which the facts source accepts as the claim for the pull request that carries it.
7. **What is not repaired**: a change whose failure needs a protected file (a pin in the requirements, a test, a pipeline) stays failed, the agent's try is refused, and the controller ends it. A build that timed out is not repaired. A pull request that does not target the default branch has unknown facts.
8. **The objective says so**: the problem's objective states that a repair of the source is expected and is part of it, and that the change of the pull request itself touches the manifests, so that the controller does not read the repair as a departure.

## Consequences

- The first code of the product that **writes code**: it goes from the agent to the forge without a person reading it, between two controls (the policy, the conductor's checks, the controller) and the pipeline of the repository, which is the only judge of whether it works outside staging. That is the maintainer's design (the loop, not a review, is the safety), and the PR that carries this ADR says so.
- The agent's image is built on the staging machine when it has none (the machine is restored after each job), which costs a minute on a repair.
- The staging machine's network is open to the agent's container (it calls the model); nothing else of the machine is reachable from it by design, the lab network keeping the staging machines away from what matters is not this runner's job (ADR 0042 6(f)).
- A repair in memory is lost at a restart of the control plane, and so is the link to the pull request that carries it: **what the control plane did is believed, what a runner says it did is not** (a dossier is not a source of the pull request of a repair). After a restart a repair that was made is outstanding, the merge and the deployment are refused, and the loop of the problem makes it again. A staging pass that repairs nothing clears a repair that an earlier pass held.
- The build of the change under test runs with the repository's metadata mounted read-only, so that what its install scripts do cannot reach the commands that the runner then runs on the machine in that folder; the agent works on the committed state, not on what the build left.
- The gateway pushes the repair branch into the repository itself, so that the workflows of the repository run on it with what the repository gives them; the test bed's repositories hold no secret. A deployment would push to a fork or run those workflows without secrets (FR-WLD-10b).
- Closing the pull request that a repair replaces is part of the merge's authorisation and is recorded in the trail with it; it has no act of its own yet.
