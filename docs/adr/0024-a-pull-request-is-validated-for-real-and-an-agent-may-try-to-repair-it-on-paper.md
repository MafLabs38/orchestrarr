# 0024 — A pull request is validated for real in a throwaway container, and an agent may try to repair it on paper

- **Status**: proposed (built in the sandbox on 2026-11-11 at the maintainer's request; accepted when the pull request that carries it is merged)
- **Date**: 2026-11-11
- **Spec**: D-72 (refines D-65 and [ADR 0017](0017-orders-are-typed-tasks-approved-with-a-second-factor-that-the-executor-checks.md); amends [ADR 0023](0023-options-lower-security-only-where-the-host-allows-it-and-the-executor-keeps-its-own-say.md))

## Context

ADR 0017 left the executor as a dry run: it checked everything and started nothing, so nobody could tell whether the chain worked. The sandbox needs a real, bounded run, and the maintainer needs to see an agent work before deciding to give any task a write power.

## Decision

1. **`ValidatePullRequest` runs for real.** The executor fetches the head of the pull request, **refuses it if it is not the commit that was approved** (the fact comes from the forge, not from the task), and runs the steps of the repository's **profile** in a container: no capability, not root, bounded CPU, memory, processes and time, no network except for the steps that ask for it (an install), no credential. The profile (image, steps, commands) is the executor's own configuration, the trusted copy of the commands (kept with the executor for the same reason as its rights list: the double control, Q-31); the `qualify` check of the application's description (D-68, ADR 0020) is the check after a deployment and never supplies a command. A task never carries a command. A step that fails is a result (`failed`), what prevents the run (no profile, no fetch, a commit that moved, a container that does not start) is a refusal. The end of every step's output goes in the chained trace.
2. **`RepairPullRequest` is a third typed task, and a failure makes the row a repair.** There is no switch to tick: when a pull request fails, repairing it is the next thing. The table reads the workshop's latest word on each commit: a pull request whose checks fail on the forge, or that failed when the workshop ran it, **goes up to "Repair"** (where the `repair` step is granted and an executor accepts the kind), and selecting the row is approving the repair. A repair that did not work can be tried again; one that worked (the typed result `Repaired`) leaves a patch and no action (applying it is not built); a pull request that passes in the workshop while the forge fails is said to point at the pipeline, not at a repair. A new commit starts again. The executor validates first (nothing to repair when it passes), lets an agent (Claude Code, headless, on the subscription) edit the code in a container, **refuses a change to a protected file** (tests, dependencies, their configuration, the pipeline, the image: matched anywhere in the repository), then **checks the repair on a clean checkout of the approved commit with exactly the patch applied** (not in the folder the steps and the agent left behind). The instruction is built from a template; what the failing step printed is placed between two markers that are different for each run, as data. The whole work of the agent (what it says, reads, edits and runs) is written in the trace as it happens, so that nothing is a black box.
   - **The agent holds one secret, the token of the subscription, and runs nothing of the pull request's.** It has no shell (the executor runs the steps), no network tool and no reading outside the work folder; it starts with only the user's settings and no MCP server, and the pull request's own instructions (its `CLAUDE.md`, `.claude` folder and MCP file) are removed from its folder and left out of the patch. The token is replaced by `***` in every line of the trace, in its own form and in base64. Its container still reaches the network (the model's API, the package registry): **this sets aside D-28 for the agent's container** while the repair is pointed at a test application only; restricting its egress to the model's API is to be done before it touches anything private.
   - **Git on the host never reads a folder a container can write.** The git directory is kept outside the folder that is mounted, with its hooks, file-system monitor and external programs off, and without the token after the fetch: a `.git/config` written by the code of a pull request or by an agent changes nothing on the host.
   - **Budget.** The operator's approval is the attempt (a failed repair can be approved again, each time a decision of a person), bounded per run by turns and minutes (Q-09, D-27).
3. **Nothing is pushed.** Applying a patch (a commit on the branch of the pull request) is a write power that is not built; it needs the maintainer's decision and its own credential (ADR 0017, point 4).
4. **A runner that changes nothing outside its sandbox does not force the code of the second factor.** ADR 0023 let the code be off only while every runner was a dry run; the validation and the repair also write nothing outside a throwaway container, so they may run on an executor that does not ask for the code (development, where the host allows it). A runner that merges, pushes or opens a pull request never may. The default stays safe: the code is asked for. *The repair holds a credential and has open egress: whether this relaxation is acceptable for the sandbox is the maintainer's to decide (review decision R-39-1); it is revisited before the repair is pointed at anything private.*
5. **The trace is sent while the run goes on**, line by line (ADR 0025), not at its end.
6. **The stop reaches the task that is running.** The executor reads the global stop and its local stop file every few seconds while a run goes on (`Executor:StopPollMilliseconds`, 3000); a control plane that cannot be read three times in a row counts as a stop (unknown means stopped). The task that is running is cancelled: its runner kills its container by name (`docker kill`; stopping the docker client does not stop the container), the task ends as skipped, nothing after it runs, and the run is reported. A shutdown of the executor kills the container the same way.

## Consequences

- The table needs what the workshop said: the queue lists the results of the tasks that ended, and a run that ends tells the screens (topic `runs`), which read the table again.
- **`ChangesNothing` means: nothing is written to a repository or to the host.** It does not mean that nothing runs: a step with `Network` runs the pull request's code with network access in a container, and the repair spends the subscription and holds its token. Whether that is enough for the second factor to be off in the sandbox is the maintainer's decision (R-39-1).
- Docker becomes a power of the executor's user (it can start any container): the executor runs as a user meant for that, and the image of the agent is a build file the maintainer merges (`docker/agent/Dockerfile`, version pinned).
- The container of the agent reaches the network (the API of the model, the package registry). With no shell, the code of the pull request never runs beside the token, but egress is still a reason to restrict it to the model's API before the repair touches anything private.
- A step with `Network` (an install) runs the code of the pull request with network access on the executor's host: allow only the repositories whose pull requests come from people you trust. A pull request from a fork is fetched like any other (`refs/pull/<n>/head`).
- The workshop's verdicts are read from the newest 500 results of ended tasks: a commit older than that window shows as never run. A per-commit store comes with a fleet large enough to need it.
- **A merge needs a pass, not the absence of a failure.** Today a merge is skipped after a validation that was refused, failed or skipped, and goes on after a dry run: before the first real merge runner the gate becomes "a merge requires `Passed` on the same commit", a verdict that comes from the workshop executor and so travels through the control plane as a precondition of the batch.
- **A workshop executor never also merges.** Validating and repairing run the code of pull requests, from a user that can start any container, beside the operators' secrets of the executor. The executor that gets the merge credential (row 3b) is another one, with its own identity and rights list and no `Validation`; `RunnersFor` is to refuse to combine them when the first write runner exists.
- **A patch that can be applied is kept whole.** Only the digest (of the bytes of the file that was checked) and the first 28 KB are in the trace, and the run folder is removed: before the "apply" vertical the whole patch is kept, addressed by its digest, and what can be approved is what can be shown.
- **The containers that have a network reach what the host reaches.** A step with `Network` and the agent run on docker's default bridge, so the code of a pull request in an install step can call the private addresses the workshop host can route to. Until an egress policy exists (D-28), the workshop host itself must block the bridge from the private ranges and from the host (a rule of its firewall), and only repositories whose pull requests come from people you trust are given a profile with a `Network` step. Nothing in the code checks either; this is the same decision as R-39-1.
- One approval starts at most five repairs (`TaskLimits.MaxRepairsPerBatch`; the control plane refuses a bigger selection with `tooManyRepairs`, the executor refuses a bigger batch): each is an agent run that spends the subscription, and the trace of the batch has to fit in the limit of a run.
- A patch that holds a secret of the run (the token of the subscription or of the forge, in clear or in base64) ends the repair as failed, with nothing offered or shown, and so does a patch that changes a binary file (a secret in one would not be found). This is a best-effort check against a careless exfiltration, not a guarantee against an encoded one: the guarantee is where R-39-1 puts it (restricting the egress, or an "after" pass with no network). The agent reads and edits only in the work folder (`Read(//work/**)`, `Edit(//work/**)`; `Glob` and `Grep` need no approval inside it, and a call elsewhere needs one, which this mode refuses), with the deny rules as a second layer.
- A delegation covers only a runner that is a dry run: the executor refuses a delegated batch whose runner runs the code of a pull request (a validation that is configured for real, a repair, and a merge once merging is real), whatever the delegation says. A validation delegation from before keeps working only while no profile is configured. Every container has a read-only image (the work folder and `/tmp` are what is written), and the agent may edit nowhere but the work folder.
- The agent image must not need git: the work folder is given without any `.git` (at any depth), so that a git in the image finds no repository to read.
- The token of the subscription goes to the container as an environment variable, never in an argument or in the trace.
- The workshop's verdict can differ from the forge's: a pull request that passes here and fails on the forge points at the pipeline (an old Node version, for example), not at the pull request. The table shows both.
