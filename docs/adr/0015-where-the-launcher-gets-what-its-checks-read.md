# 0015 — Where the launcher gets what its checks read: delivery, time and a first slice that is a dry run

- **Status**: proposed (safe defaults; the maintainer has not decided them, and Q-25 and Q-26 are open)
- **Date**: 2026-11-04

## Context

[ADR 0014](0014-the-launcher-is-a-rust-binary-held-to-the-control-plane-by-shared-vectors.md) decides that the launcher is a Rust binary held to the control plane's rules by shared conformance vectors. It leaves open what the launcher reads when it decides: the order, the grants, what production is, the stop, the trail, the time. [SPEC](../SPEC.md) D-46 says the launcher "pulls signed orders from the store"; with the control plane's file a single-replica local store ([ADR 0013](0013-approvals-the-trail-and-the-stop-are-kept-in-a-sqlite-file.md)), the store has to be behind the control plane's API. Writing this down also exposes what must hold for the launcher to stay an authorization independent of the one that signs, so this ADR records both the proposal and its constraints.

## Decision (proposed)

1. **Where the launcher gets what its checks read.** The launcher must stay an authorization **independent** of the one that had the order signed (ADR 0007 rule 2: whoever gives an order is authorized twice); if it took its grants and "is this production" from the same API that had Vault sign the order, a compromised control plane could sign any order *and* tell the launcher it is allowed. The reviews of [ADR 0014](0014-the-launcher-is-a-rust-binary-held-to-the-control-plane-by-shared-vectors.md) found what has to hold; none of it is decided yet, the list is the constraint row 3a starts from:
   - **Orders and delivery.** The launcher pulls through the control plane's API, never from the file of [ADR 0013](0013-approvals-the-trail-and-the-stop-are-kept-in-a-sqlite-file.md), and opens no port (SPEC D-46). The API **delivers** an order to the launcher identity of the order's environment and to no other, **once**; the delivery is recorded with the approval lifecycle (ADR 0013), a decision is accepted only from the identity that received it, and a delivered order not decided by its expiry goes back to waiting (whether it can be issued again without the person is settled with row 3a: a production step-up cannot). The launcher does not pull while it cannot accept (see "Ledger and time"), or while the stop is engaged. The order is **proposed to be signed when it is delivered** (D-52 says at run start today), after the control plane has checked again, at that moment, that the approver is still an operator and that the plan is unchanged (`planChanged`, ADR 0010; if it cannot check, it does not sign), so that a launcher in its quiet period does not let an approval go stale, and the card says that a launcher is in it. This is a guard of the API, in addition to the launcher's own, not independent of it. ("Delivery" is not a Vault lease, the word D-43 uses.)
   - **Grants and production** (amends D-10: a power is granted in two places). The launcher's granted powers, its list of production environments, its audience and the environments it serves are its **own configuration**, never asked of the API (one `production` flag per served environment, and one for "no environment", rather than two lists). This **reverses on purpose** what Core does today (`PolicyGrantedPowers`: one source of grants for the card and the launcher): an independent authorization is worth more than one source. The cost is that a power acts in **two places** and the effective power is the intersection, so a card can offer a step that the launcher refuses with `OutsideGrantedPowers`. That contradicts D-11 as written (a step missing from the grants is not offered), so it **amends D-11**; to keep the card honest, the launcher publishes the grants it enforces (or a digest) through the API and the control plane intersects them **for display only**, while the launcher enforces its own copy. For production, the control plane keeps classifying from the environment description (D-17) and the launcher from its own flags: an exception to D-17 for the launcher only, and when they disagree the launcher's answer wins and the step-up is refused late. The matching of grants is held by the vectors (ADR 0014, point 2).
   - **What can change the launcher.** Its configuration, the issuer's map from environment to audience, **its code (`launcher/`, `contract/`), its image and its deployment** change only by a person's review: a check in the control plane would be worth nothing against a compromised control plane, so the guards are elsewhere. **In the launcher**: its configuration lists protected repositories, and its grant matching refuses any order on one of them whatever the grants say (a vector). **At the forge**: Orchestrarr's identity is not installed on the repository of its configuration, and a ruleset (code owners) on those paths requires the review of a person that Orchestrarr's identity cannot give. **At the deployment**: the launcher runs a pinned image digest that a person changes, not the newest tag that D-50 deploys for the control plane (an exception to D-50); its manifests, in the cluster's GitOps repository, change only by a person's review; and the cluster credential issued to a run cannot write the launcher's namespace, nor the claim that lives there.
   - **Ledger and time.** The nonce ledger is **in the launcher's memory**, so that replay protection does not depend on the API and nothing is kept on disk. It is sound under three conditions, all from the launcher's **own** configuration, never from an order or the API: **a quiet period at every start** (nothing is accepted for its own `MaxLifetime + ClockSkew`, on its monotonic time: an order spent before a restart has expired by then, which also covers a recreated volume, a restored snapshot and a copied deployment that starts later); **an issue-time floor** (the launcher keeps its wall-clock start time and refuses any order issued before it minus the tolerance, so a wall clock stepped backwards cannot revive an expired order); and **a clock known to be right** (nothing is accepted until its host reports the clock synchronized; a clock wrong at the start is a deployment requirement, not something the launcher can prove). **It is sound only if exactly one process holds a launcher's identity at a time**, so the launcher takes an **exclusive claim** on its identity before it pulls (a Kubernetes Lease in its own namespace where it runs in a cluster, an equivalent lock elsewhere: a claim that does not go through the control plane's API) and pulls only while it holds it; **a new holder of the claim starts with the quiet period**, and an old holder **stops accepting, not only pulling, as soon as it can no longer prove it holds the claim** (the claim has a short time to live, and a failed renewal counts as a loss; the claim's time to live is configuration, 1 minute by default, and the quiet period of a new holder is at least `MaxLifetime + ClockSkew` plus that time to live), so a handover, a rolling update or a replica started by mistake cannot make a spent order run twice. A copy on another host with a claim store of its own is outside the guarantee; the delivery-once rule of the API and the binding of the Vault identity narrow it. A restart, or a new holder, delays acceptance by up to `MaxLifetime + ClockSkew` (10 min 30 s at the ceiling of D-51). The dry run spends ids as a real run would. The vectors script the time since the start and the wall clock and have the boundary cases.
   - **Stop and trail.** The channel to the API is **authenticated in both directions** (mutual TLS or equivalent; plain HTTP is refused). The global stop is read from the control plane as a **short-lived signed statement**, verified like an order, so that a false API cannot say that it is released, and **unknown, expired or unverifiable means engaged**, plus a local stop on the launcher's machine (an addition to D-43 and F-SAF-01). Every launch therefore depends on the control plane being reachable: an outage of the central container stops every environment, which D-43 accepts for a product that fails closed. The trace is written through the API, and if the launcher cannot record it accepts nothing. The audit route accepts a machine identity (stable per launcher, distinct per environment: a requirement on Q-25), never the approval, release or stop routes, and two kinds of entry only: a decision tied to an order that exists and was delivered to that identity, and an **untrusted refusal**, that is **any refusal before the signature is verified** (the stop, the quiet period, the clock, the verifier, the signature, the shape of the order), with no order id and the subject `unverified`, which never changes an approval. The route takes only the event names of the contract, a bounded detail checked against the audit entry of the vectors, a rate limit per order and per identity, and **deduplicates** untrusted refusals per identity and refusal code, one entry per window with a counter, so that a compromised identity cannot fill the trail that approvals depend on.

   How the launcher authenticates to the API is open (SPEC Q-25).

2. **The first slice that runs the Rust launcher is a dry run**: it pulls, verifies, writes to the audit trail what it would have started, and starts nothing; it holds no credential to Vault, no access to a forge and no container runtime. It proves the chain (the order, the signature, the checks, the pull, the trace) before any power exists. **A dry run takes the approval exactly as a real run would**: the trail names it with an event of its own (`launch.dry-run`), the approval ends in a terminal state flagged as a dry run that a real launcher never takes, and the operator approves again for a real run. **It needs Q-25 settled first**: the audit route is the first route used by a machine, and it must not share the authorization of the routes for people.

## Consequences

- Row 3a changes Core before any vector is generated: the quiet period, the clock check, the issue-time floor and the served environments (ADR 0014 point 6) are added to `Launcher` and `LauncherOptions` (no default audience, a `production` flag per served environment), D-11 is amended, the issuer addresses an order to the launcher of its environment (a map from environment to audience, which retires the shared `"launcher"` default), and the lifecycle of an approval (ADR 0013) gives "an order that exists and was delivered" a meaning.
- The dry run cannot ship before the approval-lifecycle migration of ADR 0013 (today a decision is approved once, ever); that migration comes first in row 3a.
- Tested with row 3a: **the API side of the delivery** (one delivery, the identity of the order's environment only, a return to waiting at expiry, a decision only from the identity that received it, with `FakeTimeProvider`); **the audit route** (machine identity only and refused on the approval, release and stop routes, the two kinds of entry, the contract's event names, the size, the rate, the deduplication, an untrusted refusal never changing an approval); **the launcher's start-up** (it refuses to start with the published test key, without an audience or with `launcher`, and an unknown stop counts as engaged; it pulls nothing without its claim, in its quiet period, with an unsynchronized clock or with the stop engaged); and **the dry run** (no adapter to Vault, a forge or a container runtime in its composition; its entry written once per order; the approval ending in the dry-run terminal state that a real launcher never takes, and a second approval needed).
- A restart or a handover of the launcher costs up to `MaxLifetime + ClockSkew + the claim's time to live` of acceptance (11 min 30 s at the ceiling of D-51 with the default time to live), and every environment stops when the central container is down: both are the price of failing closed (D-43), and are accepted here only as a proposal.
- A power acts in two places, so a card can offer a step that the launcher refuses until the published grants are shown beside it.

## Not decided here

- When the order is signed relative to the approval, how it is issued again after it expires undelivered, and what a production step-up that has gone stale means for that (settled with row 3a, with the open question of [the security model](../security-model.md) on the refresh of the operator's session).
- Whether the exclusive claim and its loss, and the stop statement, are part of the contract of ADR 0014 (a refusal code, a place in the order of the checks, a vector). The stop statement needs its own canonical form and tag, a key usage distinct from the orders', an audience, a sequence and a maximum age, so that it cannot be parsed as an order or replayed: settled with row 3a before the vectors are generated.
- The machine routes (delivery, decision, stop statement, published grants, audit): the allowed identity, the rate and the size of each, written before the first is built; the publication of grants is a machine write that changes what a card shows and gets the audit route's care.
- Q-25: how the launcher authenticates to the API, with an identity stable per launcher and distinct per environment. Q-26: who runs an order with no environment.
- Whether the launcher runs in the production cluster or on the workshop host (ADR 0012 only says one per environment), and the claim mechanism outside a cluster: one open point that row 3a closes before the dry run spends ids.
