# 0015 — Where the launcher gets what its checks read: delivery, time and a first slice that is a dry run

- **Status**: proposed (safe defaults; the maintainer has not decided them, except the identity of the launcher and who serves an order with no environment, [ADR 0016](0016-the-launcher-acts-under-a-mandate-of-its-own.md), and Q-27 is open)
- **Date**: 2026-11-04
- **Superseded in part** by [ADR 0017](0017-orders-are-typed-tasks-approved-with-a-second-factor-that-the-executor-checks.md) (2026-11-09): the launcher is replaced by an executor in .NET, and the order signed by the server by a task approved with a second factor that the executor checks.

## Context

[ADR 0014](0014-the-launcher-is-a-rust-binary-held-to-the-control-plane-by-shared-vectors.md) decides that the launcher is a Rust binary held to the control plane's rules by shared conformance vectors. It leaves open what the launcher reads when it decides: the order, the grants, what production is, the stop, the trail, the time. [SPEC](../SPEC.md) D-46 says the launcher "pulls signed orders from the store"; with the control plane's file a single-replica local store ([ADR 0013](0013-approvals-the-trail-and-the-stop-are-kept-in-a-sqlite-file.md)), the store has to be behind the control plane's API. Writing this down also exposes what must hold for the launcher to stay an authorization independent of the one that signs, so this ADR records both the proposal and its constraints.

## Proposal

The launcher must stay an authorization **independent** of the one that had the order signed (ADR 0007 rule 2: whoever gives an order is authorized twice). If it took its grants and "is this production" from the same API that had Vault sign the order, a compromised control plane could sign any order *and* tell the launcher it is allowed. The reviews of [ADR 0014](0014-the-launcher-is-a-rust-binary-held-to-the-control-plane-by-shared-vectors.md) found what has to hold. **None of it is decided**; this is the constraint row 3a starts from.

### 1. Orders and delivery

- The launcher pulls through the control plane's API, never from the file of [ADR 0013](0013-approvals-the-trail-and-the-stop-are-kept-in-a-sqlite-file.md), and opens no port (SPEC D-46).
- The API **delivers** an order to the launcher identity of the order's environment (for an order with no environment, the home environment's launcher, D-63) and to no other, **once** (a delivery not decided by its expiry goes back to waiting, within the bounds below). The delivery is recorded with the approval lifecycle (ADR 0013). ("Delivery" is not a Vault lease, the word D-43 uses.)
- A decision is accepted only from the identity that received the order, and is recorded and acknowledged by the API **before the run starts**.
- A delivered order not decided by its expiry goes back to waiting. **An approval is issued again only if no decision was recorded for it, and only within bounds** (a maximum age for the approval, one hour by default, and a maximum number of deliveries, so that one tick is never a standing authorization to sign); whether it can be issued again without the person is settled with row 3a (a production step-up cannot; the default is never without a fresh check that the person is still an operator).
- The order is **proposed to be signed when it is delivered** (D-52 says at run start today), after the control plane has checked again, at that moment, that the approver is still an operator and that the plan is unchanged (`planChanged`, ADR 0010); if it cannot check, it does not sign. A launcher in its quiet period does not pull, so an approval does not go stale, and the card says, before the person ticks, that the launcher of the environment is in a quiet period or is only a dry-run launcher (a tick then spends the approval without running anything).
- The launcher does not pull while it cannot accept: in its quiet period, with a clock not known to be synchronized, without its claim, or while the stop is engaged.
- These are guards of the API, in addition to the launcher's own, not independent of it.

### 2. Grants and production (amends D-10, D-11, D-17)

- The launcher's granted powers, its production flags (one per served environment and, on the launcher of the home environment, which serves orders with no environment, a production list per repository for them, ADR 0016), its audience and the environments it serves are its **own configuration**, never asked of the API. The production flag is all it keeps about an environment: no inventory of applications or deployments.
- This **reverses on purpose** what Core does today (`PolicyGrantedPowers`: one source of grants for the card and the launcher). An independent authorization is worth more than one source.
- A power therefore acts in **two places**, and the effective power is the intersection. A card can offer a step that the launcher refuses with `OutsideGrantedPowers`, which contradicts D-11 as written, so it **amends D-11** (and D-10).
- To keep the card honest, the launcher publishes the grants it enforces (or a digest), with its production flags and its per-repository list, through the API, and the control plane intersects them **for display only**; the launcher enforces its own copy.
- For production, the control plane keeps classifying from the environment description (D-17) and the launcher from its own flags: an exception to D-17 for the launcher only. When they disagree the launcher's answer wins and the step-up is refused late; the control plane shows the launcher's published flags beside Portarr's classification, so that the drift is visible.
- The matching of grants is held by the vectors (ADR 0014, point 2).

### 3. What can change the launcher

A check in the control plane is worth nothing against a compromised control plane, so the guards are elsewhere. The files concerned are the **launch contract files**, listed here once (CLAUDE.md rule 15 and SPEC D-61 point to this list):

- In this repository, the launcher and the contract: `launcher/`, `contract/`.
- The C# oracle: `Launcher.cs`, `OrderIssuer.cs`, `LaunchOrder.cs`, `OrderValidation.cs`, `OrderRefusals.cs` in `src/Orchestrarr.Core/Launch/` and the production-classifier port of `Ports.cs` (not `Approver.cs`, nor the other ports, which the approvals and the sign-in use), and the grant matching it relies on (`src/Orchestrarr.Core/WorkItems/ConfiguredPowerPolicy.cs`, `PolicyGrantedPowers.cs`), with their tests, the vector generator included.
- The pins of the Ed25519 libraries (the lines that pin them in `Directory.Packages.props` and `launcher/Cargo.lock`; a bump of any other line of those files stays routine).
- The images: the Dockerfiles and `.dockerignore` (a pull request that only bumps a `FROM` digest of the control plane's Dockerfile stays routine; the launcher's image stays protected).
- The rules and the gate: the whole of `CLAUDE.md` and `.github/CODEOWNERS`, this ADR, ADRs 0014 and 0016 and the rows D-59 to D-64 of `docs/SPEC.md`, and the notes and questions that restate them (the amendments note, Q-14, Q-25 to Q-29) (rule 15 applies to a pull request that edits them; a rule on paths cannot be limited to rows, so the forge does not enforce this part), everything under `.claude/` (agents, skills, settings and hooks), `.github/workflows/ai-review.yml`, the secret-scan settings (the gitleaks configuration and ignore file, when they exist), the workflow files that run the conformance lane and the image scan, and any change to a workflow that touches secrets, permissions or the security steps.
- Outside this repository: the repository's settings (`repos/orchestrarr.yaml` of `github-template`: required checks, code owners ruleset), the launcher's configuration, the issuer's map from environment to audience, the launcher's image and its deployment.

- *Update of 2026-11-10 ([ADR 0017](0017-orders-are-typed-tasks-approved-with-a-second-factor-that-the-executor-checks.md)): the launcher is the executor, and the Rust launcher, the contract vectors, `Launcher.cs`, `OrderIssuer.cs`, `LaunchOrder.cs`, `OrderRefusals.cs` and `PolicyGrantedPowers.cs` no longer exist. The launch contract files are now: `src/Orchestrarr.Executor/`, `src/Orchestrarr.Core/Tasks/` (the task model, the queue port, the journal), `src/Orchestrarr.Core/SecondFactor/`, `src/Orchestrarr.Host/Tasks/`, `src/Orchestrarr.Core/Launch/` (`OrderValidation.cs`, `Ports.cs`) and their tests, together with the rest of this list (images, rules and gate, outside the repository).*

- **The coding agent** does not merge a pull request that touches them, does not enable auto-merge on one and does not approve one (SPEC D-61 and CLAUDE.md rule 15, proposed; followed as a precaution, enforced by nothing but its instruction today).
- **The review gate runs from the base.** Today the review workflow checks out the pull request's merge ref, so the reviewing agents read the pull request's own `.claude/agents/` (and `.claude/` may carry settings and hooks that run shell commands in the job that holds the model token); the action restores `CLAUDE.md` from the base (observed on 2026-11-04 in the reviews of the pull request that introduced this ADR) but not `.claude/`. A pull request could therefore weaken the agents that review it. Requirement: the review step restores **all of `.claude/` and `CLAUDE.md`** from the base branch before the model runs, and the workflow file itself is protected at the forge (code owners on `.github/` and `.claude/`, in the ruleset of `repos/orchestrarr.yaml`). This is a change to the pipeline, to be made in its own pull request, not carried by this one; SPEC row 3a tracks it.
- **At the forge**: Orchestrarr's identity is not installed on the repository of the launcher's configuration, and a ruleset (code owners) on those paths requires the review of a person that neither the coding agent nor Orchestrarr's identity can give. Proposed; `CODEOWNERS` has a single catch-all rule today.
- **In the launcher**: its configuration lists protected repositories, and its grant matching refuses any order on one of them whatever the grants say (a vector).
- **At the deployment**: the launcher runs a pinned image digest that a person changes, not the newest tag that D-50 deploys for the control plane (an exception to D-50); its manifests, in the cluster's GitOps repository, change only by a person's review; and the cluster credential issued to a run cannot read or write the launcher's namespace, nor its key, nor the claim that lives there.

### 4. Ledger and time

The nonce ledger is **in the launcher's memory**: replay protection does not depend on the API, and nothing is kept on disk. It is sound under these conditions, all from the launcher's **own** configuration, never from an order or the API:

- **A quiet period at every start** (`StartQuietPeriod`): nothing is accepted for its own `MaxLifetime + ClockSkew` (`ClockSkew` is the clock tolerance of D-51; `MaxLifetime` is the launcher's lifetime **ceiling**, 10 minutes by default, not the 5 minutes of an order: only the ceiling makes the in-memory ledger sound), measured on a clock that keeps counting while the host is suspended (`CLOCK_BOOTTIME` on Linux, not `CLOCK_MONOTONIC`). An order spent before a restart has expired by then, which also covers a recreated volume, a restored snapshot and a copy that starts later.
- **An issue-time floor**: the launcher keeps its wall-clock start time and refuses any order issued before it minus the tolerance, so that a wall clock stepped backwards cannot revive an expired order.
- **A clock known to be right**: nothing is accepted until its host reports the clock synchronized. A clock wrong at the start is a deployment requirement, not something the launcher can prove.
- **Exactly one process holds a launcher's identity at a time.** The launcher takes an **exclusive claim** on it before it pulls (a Kubernetes Lease in its own namespace where it runs in a cluster, an equivalent lock elsewhere: a claim that does not go through the control plane's API) and pulls only while it holds it.
- The claim has a **time to live** (configuration, 1 minute by default). The launcher measures it on that same suspend-proof clock from its last successful renewal, and refuses to accept when that clock and its wall clock disagree by more than the clock tolerance since the previous check (a suspend or a step), and **refuses to accept**, not only to pull, when that renewal is older than the time to live minus a margin: an old holder that was paused cannot accept after a new one took over.
- **A new holder of the claim starts with a quiet period** (`HandoverQuietPeriod`), `StartQuietPeriod` plus the time to live. A handover, a rolling update or a replica started by mistake cannot make a spent order run twice. A copy on another host with a claim store of its own is outside the guarantee; the delivery-once rule of the API and the binding of the Vault identity narrow it.
- The dry run spends ids as a real run would. The vectors script the time since the start and the wall clock, and have the boundary cases.

### 5. Stop and trail

- The channel to the API is **authenticated in both directions**: the launcher by its signed token, and the API by TLS verified against the certificate authority the launcher is configured with ([ADR 0016](0016-the-launcher-acts-under-a-mandate-of-its-own.md)); plain HTTP is refused.
- The global stop is read as a **short-lived signed statement**, verified like an order, so that a false API cannot say it is released. A replayed copy of the **current** statement is accepted until it reaches its maximum age, so an engaged stop can take up to that age to reach a launcher (the local stop is immediate). The statement carries a **sequence number**, and the launcher refuses one lower than the highest it has seen since its start (a restart forgets it; the quiet period covers that gap, which needs the statement's maximum age to be **strictly below `StartQuietPeriod`**: the launcher refuses to start otherwise). **Unknown, expired or unverifiable means engaged.** A local stop on the launcher's machine is added (an addition to D-43 and F-SAF-01).
- Every launch therefore depends on the control plane being reachable: an outage of the central container stops every environment, which D-43 accepts for a product that fails closed.
- The trace is written through the API, and if the launcher cannot record it accepts nothing.
- The API is not the only record, since a compromised one could acknowledge a write and drop it. The launcher also writes the same entries, **hash-chained** (each carries the hash of the previous one), to its standard output, which the platform's log shipping collects where the control plane cannot write (each start logs a `started` entry with a boot identifier, and the platform's own record of restarts shows whether a start is missing, so that a gap at a restart is visible); the Vault audit device and the command logs of the machines record independently (ADR 0006 point 6). An audit compares them with the control plane's trail.
- The audit route accepts a machine identity (stable per launcher, distinct per environment, ADR 0016), never the approval, release or stop routes, and two kinds of entry only: a decision tied to an order that exists and was delivered to that identity, and an **untrusted refusal**, that is any refusal before the signature is verified (the stop, the quiet period, the clock, the verifier, the signature, the shape of the order), with no order id and the subject `unverified`, which never changes an approval.
- The route takes only the event names of the contract and a bounded detail checked against the audit entry of the vectors, limits the rate per order and per identity, and **deduplicates** untrusted refusals per identity and refusal code, one entry per window with a counter, so that a compromised identity cannot fill the trail that approvals depend on.
- How the launcher authenticates to the API: a signed token of its own, ADR 0016 (SPEC D-62).

### 6. The first slice is a dry run

- The Rust launcher's first slice pulls, verifies, writes to the audit trail what it would have started, and starts nothing; it holds no credential to Vault (the service account that takes its claim is distinct from the one Vault's role is bound to, and has rights on the claim only), no access to a forge and no container runtime. It proves the chain (the order, the signature, the checks, the pull, the trace) before any power exists.
- **A dry run takes the approval exactly as a real run would**: the trail names it with an event of its own (`launch.dry-run`), the approval ends in a terminal state flagged as a dry run that a real launcher never takes, and the operator approves again for a real run.
- Its identity and who serves an order with no environment are settled (ADR 0016). The routes a machine uses are the first not used by a person and must not share the authorization of the routes for people (SPEC Q-27).

## Consequences

- The proposal is annotated where it touches other documents (inline marks and dated notes); D-17 (frozen) is not edited, and D-19 carries a dated mark (ADR 0016): if §2 and §3 are accepted, a new `D-xx` row would record the exceptions: D-64 holds the exception for the home launcher's per-repository list, and D-60 and D-61 are the proposals for the rest. D-55 is amended by D-63 (ADR 0016).
- Row 3a changes Core before any vector is generated: the quiet period, the clock check, the issue-time floor and the served environments (ADR 0014 point 6) are added to `Launcher` and `LauncherOptions` (no default audience, a `production` flag per served environment and, for "no environment", a production list per repository), D-11 is amended, the issuer addresses an order to the launcher of its environment (a map from environment to audience, with an explicit entry for "no environment" and no default, which retires the shared `"launcher"` default), the classification of an order with no environment per repository, an unknown one being production (ADR 0016; `OrderIssuer` and `Launcher` treat such an order as not production today, and the classifier port, which takes an environment, gains the repository: a change to the contract), and the lifecycle of an approval (ADR 0013) gives "an order that exists and was delivered" a meaning.
- The dry run cannot ship before the approval-lifecycle migration of ADR 0013 (today a decision is approved once, ever); that migration comes first in row 3a.
- Tested with row 3a: **the API side of the delivery** (one delivery, the identity of the order's environment only, a return to waiting at expiry, a decision only from the identity that received it, with `FakeTimeProvider`); **the audit route** (machine identity only and refused on the approval, release and stop routes, the two kinds of entry, the contract's event names, the size, the rate, the deduplication, an untrusted refusal never changing an approval); **the launcher's start-up** (it refuses to start with the published test key, without an audience or with `launcher`, and an unknown stop counts as engaged; it pulls nothing without its claim, in its quiet period, with an unsynchronized clock or with the stop engaged); and **the dry run** (no adapter to Vault, a forge or a container runtime in its composition; its entry written once per order; the approval ending in the dry-run terminal state that a real launcher never takes, and a second approval needed).
- A restart or a handover of the launcher costs up to `MaxLifetime + ClockSkew + the claim's time to live` of acceptance (the sum of three configuration values, not a fixed figure), and every environment stops when the central container is down: both are the price of failing closed (D-43), and are accepted here only as a proposal.
- A power acts in two places, so a card can offer a step that the launcher refuses until the published grants are shown beside it.

## Not decided here

- Whether every workflow, not only the review gate and those that touch secrets, permissions or the security steps, should need the maintainer's merge: a security reviewer proposes it, CLAUDE.md rule 12 treats CI work as routine, and the maintainer decides.
- Whether the matching of grants that the card displays is split from the matching that the launcher enforces (today one code serves both, and it is part of the cross-language contract).
- A production step-up is fresh for a few minutes (D-51) and signing at delivery can come later than that (a queue, a quiet period, an outage): such an approval would be refused late, and row 3a settles how.
- When the order is signed relative to the approval, how it is issued again after it expires undelivered, and what a production step-up that has gone stale means for that (settled with row 3a, with the open question of [the security model](../security-model.md) on the refresh of the operator's session).
- Whether the exclusive claim and its loss, and the stop statement (which has its own verification key, under the same start-up refusal of the published test key), are part of the contract of ADR 0014 (a refusal code, a place in the order of the checks, a vector). The stop statement needs its own canonical form and tag, a key usage distinct from the orders', an audience, a sequence and a maximum age (which bounds the time a stop takes to reach a launcher; 1 minute is the proposed default), so that it cannot be parsed as an order or replayed: settled with row 3a before the vectors are generated.
- The machine routes (delivery, decision, stop statement, published grants, audit; SPEC Q-27): the allowed identity, the rate and the size of each, written before the first is built; the publication of grants is a machine write that changes what a card shows and gets the audit route's care: only the identity of that launcher, only the environments it serves, a size bound and an audit entry for every change.
- The rotation of a launcher's key and where it is kept (ADR 0016, SPEC Q-27).
- Whether the launcher runs in the production cluster or on the workshop host (ADR 0012 only says one per environment), and the claim mechanism outside a cluster: one open point (SPEC Q-27), which row 3a closes before the vectors are generated.
