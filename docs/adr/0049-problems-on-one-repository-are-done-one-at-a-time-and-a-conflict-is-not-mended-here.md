# 0049 — Problems on one repository are done one at a time, and a conflict is not mended by an agent that stands in the way of the others

- **Status**: proposed (accepted when the pull request that carries it is merged)
- **Date**: 2026-11-24
- **Spec**: D-103 ([SPEC.md](../SPEC.md)). Extends FR-MIS-6 ([FUNCTIONAL.md](../FUNCTIONAL.md): the lock of a problem on its repository; it does not yet describe the line in which a second problem waits, planned and not started, which is added there when this ADR is accepted), [ADR 0042](0042-a-runner-serves-one-world-and-the-test-bed-validates-through-the-plan.md) (the plan that starts a problem) and [ADR 0048](0048-a-problem-with-no-pull-request-is-solved-by-a-free-agent-in-staging.md). Case 07 of [CASE-GRID.md](../CASE-GRID.md).

## Context

Case 07 asks what happens when many pull requests of one repository are ticked together: an order, a grouping, the conflicts between them, and no ten deployments if one will do. A first reading was a batch: order the pull requests by risk, test their combined result once, merge them in turn and deploy once.

The maintainer set it aside in the chat of 2026-11-24: this is a **Git flow** problem, not a grouping problem. Treating the pull requests one after the other is not a defect; treating them one after the other *carelessly* (without merging one before starting the next) is. So the rule is plain: **no work site starts on a repository while another is going on there.**

## Decision

1. **One work site at a time on a repository.** Problems that are validated together on one repository are done in the order they were validated, each one through its worlds (staging, merge, release) before the next one starts. A problem that has to wait is **planned but not started**: no mandate is issued, no approval is used, so what waits does not expire (the lifetime of a mandate is an hour, and ten problems do not fit in it). It starts when no other problem is in progress on its repository (`ProblemQueue`, `ProblemQueueDriver`; the response of the validation says which rows wait). The line is in memory like the other stores of the test bed. The decision "start now or wait" and the start itself are made **under one gate per repository**, by the validation and by the driver of the line alike, so that two validations (two tabs, two operators), or a validation and a pass of the driver, never both find the repository free. A problem that is not on exactly one repository does not wait: the conductor refuses it. **The global stop empties the line** at the next pass of the driver (every three seconds; the conductor refuses a start while the stop is on, so a stop that is released before a pass leaves the line whole, and what then starts was validated by the maintainer and is checked again at its start; each problem that leaves is in the trail), and a problem that waited longer than the approval lasts (two hours) leaves it too: the maintainer validates again. A start that fails is a refusal like any other, written in the trail (`problem.queue-refused`); it never loses the others.
2. **A problem that does not succeed does not hold the others.** It ends (done, failed, escalated, stopped) and the next one starts. A change that is not sure is never merged: nothing is opened or merged on a failure, and the queue goes on.
3. **A refusal that no agent mends ends the problem at once, and the trail says the code did it.** When the runner stops before building because the pull request **conflicts with its base** (the base moved: an earlier problem of the repository was merged) or **moved since the maintainer approved it**, it says so with a marker in the dossier (`refused:conflict`, `refused:moved`). The control plane, by its code and without asking the controller, ends the problem (the trail has `mission.runner-refused`, never `controller.decided`): the controller would send it back, the same worker could not mend it, and the loop would use its three send-backs for nothing. The marker is a claim of the runner and can only stop work, never widen a power.
4. **What a conflict then needs is a new pull request**: a dependency bot makes its own again on the new base (the lab plays that bot: `lab/sandbox.sh rebase`), and the maintainer ticks it again, on the commit it is now at (the approval is of a commit, so a head that moves is validated again).

## What this holds only on the test bed

- **The certificate of the approval is issued when the problem starts, not when it was validated**, because the approval authority of the test bed is in the process and signs with no code. On a deployment the certificate is issued at the human act (the maintainer's one-time code), so how a long line meets its lifetime (a new approval at start, or a certificate per batch) is **open**, and is the maintainer's to decide when a deployment can start a problem (ADR 0031 point 7).
- **The lead plans a problem when it is validated**, and that plan is used when the problem starts, possibly after the others of its repository, on a base that has moved. A plan only narrows how far the problem goes, and what the base became is read again by the proof and the pipeline, so a stale plan costs a refusal at worst; it is accepted and said here.
- **The order of the line is the order of the selection** (the rows in the order they were sent, then the time they were queued), not a ranking.

## Answered by the maintainer

- **A problem that is escalated frees the repository, and the next one starts**: this stays for a problem that is escalated for another reason than a failed release. For a failed release the maintainer answered, on 2026-11-24, that it is a matter of flow and not of a blocking rule: the problem goes back with a raised priority and holds its repository, so nothing else lands on a failing production ([ADR 0050](0050-the-flow-has-a-priority-from-0-to-100-and-a-failed-release-goes-ahead.md), which withdraws FR-WLD-13's blocking rule).

## Not decided here, not built

- **An agent of the Git world that resolves a conflict** is the maintainer's intended fallback, and it is not built: the rules above are meant to keep the case from arising (it arises only when something moves the base outside this product, or by timing). It is its own change.
- **Grouping, ordering by risk and one deployment for many pull requests** are not built: with one problem at a time each merged pull request is deployed by its own problem. A shared deployment is a possible later optimisation, never a condition of correctness.
- The line is not kept across a restart of the control plane, and it is shown only by the answer to the validation and the trail (`problem.queued`, `problem.queue-refused`). **Showing it on the Missions screen, and a notice in the bell when a waiting problem leaves without starting, are product choices for the maintainer** (rule 16 of `CLAUDE.md`) and are not built.
