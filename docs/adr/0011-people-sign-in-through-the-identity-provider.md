# 0011 — People sign in through the identity provider; the host keeps the session

- **Status**: proposed
- **Date**: 2026-11-03

## Context

[ADR 0006](0006-a-launch-is-a-signed-order-and-credentials-are-short-lived.md) puts the security of an agent that can act in **who can cause a launch**, and says the interface and the API are behind OpenID Connect (SPEC D-40, D-47). [ADR 0010](0010-approving-records-a-decision-and-the-sandbox-operator.md) built the approval with a **sandbox operator** that has no sign-in and that the host refuses outside the Development environment and off the loopback, and listed the sign-in (SPEC Q-12) as a condition before a launcher exists. Until now the API had no authentication at all: the image had to sit behind an authenticating front, which only protects what the front covers.

## Decision (proposed)

1. **The host signs people in itself**, through the authorization code flow with PKCE, as a confidential client of the identity provider (`Approvals:Mode=OpenIdConnect`, section `SignIn`). It does not trust a header that a front adds, and it does not depend on the network around it.
2. **The browser never holds a token.** The host keeps the claims of the identity token in a session cookie (`HttpOnly`, `SameSite=Lax`, `Secure` and named `__Host-orchestrarr.session` as soon as the public address is https, so that a sibling site of a shared domain cannot plant its own session; a fixed lifetime of `SignIn:SessionHours` that use does not extend). No token is kept: no access token, no refresh token. The claim that says a second factor was passed (`acr`), which the handler drops by default, is kept on purpose.
3. **Everything the API says is for a person who signed in**, reads included, because who approved what is not for anybody. A request without a session is a 401 and never a redirect to the provider; `GET /auth/me` is open to any session and says whether the API will answer it; a page of the interface is sent to sign in by the interface itself, which comes back to where it was, and which does not try again within 10 seconds of its last attempt, nor after a failed one, so that a sign-in that does not hold is not a loop. The files of the interface are public (they say nothing about the fleet), and so are `GET /health` and the sign-in's own routes (`login`, `logout`, the two callbacks); `GET /auth/me` needs a session, any session. Any other route under `/auth` is a 404, never the page of the interface.
4. **An operator is a member of a configured group** (`SignIn:OperatorGroup`, read in the claim `SignIn:GroupsClaim`). A group is compared **exactly as the claim writes it**: with Keycloak's full path, `/orchestrarr-operators`, so that a group of the same name in another branch of the tree is not an operator. The subject of an approval is the identifier the identity provider gives (`sub`), which does not change when the person is renamed; the name shown is for display only. Being signed in is not being an operator: somebody who is not one reads, and the approval and the stop are refused with `notAnOperator`, and the interface does not offer them.
5. **Who may read is a choice**: with `SignIn:ReaderGroup` only its members and the operators read; **without one, anybody who signed in reads, which is every account of the provider's realm**. In a shared realm (family, guests, other applications), set it.
6. **The second factor is read, not asked for yet.** When `SignIn:StepUpAcr` is set and the session was opened at that authentication context, the approver carries the moment of it (`auth_time`); otherwise nobody counts as having passed one. Asking for a step-up (sending the person back with `acr_values`) comes with the first production approval.
7. **The addresses come from the configuration, never from the request**: the address the provider sends the code to, the one it sends the person back to after signing out, and the only origin a change may come from. A forged `Host` or `X-Forwarded-Host` changes none of them.
8. **A change must come from the application's own origin.** On top of `SameSite=Lax`, a request that is not a read is refused (`originNotAllowed`, 403) when its `Origin` is not the public one; when it has none, when `Sec-Fetch-Site` says another site; and when it has neither but carries the session cookie. Signing out is a POST, sent as a form, and the provider's own front-channel logout is not used.
9. **The host refuses to start unless it is safe**: the provider's address and the public address are https (http only on the loopback of a Development machine), the client and its secret are set, and the groups, the claim and the lifetime make sense. The secret never goes in a file that is committed. The host reads them into one validated, immutable value.
10. **The sandbox operator stays for the sandbox.** `Development` is unchanged (no sign-in, loopback only). A local identity provider for the demonstration is in `samples/keycloak`.

## Consequences

- A production host has one way to know who approves, and it is the identity provider's. The sandbox operator remains impossible there.
- **The session is a snapshot, and it is not revoked.** The groups are read at sign-in and kept for up to `SignIn:SessionHours` (8 by default): an operator removed from the group, or disabled, still approves and releases the global stop until their session ends; a copied cookie stays valid after the person signs out. Today that gives no power, since nothing runs. Before a launcher exists, the vertical that issues orders must close it, with a server-side session store that can revoke, or a re-check with the identity provider when the order is issued (ADR 0010, conditions). The role is therefore not "checked again with the identity provider" yet, which D-47 and ADR 0010 say the issuer will do.
- The session is encrypted with the host's data-protection keys. Without `SignIn:KeysDirectory` the host uses the framework's default: a folder of the user's profile when there is one, otherwise memory. The image has one, inside the container: the keys survive a restart of the same container, are lost when it is recreated (a deployment, a new image), and a second replica cannot read the first one's cookies; outside Development the host warns of it. With the setting, the keys sit on that volume **unencrypted**: whoever reads it, or a copy of the container's layer, can forge a session, so the volume is a secret. Encrypting them with the Vault belongs to the control-plane vertical.
- Signing out ends the session of the application and sends the person to the provider's end-session page. The provider asks for a confirmation because no token is kept to hint who leaves; that is the price of keeping none.
- The trail and the queue show the subject of the provider (an identifier), not a name. Names come with a later change of the stored schema (ADR 0013).
- A service account cannot sign in this way, so it cannot be an operator (SPEC D-47). Nothing for machines exists yet: nothing needs it.
- A failed sign-in, or a provider that cannot be reached, is logged by the host (a warning, never a claim or a token); signing in and signing out are not logged, and none of them is recorded in the audit trail yet.
- To sign in and read without approving anything, leave `Powers:Grants` empty: nothing is granted, so nothing can be approved (an operator can still engage and release the global stop). With the default `Disabled` mode the API stays open, as the README says.
- The session keeps every claim of the identity token, groups included: with a very large directory the cookie is split into chunks and grows. Keeping only what the approver needs is possible later.
- A subject that the order cannot carry (letters, digits and `. _ - @ : +`: a `|` in the subject of some providers) can sign in but cannot read; `GET /auth/me` says so, and the interface offers the way out.
- Every answer, in every mode, carries `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and a `Content-Security-Policy` that keeps the scripts, styles and requests of the interface to itself and forbids framing (`form-action` is left out: signing out is a form that ends in a redirect to the provider); with the sign-in on and an https public address it also carries `Strict-Transport-Security`. A page of a sibling site cannot frame the interface and make the person click, and a script that found its way into a page cannot load another or send what it reads elsewhere. This also rules out any future embedding of the interface by another product; that would be a new decision.
- A page of another site can start sign-ins in the person's browser: each leaves two cookies, which the browser only sends to `/auth/callback` and which expire after 15 minutes. Many of them could make that one request too large for a proxy, so that signing in fails for that time; the API and the global stop never see those cookies, and nothing is done about it.
- A provider that cannot be reached, or a sign-in that fails, sends the browser back to `/?signInFailed=1`, where the interface says so and offers to try again. A fault of the application itself is not reported as an outage: it is a 500.
- `/auth` belongs to the sign-in even when it is off: any route under it that does not exist is a 404, never the page of the interface.
- The groups must reach the session: in the identity token, or, for a provider that only sends them at the user-information endpoint, read there with `SignIn:ClaimsFromUserInfo`, which takes the groups and the username, plus what the handler maps by default (`sub`, `name`, `given_name`, `family_name`, `profile`, `email`, added unless the identity token carried the same value (when they differ, both are kept and the identity token's comes first)), and never the authentication context. A provider that gates them behind a scope of its own is configured with `SignIn:Scopes`, which replaces the default `openid profile`. The access token is used for that call only and is not kept.

## Not decided here

- How production approval asks for the step-up, which authentication contexts count (a list: providers use levels or URIs), and how long it stays fresh (SPEC Q-21).
- Recording the issuer of the identity (`iss`) with the subject: a subject is only unique within one provider. The schema is fixed (version 1, ADR 0013), so it is now a migration (`user_version` 2).
- Sign-ins and sign-outs in the audit trail.
- Access for machines to the API (keys, or the client-credentials flow), and the link in a mail: it opens the page, which signs in first.
- A shared session store, if the host ever runs as several replicas.
