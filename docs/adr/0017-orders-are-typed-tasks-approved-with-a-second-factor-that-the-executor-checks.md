# 0017 — Orders are typed tasks, approved with a second factor that the executor checks; the executor replaces the launcher

- **Status**: accepted by the maintainer on 2026-11-09, as principles. The mechanisms are settled while the vertical is built; the first slice (a dry run: it checks everything and runs nothing) is built, and "What the first slice settled" below records what it chose.
- **Date**: 2026-11-09
- **Supersedes in part**: [ADR 0014](0014-the-launcher-is-a-rust-binary-held-to-the-control-plane-by-shared-vectors.md) (a Rust launcher and shared vectors), [ADR 0015](0015-where-the-launcher-gets-what-its-checks-read.md) and [ADR 0016](0016-the-launcher-acts-under-a-mandate-of-its-own.md) (server-signed orders, the replay ledger, the quiet periods, the stop statement, the token of the launcher), and the rows D-59 to D-64 of the SPEC in what they say about those. Kept: [ADR 0001](0001-merge-and-deploy-on-operator-approval.md), [ADR 0006](0006-a-launch-is-a-signed-order-and-credentials-are-short-lived.md) and [ADR 0007](0007-a-dedicated-vault-and-a-small-control-plane.md) for the idea that an agent is omnipotent on its environment only for the length of a run, with short-lived credentials, and [ADR 0012](0012-one-launcher-and-one-vault-role-per-environment.md) for one identity per environment.

## Context

The launcher designed in ADR 0014 to 0016 defended against a compromised control plane with an order signed by the server. That signature protects nothing: the control plane signs from its own queue, so a rogue line written in the queue, or a control plane taken over, produces a valid signed order. The real weak point is **what enters the queue**, as in a message queue or the control plane of Kubernetes. The mechanisms around the signature (replay ledger, quiet periods, clock checks, two implementations kept equal by vectors) were heavy for what they protected.

## Decision

1. **A task is typed.** The queue holds tasks of a **closed catalogue** (validate a pull request, merge a pull request, repair a backup, ...), each with parameters checked by shape (repository, number, commit, environment). No free command and no free prompt: the instruction of an agent is built by the server from templates, and what findings say is data. The catalogue is configuration. A free order may be added later, only by configuration.
2. **One entry to the queue**: the approval function, which validates like an admission step. Portarr, the forge and every other source create **proposals** (cards), never tasks. Nothing else writes in the queue's store.
3. **The control plane is not exposed on the Internet**: it answers on the local network or through a VPN only, behind the sign-in with local accounts ([ADR 0018](0018-people-sign-in-with-local-accounts-and-permission-based-roles.md)).
4. **The executor** replaces the launcher: a separate .NET process per environment, with an identity certified by Vault, the only one that obtains the credentials of a run. It takes its tasks only from the control plane (an authenticated channel; it connects out, so an environment opens no inbound port). It has **its own rights list**, in its own configuration: the task kinds, repositories and environments it accepts, whatever a task says, with credentials limited to each kind. Everything is configurable, the safe value being the default; a loosening is a configured choice and is audited.
5. **Every task is approved with a second factor that the executor checks.** The operator gives a one-time code of an authenticator app (TOTP) when approving. The executor verifies it with a secret that **the control plane never holds** (enrolled on the executor's side, kept in Vault or its own store), accepts one use per time step, limits the attempts and locks after failures. The method is **pluggable** (a passkey that signs the content can be added). **Standing delegations**: a task kind may run automatically under a rule (kind, scope, conditions, expiry, daily quota) that the operator approved with the second factor; the executor checks the rule's approval and its limits, and each automatic run still goes through points 4 and 6.
   - **Limit, stated**: a code is not bound to the content. It protects against an order written without the operator (a rogue line in the queue, a control plane taken over while nobody approves). It does not protect against a control plane that sits in the middle of a live approval and swaps the task. A method that signs the content is the upgrade for the kinds that act on production.
6. **Double control.** Before it runs a task, the executor checks its identifier: unique, not expired, never run (the executor keeps its own record), and present in a **record independent of the queue** (the approval journal, shipped out of the queue's store). The facts that authorize an irreversible step (a merge) come from the forge (checks green, same commit as approved), not from what the agent says.
7. **Auditability is a requirement, not a feature.** Every run leaves a complete trace: the task, the result of every check, the credentials issued (identifiers, never values), the agent's tool calls and their outputs, its report and the end state. The trace is append-only and hash-chained, kept by the executor, sent to the control plane and to a journal outside its database. **The interface shows each run as a timeline**, so that a person can see what happened and spot anything odd. Commands run on a machine are also logged on the machine.

## Consequences

- The Rust launcher, the conformance vectors, the quiet periods, the in-memory replay ledger and the stop statement are not built. The verification code is shared by the control plane and the executor (one .NET codebase), so a change to the format of a task changes both in the same pull request.
- The global stop and the budget stay (ADR 0001, F-SAF-01): the executor refuses new tasks and ends the runs when the stop is engaged.
- The first slice runs no agent and holds no credential: it checks everything and writes in the audit trail what it would have started. The validation step (who starts a workshop run, SPEC Q-28) and the required review (Q-14) are settled before the first write power.
- The first write power needs a GitHub App token and the subscription token, not the dedicated Vault yet; Vault comes with the first machine.

## Not decided here

The enrolment of the operator's secret on the executor, its rotation and loss; the channel between the control plane and the executor (certificates from Vault or another); the format of the journal and where it is shipped; the revocation of a standing delegation; which task kinds may be delegated at all. Settled while building, and recorded here. Also open, found by the review of the first slice: whether a delegation ends with the account of its operator (the executor does not know accounts); and that the report of a run is lost when the executor cannot reach the control plane after it ran the batch (the batch then shows as expired), or when a runner fails half way (the dry-run runners cannot); both must be solved before the first real runner. The lockout of the second factor slows guessing down (five tries every fifteen minutes) but does not cap it over a longer period: an escalating lockout is to be considered with the first write power. A merge cannot be delegated yet, and a delegation never covers every repository.

## What the first slice settled

The first slice is a dry run, so the choices below are **interim**: each is replaced before the first write power.

- **Identity of the executor.** A static bearer token per executor, in the host's configuration (at least 32 characters, compared as hashes in constant time), not yet an identity certified by Vault (point 4). Plain HTTP is accepted between the executor and the control plane on a private network; HTTPS is expected beyond it.
- **Where the code is checked.** By the executor, **when it takes the batch**, not when the operator approves. A code is good for about a minute and a half, so `Tasks:BatchLifetimeMinutes` is 2 by default: a batch that waits longer expires, and the operator approves again with a fresh code, rather than being refused for a code that went stale. Splitting the take from the run (check at once, run later) is part of the vertical that runs real work.
- **The journal.** A hash-chained JSONL file that the control plane appends to and the executor reads **from the same path**, so the two share a filesystem. The double control (point 6) is therefore not yet independent of a compromised control-plane host, since that host writes both the queue and the journal. A journal that is torn or tampered with refuses every approval and every batch (it fails closed); the recovery is to stop the host, set the file aside with the executor's own record, and start again, which a journal shipped out of the host and rotated will make routine. Shipping the journal out of the host, append-only for its writer, comes before the first write power.
- **Enrolment and delegations.** Commands of the executor, run in the operator's own terminal (the secret is never shown elsewhere); the operator is named by the id of their account ([ADR 0018](0018-people-sign-in-with-local-accounts-and-permission-based-roles.md)). The executor accepts a batch that cites a delegation, but nothing in the control plane produces one yet: that comes with the vertical that lets it propose them.
- **Routing.** A batch goes to whichever executor takes it first, so the host refuses to start with more than one executor in `Tasks:Executors`; routing by the rights an executor announced comes with the second executor.
- **The trace.** Hash-chained in the executor's own database and sent to the control plane (`/runs/{id}/events`), where the Runs screen shows it as a timeline. The copy in a journal outside the executor's database (point 7) is not built.
- **Limits of the second factor.** Five failures in fifteen minutes lock the subject for fifteen minutes, and one step of clock drift is accepted: fixed defaults for now, not configuration. What is configurable: the rights list, the executor's name and paths, its poll interval, and the control plane's tokens and lifetimes.
- **Not built.** Certification of the executor's identity by Vault, any real runner (validate, merge), the rotation and loss of an enrolment, and a method that signs the content.
- **The task format has no environment yet**, and a batch goes to whichever executor takes it first; both come with the second executor (the rights list then names the environments, and a batch is routed by the rights an executor announced).
- **Sizes and shapes.** A batch holds at most 200 tasks (`TaskLimits`), checked by the control plane when it approves (`tooManyPullRequests`) and by the executor. The executor reuses the shape rules of the control plane (`OrderValidation`), so the two cannot disagree. A delegation names one repository or every repository of one owner (`owner/*`), never more.
- **The executor shares the whole of Core for now.** It links the accounts and the stores it does not use. Splitting the shared part (the task model, the second factor, the shape rules) from the rest is cheap before the first real runner and costly after: it is part of the vertical that adds one.
