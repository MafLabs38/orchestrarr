# 0046 — A lead agent thinks and has no power; workers act on one world with one instruction

- **Status**: proposed (accepted when the pull request that carries it is merged)
- **Date**: 2026-11-22
- **Spec**: D-100 ([SPEC.md](../SPEC.md)). Builds on [ADR 0032](0032-a-controller-agent-grants-the-next-mandate.md), [ADR 0031](0031-a-mandate-is-the-signed-permission-for-a-mission.md), [ADR 0035](0035-the-frame-is-enforced-by-the-environment.md) and [ADR 0045](0045-a-case-is-ticked-by-a-replayable-scenario.md).

## Context

The plan of a problem is fixed in code (staging, then Git, then release) and the controller only judges what a world hands over. Nothing reads the whole problem and decides what to do about it, so the complex cases of [USE-CASES.md](../USE-CASES.md) (many pull requests at once, a major upgrade, a database, several services) have no one to plan them. The reviews of the agents also keep finding the same thing: text written by someone else (a pull request's title, a message, a file) reaches an agent that holds a power.

**The maintainer decided this in the chat of 2026-11-22**: one agent in the control plane has the global view of the problem, only thinks, and has no right to act. The agents that act are started for a mission with a mandate: they have rights only on the world they work in, and only the instruction of their mission. "Without intelligence in the control plane there is no relevant workflow."

## Decision

1. **The lead agent** is the controller of ADR 0032, given the whole problem and one more job. It has no tool, no credential, no write path and a fresh context for each decision. It does two things, and both are **proposals in a fixed structure**:
   - **plan** (before the first mandate): which worlds, in which order, and for each one the instruction of its mission, and whether the problem is complex and why;
   - **judge** (after each handover): grant the next step, send back with remarks, end, or escalate to the maintainer (ADR 0032, unchanged).
2. **It reads the whole problem as data.** The problem as the control plane fetched it (kind, repository, the description with its source, the facts read by the control plane itself, the ceiling the maintainer approved) is given in the fenced section of the prompt, marked untrusted when it comes from a forge. What the lead writes back (an instruction, remarks) is text of an agent that read untrusted data, so it is bounded and is never a power.
3. **The conductor, which is code, decides what is allowed.** A plan is checked before anything starts (`LeadPlanChecks`): the worlds are consecutive, in the order staging, Git, release, and start at the first world of the problem (a staging is never skipped); none goes beyond the powers as they are when the problem starts, so the plan can only stop the work earlier (`PowersFor` tells the lead how far; `HighestWithoutPlan` is what the plan is checked against; then the plan narrows the powers read at each crossing, `HighestNow`); the instructions are short plain text with no marker; the budgets and the frame are the control plane's own. A plan that fails a check is refused, and the problem waits and is reported; it never runs on a default that nobody chose. The mandates are issued and signed by the control plane from the validated plan.
4. **A worker is started per mission, with one mandate.** It has the rights of one world and the instruction of one mission: it never receives the problem as a whole, the plan, the other worlds' instructions or the reasoning of the lead. What it hands over is a dossier, which is data for the lead.
5. **What this does and does not buy in security.** The only agent that reads the whole untrusted problem cannot act, and the agents that act read a short instruction and are held by mandates that the environment enforces (ADR 0035). A hostile title can therefore at most steer the plan among what the code allows. It does not make the lead immune to a manipulated plan, and a review may still flag untrusted text that reaches a model; what changes is the reach of such a flaw.

## Consequences

- **Built.** The plan is asked when the maintainer validates a selection (once per row, at most thirty rows, two questions at a time, nothing asked while the global stop is engaged). The lead is told how far the problem can really go (what was asked and the grant of the application). The plan is checked when it is received, before an approval is made for it, and by the conductor again when the problem starts, on the powers as they are; it is stored with the problem, and **narrows the powers read at each crossing** (`HighestNow`). Each world's mission carries the instruction written for it **apart from its objective**: the objective stays the sentence the control plane states itself, the instruction is data of an agent that read untrusted text, shown to the judge inside the data fence. The plan, its reasons and the complexity mark are in the audit entry of the start; a problem the lead could not plan is in the trail as `lead.refused`. The judge reads the problem too, as data.
- **Who reads the instruction.** The one worker that is a model, the repair agent of the staging world, gets it in its prompt after the runner's own rules, with the statement that it does not lift them. The other workers are code (the staging proof, the Git world, the release world) and ignore it today. The claim of a mission over the runner's wire (`ClaimedMission`) now carries it. The reasons of the plan are shown with the first mission; the instruction itself is in the stored mission and not on the Missions screen yet.
- **Not yet**: a plan that changes after a failure (the lead re-plans), a plan that splits a problem, the mail for a complex problem, a lead of its own model and budget (it shares `Agents:ControllerModel` and `Agents:ControllerTimeoutSeconds` with the judge), **planning in the background** (today the validation waits for the answers, bounded by `Agents:LeadMaxRows` and `Agents:LeadMaxConcurrent`, which is fine for a selection of a few rows and not for a large one), and **the instruction in the signed mandate** (it travels with the claim, outside the signature, like the rest of the claim: when the runner checks the mandate, the instruction must be bound to it).
- Problems that are not pull requests are still `NoAction` in the table; once they can be started (lot 1 of [CASE-GRID.md](../CASE-GRID.md)), their description reaches the lead as data with its source, and the provenance question is settled there.
- A failure to run the lead, to read its answer, or a plan the conductor refuses is never a default plan: the problem does not start and no approval is used. Starting a problem through the validation therefore needs `Agents:Enabled`.
- The lead is an interim use of the maintainer's subscription like the controller (`Agents:Enabled`).
