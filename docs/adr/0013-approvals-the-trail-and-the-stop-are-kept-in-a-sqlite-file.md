# 0013 — The approvals, the audit trail and the global stop are kept in a SQLite file

- **Status**: proposed
- **Date**: 2026-11-03

## Context

[ADR 0010](0010-approving-records-a-decision-and-the-sandbox-operator.md) built the approval with stores in memory, and listed what must exist before a launcher does: a global stop that is **persistent and starts engaged** when its state cannot be read, and approvals and a trail that are **persistent**, the store enforcing the uniqueness of a decision itself. A restart forgot the queue, the trail and the stop, which a sandbox accepts and production does not: a stop that a restart releases is a stop that does not stop.

## Decision (proposed)

1. **One SQLite file** holds the three (`Storage:Provider=Sqlite`, `Storage:Path`). SQLite is what Mnemarr already uses, through `Microsoft.Data.Sqlite` without an ORM, and it keeps Orchestrarr a single container with one volume. `Memory` is the choice of the sandbox: **unset, the provider is `Memory` in Development or when nobody can approve, and the host refuses to start otherwise**, so that a restart never releases the stop by omission. **The image sets `Sqlite` and the file `/config/orchestrarr.db`**, in a volume `/config` (the convention of the *arr images) that only the process can open. The storage lives in its own project, `Orchestrarr.Storage`, behind the interfaces of Core; the routes and the services did not change.
2. **The database itself holds the rules**, not only the code: a unique key on repository, pull request, commit and steps, so that two processes cannot both record the same decision; and triggers that refuse any update or delete of the audit trail, which is append-only. Writing is all or nothing, in a transaction that takes the write lock first.
3. **An approval and its trace are one write.** A narrow port, `IApprovalLedger`, records the approvals and the entry that traces them in the same transaction: either both are in the file, or neither is. It is the only way to write an approval: `IApprovalStore` only reads. A decision already there answers "already approved" without a second entry.
4. **Unknown means engaged.** A global stop whose state cannot be read counts as engaged. Engaging always takes effect, even when it cannot be saved: it is then held in memory, and the status says `killSwitchSaved: false` (the interface warns that a restart would release it). Releasing is the delicate direction: the release must be **saved** (else 503 `killSwitchUnavailable`) and **traced** (else 503 `auditUnavailable`), and the stop and its trace are **one write**: `IKillSwitchControl.ChangeAsync(engaged, entry)` runs both in one transaction, so a failure leaves nothing to undo and a crash cannot leave a release without its trace. The rule lives in the stop, not in the route, so that the launcher or any other caller gets it too.
5. **A database that did not exist starts engaged**, outside Development: a new file is also a lost file, and "nothing was ever stopped" cannot be told from "the state was erased". The host traces `instance.created` and the operator releases the stop once, deliberately. In Development a new file starts released.
6. **An approval or an entry that cannot be written is refused, never lost.** The trail answers "not recorded" and the product fails closed (`auditUnavailable`). A file that cannot be used stops the host **at its start**, not at the first approval; a persistent store with nowhere to persist is never a quiet fallback to memory. A file that becomes unreadable later makes the reading routes answer 503 `storageUnavailable` (never an empty list) while the status still answers, with the stop engaged and not saved. The ledger reads the stop inside its own write, so an approval is never recorded after the stop.
7. **The capacities depend on where things are kept**: 500 approvals and 2,000 entries in memory, 10,000 and 200,000 in a file (`Approvals:QueueCapacity`, `Approvals:AuditCapacity` override both). One policy, shared by both implementations, keeps **a twentieth of the trail (at least one entry) for the global stop and the creation of the database**, and gives refusals three quarters at most, so that a client that is refused again and again, or a trail filled by decisions, cannot make the stop untraceable. A full trail is not the end of the product: the stop still engages, and a release still has its place.
8. **The lists are bounded**: `GET /approvals` and `GET /activity` answer the newest 200 entries by default and at most 1,000 (`?limit=`), because a trail in a file holds hundreds of thousands. An entry of the trail carries its number (`id`, from 1, never changing), so paging further back (`?before=<id>`) will not change the contract; it is a later decision.
9. **Approving is limited per person** (`Approvals:ApprovalsPerMinute`, 30): more is a 429, before anything is recorded, so that a signed-in reader cannot fill the trail with refusals. The global stop is never limited. The same person refused for the same reason is traced once every ten minutes, not at every try (the first entry says who and why; the limit bounds how long it can go on), so that a loop of refusals cannot use up the share of the trail kept for them.
10. **The status says where things are kept** (`storage.kind`, `sqlite` or `memory`), and the interface shows it, and says in words when it is memory that everything is lost at a restart. A host with the sign-in on and the store in memory, outside Development, warns in its log that everything is lost at a restart.
11. **The file is created for its owner only (0600), and only once.** Every later operation opens it read-write: a file that disappears while the host runs is an error, not a new empty database that hides the loss. A folder created by the host is 0700; one that already exists keeps its mode, so mount `/config` with the right owner.
12. **The names of the steps are the file format.** A step is stored by the name of its `StepKind` (`Validate`, `MergePullRequests`, …): renaming one is a schema change, with a new `user_version`.

## Consequences

- An engaged stop stays engaged after a restart, and the trail and the queue survive it. Nothing yet takes an approval, so the lifecycle of an approval (taken, done, expired, superseded when the pull request moved on) comes with the launcher that does.
- The file is a volume to keep and to back up, with SQLite's online backup (`sqlite3 orchestrarr.db ".backup copy.db"`, `VACUUM INTO`), run from a container that has the `sqlite3` tool and mounts the volume: the image of the host does not ship it, and a copy of the file alone while the host runs can be torn. On Kubernetes the pod needs `fsGroup` or `runAsUser` to match the owner of `/config`. It holds identifiers of people (the subject of the identity provider) and their decisions, not credentials: erasing a person on request is not possible without breaking the append-only rule, which is a question to settle with the retention below.
- **One replica, on a local disk.** SQLite's locks are not reliable on a network share, and a rollout that starts the new pod before stopping the old one makes two writers. The deployment uses a single replica with a `Recreate` strategy, as the sign-in already does (ADR 0011).
- The schema is versioned with `PRAGMA user_version`; a database of a newer version is refused, not damaged.
- A tamper-proof trail would need more than a trigger: someone who can edit the file can drop the triggers. The append-only rule defends against the application and against mistakes, not against the owner of the volume. Signing or shipping the trail elsewhere is a later question.

## When a store is full

Nothing removes an approval, and the trail is append-only, so the queue (10,000) and the trail (200,000) have an end. Meanwhile there is a procedure, in the README: stop the host, take the online backup, move the file away and start the host: the new database starts engaged. The retention policy is Q-24.

## Not decided here

- The lifecycle of an approval, and who moves it.
- Retention of the trail past its capacity (today it refuses when full; archiving it, and erasing a person, are later decisions).
- Keeping the trail outside the host (a signed export, or a log shipper).
- A stop that is engaged and held in memory while the trail also cannot be written: it works, but leaves no trace until the file comes back. An engagement that finds the trail full is logged as an error.
- **The identity is a bare subject, with no issuer**: every row of the approvals and of the trail names the person by the subject of the identity provider. One provider per deployment is assumed (ADR 0011), so a subject is unambiguous. Recording the issuer later is a migration that adds a nullable column (`ALTER TABLE ... ADD COLUMN` is not blocked by the append-only triggers, which refuse an `UPDATE` or a `DELETE` of a row): the rows written before it read as "the one provider of this deployment". It is not added now because nothing would fill it until the sign-in hands the issuer to the approver, which is a change of its own.
- **Orders and the stop reach a launcher through the API of the control plane, never through this file** (D-46, D-55): the file is a single-replica, local-disk store that a launcher of another environment cannot open. It follows that a launcher that cannot reach the control plane must count the stop as engaged. Proposed here, decided with the launcher by the maintainer.
- `Storage:Provider=Memory` set explicitly outside Development, with approving on, is the operator's deliberate choice, and its stop **starts engaged** at every start, with an `instance.created` trace, like a new database: a store that forgets everything is a new store. `Storage:MemoryStartsEngaged=false` says otherwise (the tests do). The host logs a warning at its start; the launcher will refuse it (SPEC row 3).
- A health probe that checks the storage, so that a host whose file is unreadable leaves the load balancer.
- Enforcing the single writer (an advisory lock on the file) instead of documenting it; paging further back than the newest entries; a counter table instead of counting the trail at each write.
- **Nothing yet takes an approval, and the migration that adds the lifecycle must not make the old ones work.** Every approval recorded before the lifecycle exists is history, not a waiting order: the migration marks them so (never `waiting`), because a commit approved months ago has long moved on, and a launcher must act on what an operator approved *for the current commit* (ADR 0001).
- The unique key of a decision allows each pull request, commit and steps to be approved once, ever: the lifecycle of an approval (a stepwise migration, a unique key limited to the waiting state) comes with the launcher. Whether the launcher pulls its orders through the API or opens the file is decided with the launcher (ADR 0007, SPEC D-46); the intent is that it never opens this file.
