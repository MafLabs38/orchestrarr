# Review decisions: pull request 39

Real validation, repair by an agent on paper, live screens and a readable table. Every finding of the five agents of the first round (head `b2f5dd2`) was checked in the code. **Fixed** (not entered below, one line each in the pull request's *Review* section): the host `git` that read a folder a container could write (critical), the token and the pull request's code in one container, the pull request's own `CLAUDE.md` and settings steering the agent, the marker that the output could close, the protected paths that did not cover nested files or test configuration, the repair checked in a dirty folder, the stringly-typed "repaired", the live sender that could hide an outcome, the notices of ADR numbers, the documents that said "dry run, starts nothing", and the tests that were asked for.

## R-39-1 | architecture | major | declined

- **Finding**: the repair is classed `ChangesNothing`, so the code of the second factor can be off while an agent runs with the subscription token and open network egress (D-28); either keep the code asked for, or give the agent no shell and restrict its egress to the model's API.
- **Where**: `RepairPullRequestRunner.ChangesNothing`, ADR 0023 §5 and ADR 0024 §2 and §4.
- **Reason**: the exposure that the finding describes is fixed: the agent has no shell (the executor runs the steps), so the code of a pull request never runs beside the token; it cannot read outside the work folder, it does not see the pull request's own instructions, and the token is masked in every line of the trace. What is left is the open egress of the agent's container (nothing in it can use it: no network tool, no shell) and the relaxation of the code for the sandbox. Keeping the code asked for would bring back the second factor at every click in the sandbox, which the maintainer asked to avoid for tests; restricting the egress needs a proxy or a network policy that does not exist yet and is to be built before the repair touches anything private. The relaxation is only possible where the host allows it (never in Production) and, since the third round, the executor itself refuses to start without the code unless `DOTNET_ENVIRONMENT` is Development or Testing, and validation exists only on a host declared a workshop. The ADR 0024 records the exception to D-28. **Added in the fourth round (security review, high)**: an agent that a pull request manages to steer could still try to carry the token out in the patch (written, encoded, into a source file), which the "after" pass then runs with the network of an install step; the reads of `/proc`, `/sys`, `/etc`, `/tmp`, `/root` and now `/dev` are denied, the token is masked in the trace, and the patch is bounded and visible, but the full guarantee is the restriction of the egress (D-28) or a repair whose "after" pass has no network, which the maintainer should decide before a repair touches anything private. This is the same question as above: the token and the open egress. **Added in the tenth round (security review, medium)**: the same open egress lets an install step or the agent reach the private addresses the workshop host can route to (the control plane, Portarr, other machines): until an egress policy exists, the host's own firewall has to block the docker bridge from the private ranges (ADR 0024), and nothing in the code enforces it. The maintainer decides together: keep the code asked for a repair, restrict the egress (a proxy or a network of its own) before the first non-test repository, or accept both for the test application only.
- **Approved**: to be given by the maintainer in a comment of this pull request ("OK to decline R-39-1")

## R-39-2 | architecture | minor | declined
