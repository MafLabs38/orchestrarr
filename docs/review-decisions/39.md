# Review decisions: pull request 39

Real validation, repair by an agent on paper, live screens and a readable table. Every finding of the five agents of the first round (head `b2f5dd2`) was checked in the code. **Fixed** (not entered below, one line each in the pull request's *Review* section): the host `git` that read a folder a container could write (critical), the token and the pull request's code in one container, the pull request's own `CLAUDE.md` and settings steering the agent, the marker that the output could close, the protected paths that did not cover nested files or test configuration, the repair checked in a dirty folder, the stringly-typed "repaired", the live sender that could hide an outcome, the notices of ADR numbers, the documents that said "dry run, starts nothing", and the tests that were asked for.

## R-39-1 | architecture | major | declined

- **Finding**: the repair is classed `ChangesNothing`, so the code of the second factor can be off while an agent runs with the subscription token and open network egress (D-28); either keep the code asked for, or give the agent no shell and restrict its egress to the model's API.
- **Where**: `RepairPullRequestRunner.ChangesNothing`, ADR 0023 §5 and ADR 0024 §2 and §4.
- **Reason**: the exposure that the finding describes is fixed: the agent has no shell (the executor runs the steps), so the code of a pull request never runs beside the token; it cannot read outside the work folder, it does not see the pull request's own instructions, and the token is masked in every line of the trace. What is left is the open egress of the agent's container (nothing in it can use it: no network tool, no shell) and the relaxation of the code for the sandbox. Keeping the code asked for would bring back the second factor at every click in the sandbox, which the maintainer asked to avoid for tests; restricting the egress needs a proxy or a network policy that does not exist yet and is to be built before the repair touches anything private. The relaxation is only possible where the host allows it (never in Production) and, since the third round, the executor itself refuses to start without the code unless `DOTNET_ENVIRONMENT` is Development or Testing, and validation exists only on a host declared a workshop. The ADR 0024 records the exception to D-28.
- **Approved**: to be given by the maintainer in a comment of this pull request ("OK to decline R-39-1")

## R-39-2 | architecture | minor | declined

- **Finding**: the verdicts of the workshop come from the newest 500 results of the whole queue, so an old commit falls out of the window and a "patch ready" row goes back to "Repair".
- **Where**: `ProblemsEndpoints.WorkshopWindow`.
- **Reason**: bounded on purpose, since the query runs on every read of the table; it is a named constant with its reason, and ADR 0024 records the limit. A per-commit store (the latest verdict per repository, pull request and commit, with an index) comes with a fleet large enough to need it.

## R-39-3 | quality | minor | declined

- **Finding**: glyphs (`✦`, `▲`, `▼`) are written in the components instead of coming from the icon registry.
- **Where**: `frontend/src/Decisions/ProblemTable.tsx`.
- **Reason**: they are text marks of a verdict and of a sort direction, read by the page as text (the sort header has its own accessible name); an icon component would add nothing to a screen reader.

## R-39-4 | quality | minor | declined

- **Finding**: `Live.cs` holds four small types; `LiveHub.Path` and `AgentTranscript.Path` shadow `System.IO.Path`; `Answer`/`AnswerOf` and `Kill` names.
- **Where**: `Live/Live.cs`, `AgentTranscript.cs`, `ExecutorEndpoints.cs`.
- **Reason**: naming and file layout, no behaviour; the four types are one idea (the channel) and are tiny.

## R-39-5 | test | minor | declined

- **Finding**: the cut assertion of `AgentTranscriptTests` pins an exact length.
- **Where**: `AgentTranscriptTests`.
- **Reason**: the length is the documented bound of what a trace line keeps (300 characters and a mark); pinning it is the point of the test.

## R-39-6 | test | minor | declined

- **Finding**: the table tests read a whole row as one text and pin the sort order of a column.
- **Where**: `Decisions.test.tsx`.
- **Reason**: a row read as a line is what the operator reads; a change of the order of the columns should break these tests. The sort test pins the numbers, which are the stable language of the table.

## R-39-7 | test | medium | declined

- **Finding**: nothing tests that each executor route announces (claim, lines, end) and only on success.
- **Where**: `ExecutorEndpoints`.
- **Reason**: the rules of announcing (not on a read, a refusal, the executor routes or the sign-in) and the registry's change detection are now tested, and the executor routes are exercised end to end by the real executor in `ExecutorApiTests`; the three calls are two lines each on the same notifier.

## R-39-8 | quality | minor | declined

- **Finding**: exit codes 126 and 127 are treated as "docker could not run the container", although a shell returns them for "command not found" inside it.
- **Where**: `PullRequestWorkspace.DockerCouldNotRun`.
- **Reason**: `docker run` itself returns 126 and 127 when the command of the container cannot be invoked or found, so the two cases cannot be told apart by the code; a missing tool is a fault of the profile or of the image, not a verdict on the pull request, and the refusal says "the container could not be started" with the output in the trace.

## R-39-9 | quality | minor | declined

- **Finding**: the set of steps that become tasks is written in three places of `ApprovalService`; the `Math.Max` limits are repeated; the topics are listed in several places.
- **Where**: `ApprovalService`, `ExecutorWorker`, `LiveChangeMiddleware`.
- **Reason**: no behaviour; each is a one-line list next to the code that uses it, and a test fails when a step kind is missed (`ApprovalSelectionTests`, `LivePublishTests`).

## R-39-10 | security | low | declined

- **Finding**: the disk use of a run is unbounded (a bind mount without a quota).
- **Where**: `PullRequestWorkspace.SandboxArguments`.
- **Reason**: a size limit of a bind mount needs a quota of the file system, which docker does not set by itself; the folders are removed at the end of every run, and the run folders belong on a volume of their own on the host (documented with the executor's configuration). To be set up with the host of the workshop.

## R-39-11 | security | low | declined

- **Finding**: `git add -A` stages what the steps before the agent wrote (build output not in `.gitignore`), so the patch may carry it, attributed to the agent.
- **Where**: `RepairPullRequestRunner.StagedPathsAsync`.
- **Reason**: the repair is checked on a clean checkout of the approved commit with exactly the patch, so extra files cannot make a repair pass by themselves, and the protected paths cover the places that matter; a noisy patch is visible in the trace. A baseline commit before the agent runs would make the patch relative to a tree that the approved commit does not hold.

## R-39-12 | architecture | minor | declined

- **Finding**: the hello does not say whether the validation is real or a dry run.
- **Where**: `ExecutorWorker.Hello`.
- **Reason**: the kinds it reports are now only those that have a runner (fixed); a per-kind dry-run flag is for the status screen when a second executor kind exists.

## R-39-13 | test | minor | declined

- **Finding**: the scripted `git init` effect finds the work folder with the last argument.
- **Where**: `RepairPullRequestRunnerTests`.
- **Reason**: the order of the arguments of `git init` is fixed by git (the directory comes last); a named accessor would only rename it.

## R-39-14 | quality | minor | declined

- **Finding**: a `label` parameter that only names a step, magic numbers for the live and stop timeouts, the order of the `using` lines.
- **Where**: `PullRequestWorkspace`, `ExecutorWorker`.
- **Reason**: the numbers are named constants or options next to their use; `dotnet format --verify-no-changes` passes, so the order of the usings is what the repository's rules say.

## R-39-15 | quality | minor | declined

- **Finding**: the status topic is not published when an executor goes away on its own.
- **Where**: `ExecutorRegistry`.
- **Reason**: the registry already raises `Changed` on a hello and the screens read the connection from the status on every change and on reconnect; a silent disappearance is shown after the executor's liveness window, which is the same for every screen.

- **Where**: `RepairPullRequestRunner`.
- **Reason**: the runtime is decided (D-24, D-25, ADR 0004) and there is one; an interface with one implementation is built when a second runtime exists.
